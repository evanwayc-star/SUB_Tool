## 這個功能要解決什麼

使用者要能一次送出**多份交付**（不同格式、不同解析度），在它們背景執行的同時
繼續編輯專案，並隨時叫出一個監控視窗查看各份的進度、預估時間、已花時間，
以及暫停／繼續／停止個別工作。參考對象是 Final Cut Pro 的 Share ＋ 背景工作視窗。

## 已定案的決策

### D1 — 交付規格是獨立於專案的概念

專案畫布仍由素材決定、仍是預覽與合成的基準；**交付規格**（格式／交付解析度／位元率／
時間碼／音訊編組）一份交付一組，不寫回專案。

*為什麼不是「讓使用者編輯專案輸出解析度」*：那會同時改動預覽、字幕像素座標顯示、
建議位元率與 mpv 那一路，三路一致（§0.1）的驗證面積大很多。

### D2 — 一份交付一個 ffmpeg 程序

不採用「單一 ffmpeg 多路輸出」。佇列**預設同時跑 1 個**，並行度可調。

代價明確接受：N 份交付＝N 次完整讀取與合成，在 44GB MXF 上是成倍的時間。
換到的是逐份暫停／停止、隨時追加、一份失敗不影響其他。
詳見 [ADR-0001](../adr/0001-每份交付各自一個-ffmpeg-程序.md)。

*日後若總批次時間真的痛*：解法是加一層「共用中間母帶」（先合成一次無損母帶，
各份交付從母帶轉），**不是**回頭改用單一 ffmpeg 多輸出。不進第一版。

### D3 — 送出即凍結

按下「加入佇列」的瞬間，把 clips／videoTracks／audioPlan／assText／專案畫布尺寸／
FPS 全部序列化成一個**匯出工作**，之後專案怎麼改都與它無關。

*為什麼不是「開跑才取樣」*：排隊等待造成「送出」與「開跑」之間有時間差，取樣式會讓
同一批交付內容不一致（先跑完的是舊字幕、後跑完的是新字幕），而且不可預測。
三個檔案都成功產出、內容卻對不起來、沒有任何錯誤訊息——正是 §0.6 的形狀。

隨之而來的兩件事：
- 改完專案後要有明確的「以目前專案重新送出」動作，不能讓使用者以為佇列會自動跟上。
- **路徑無法凍結**。素材在等待期間被移走／改名，工作照樣失敗；失敗訊息必須指出是哪個檔案。

關閉專案或開新專案**不影響**已送出的工作——工作已與專案脫鉤。

### D4 — 交付解析度只開放同比例

解析度選單依專案畫布比例產生（1920×1080 專案 → 3840×2160／1920×1080／1280×720／960×540），
**比例不同的尺寸不出現在選單裡**。

實作即「用不同的 `W`/`H` 跑同一條既有 filtergraph」，同比例情況下是**零新不變量**的改動。

*為什麼不開放改變比例*：字幕燒在專案畫布上、位置是該畫布高度的百分比。
16:9 → 4:3 交付時素材 contain 產生上下黑邊，字幕 `posY=91%` 會**落在下方黑邊上**——
畫面正常、字幕在黑條裡。要做對就得決定裁切／黑邊、PiP 與圖片的 0..1 位置以哪張畫布為準、
字幕要不要重排，是一整套新的不變量。改變比例通常是剪輯階段的決定，不是上字幕階段的。

日後要開放時 D4 不擋路：放寬選單即可，屆時再定裁切規則。

### D5 — 不做真暫停

「暫停」是**佇列層級**的：按下暫停後**不再啟動新的工作**，已在跑的那個跑完為止。
個別工作只有「停止」。

*為什麼不做程序層級的真暫停*：Windows 沒有 `SIGSTOP`，唯一的路是 `NtSuspendProcess`——
要嘛引入專案的**第一個原生相依**（`ntsuspend`：node-gyp、`electron-rebuild`、
每次升 Electron 都要重驗），要嘛用 PowerShell P/Invoke 即時編譯（有防毒誤判風險）。
Sysinternals `pssuspend.exe` 的授權不允許隨安裝包散布，直接出局。

這個專案靠「純 JS ＋ 外部執行檔」維持打包穩定，變更紀錄裡已經有「安裝版才壞、
開發版正常」的坑（§0.4 的 fontsdir）。不值得為暫停再加一個「原生模組沒 rebuild 才壞」
的失敗模式。

**停止**則沿用既有作法（記住 proc 後 kill，見 `_currentIngestProc`），並須刪掉半成品
輸出檔——半成品 mp4 比沒有檔案更糟。

### D6 — 佇列的真相來源在主行程；監控視窗是獨立的 BrowserWindow

工作要在專案被改動甚至關閉之後繼續跑（D3），所以**佇列由主行程擁有**，主視窗與監控
視窗都只是它的檢視。這是本專案的一個轉向——目前幾乎所有狀態都由 renderer 驅動。

監控視窗是**獨立 `BrowserWindow`，手寫 HTML，不進 Vite bundle**
（先例：`_mpvWin` 用 `data:` URL、`_mpvGuideWin` 配手寫 preload，`electron/main.js:1740`）。
**不可**載入 `dist/index.html`——那等於把整個 app 開第二份。

*為什麼不是應用內面板*：mpv 是 OS 層覆蓋視窗，會蓋住 HTML（`src/ui.js:39-51` 的
`_modalKeepVideo` 就是為此存在）。面板只要有任何部分蓋到影片區，就要重演「隱藏 mpv
還是靠右停」的取捨。而使用者要的是「平常不佔畫面、需要時叫出來、而且一直存在」，
只有獨立視窗同時給得起。

**明確接受的代價**：這是**第二套 UI 程式碼**，不與 `src/` 共用樣式或元件。
緩解方式是讓它**刻意極簡**（一個清單、每列一條進度、三個按鈕），並在檔案開頭寫明
「這是刻意獨立的一套，不要試圖與 `src/` 共用」。與其假裝能共用而慢慢漂，不如一開始分家。

行為：
- **關掉監控視窗只是關掉視窗，佇列照跑。** 主視窗狀態列要有常駐入口（「輸出 N」）能再叫出來。
- **自動彈出只在兩個時機**：送出第一份交付時、有工作失敗時。全程不彈會讓人以為沒送出，
  每次都彈很煩。

### D7 — 佇列持久化，但重啟後不自動開跑

關閉軟體**不可以**弄丟已排程的交付。

- **存哪裡**：不寫進 `config.json`（快照含完整 `assText` 與 clips 陣列，會讓設定檔膨脹到
  不像設定檔）。改成 userData 下的獨立佇列目錄，**一個工作一個檔**，`assText` 大時另存
  `.ass`。工作結束就刪掉它自己的檔——不必寫回一個大檔，也不會互相覆蓋。
- **關閉 app 時**：正在跑的那個必須 kill（沒有斷點續傳），但它**退回「等待中」而不是消失**，
  半成品輸出檔刪掉。下次開啟它還在佇列裡，從頭跑。
- **重啟後**：所有恢復的工作都是「等待中」，**不自動開始**，使用者按「開始」才跑。
- **恢復時先驗素材**：路徑不存在的工作標成「來源遺失」並指出是哪個檔案，不要讓它跑到
  一半才失敗。

*為什麼不自動開跑*：恢復的工作用的是上次的專案快照，使用者很可能已經改過專案、需要
先看一眼再決定。而且 D5 已把「暫停」定義成佇列層級的開關，「開啟時佇列處於暫停狀態」
剛好共用同一個概念，不必新增語意。

已完成／失敗的工作留在清單上直到 app 關閉（可手動清除），讓使用者看得到已花時間、
輸出路徑與錯誤訊息；**這一類不持久化**。

### D8 — 每份交付都留完整的失敗記錄

現況的弱點（已查證）：`runFF` 失敗時只丟 **stderr 的最後 600 字**
（`electron/main.js:260`），`err` 本身也只保留最後 8000 字（同檔 248 行），
而 renderer 把它塞進一個 **3.5 秒後就消失的 toast**（`src/subio.js:741`）。

**「只留尾端」對 ffmpeg 是最糟的截斷方向**——filtergraph 解析失敗的訊息出現在**開頭**，
後面全是無關的用法說明。§0.4 的 fontsdir 坑就是這個形狀，現行錯誤處理剛好會丟掉那句話。
（`maps` 之所以單獨收集，註解已寫明「出現在輸出開頭，需單獨保留，否則被 err 截斷丟失」
——同一個問題被繞過一次，但沒有被解決。）

1. **保留完整 stderr**，不截斷，寫進該工作的 log 檔（與 D7 的佇列目錄同一處）。
2. **log 開頭寫入完整的 ffmpeg argv**，能直接複製到 shell 重跑重現。§0.4 的教訓是
   「用 `spawn`（無 shell 介入）重測才能確認是程式的問題」——存下實際 argv 才做得到。
3. **監控視窗的失敗列可展開**：上半人話摘要，下半「開啟完整記錄」「複製錯誤」。
4. **摘要要可操作**：找不到來源檔（指出哪一個）／磁碟空間不足／編碼器不可用／
   filtergraph 解析失敗／輸出路徑無寫入權限。認不出來的原樣顯示**前 20 行 + 後 20 行**。
5. **失敗的工作可重試**，重跑同一份凍結快照（D3），不是當下的專案。

與 D7 的衝突已解：**失敗的 log 保留到使用者手動清除**（不隨 app 關閉消失），
成功的工作結束即刪。

### D9 — 匯出對話框改成交付清單

對話框內是一張**交付清單**，可「＋新增一列」，每列一組完整的交付規格，最後一次送出全部。

*為什麼不是「開三次對話框」*：那讓「一次送出多份」退化成「重複同一套操作三次」，
而且每開一次就重跑一次 `_buildExportData()`，三次的凍結時機不同——同一批交付內容
不一致，正是 D3 要擋掉的問題。

**輸出路徑**：選**一次**輸出資料夾（記住上次的），檔名自動生成、每列可改：
`ST_<專案>_<格式>_<高度>p`（例：`ST_Foo_H264_1080p.mp4`、`ST_Foo_ProRes422HQ_2160p.mov`）。
**帶高度是必要的**——D4 讓同一格式可有多種解析度，不帶它兩份就會互相覆蓋。
送出前檢查同批內的檔名衝突與磁碟上的既有檔案，直接在對話框標出來。

**交付範本（FCP 的 Destinations）是對的終點，但不進第一版。** D1 已把交付規格定義成
獨立可序列化的物件，之後要做只剩「存幾組規格 + 命名 + 套用」的 UI，D9 不擋路。

### D10 — ETA 用 ffmpeg 自己報的 `speed=`

stderr 的進度行本來就有 `speed=1.23x`，**現行程式碼只抓 `time=`、把它丟掉了**
（`electron/main.js:251`）。ETA = `(D − 已編碼媒體秒數) ÷ speed`——這是 ffmpeg 對自己
吞吐的直接量測，不是從已花時間外推的猜測（外推在開頭最不準：44GB MXF 的 seek、
hwaccel 初始化、第一個 GOP 都慢，而那正是使用者第一眼看到的數字）。

兩層保護：`speed` 剛啟動時是 `N/A` → 顯示「估算中」而不是假數字；對 speed 取最近數次的
平滑值，避免 ETA 每秒跳動。

*不改用 `-progress pipe:`*：那條解析路徑同時服務 proxy、抽音軌、波形、ingest 五種工作，
動它的風險與收益不成比例。

**不顯示佇列總 ETA。** 並行度可調、後面每份交付的速度取決於它自己的格式與解析度，
總 ETA 只會是一個看起來精確的謊。每份各自顯示 ETA，加一行「還有 N 份等待中」。

**必改**：`task-progress` 改成帶唯一 jobId（現在匯出寫死 `'export'`，
`electron/main.js:845`），並補上 `elapsedMs` 與 `etaMs`。不改的話兩份交付的進度會互相蓋掉。

**順帶修掉的既有缺陷**：影片匯出把 `duration: duration || 0` 傳給 `runFF`（同檔 845 行），
但實際編碼長度是 `D = Math.max(0.05, duration, planDuration)`（602 行）。外部音訊比影片長時，
進度會提早滿格卡在 99%。WAV 那條路傳的是 `D`（617 行），是對的。

### D11 — 解析度清單由高度驅動，但資料模型存寬與高

**資料模型：交付規格存「寬」與「高」兩個數字**，不是只存高度、由專案比例推寬。
UI 現階段只產生同比例的選項，底層卻已接受任意 `W/H`——日後開放改變比例時
不必動資料結構或既有工作的快照格式。

UI：
- **清單由「高度」驅動**，寬 = `round(目標高 × 專案寬 ÷ 專案高)` 取最接近的偶數。
  使用者腦中想的是「交 1080p」，不是「交 1920×1080」。
- **清單內容**：`2160 / 1440 / 1080 / 720 / 540` ∪ 專案畫布原生高度，去重、由大到小。
  **2160 與 1080 置頂**（使用者最常用 FHD／4K），新增一列時預設 1080p。
  原生標「原生」，高於原生標「放大」。
- **允許自訂高度**輸入框，寬度自動算。罕見尺寸走它，不必為此開放改變比例。
- **記住上次選擇**，與 D9 的輸出資料夾一起存進 config。

**「同比例」實務上是「近似同比例」**：H.264／yuv420p 要求寬高皆為偶數，非 16:9 的專案畫布
（例如 2.35:1 的 2048×872）等比縮下去的寬常是奇數，必須取最接近的偶數。誤差在 0.1% 以下，
對 libass 依高度縮放的字幕完全無影響。**寫在這裡是為了讓日後拿計算機驗比例的人不要誤判成 bug。**

**必改**：
- `_suggestMbps()`（`src/subio.js:575`，公式 `w×h×fps×0.12`）現在吃專案畫布，必須改吃
  **該列的交付解析度**。否則 1080p 專案交 4K 時建議值給 7Mbps，而同處註解已記錄過
  「5Mbps 的 4K 匯出細節區有明顯色塊」這個真實回報。
- `_lastVbrMbps`（`src/subio.js:579`）是 session 級的**單一值**，多份交付下必須改成**每列各自**，
  預設為該列解析度的建議值。

### D12 — 直式交付的解法是「專案畫布可設定」，而不是改變比例的匯出

分成兩種需求，結論不同：

- **素材本身就是直式**（手機拍的、直式母帶）：專案畫布本來就是直式，**現有機制已完全支援**，
  D4 自動成立，零額外工作。
- **橫式素材要交直式**（16:9 專案輸出 9:16）：這是改變比例。**不用「匯出時改變比例」來解，
  改用「建立專案時就選直式畫布」來解。**

*為什麼這樣切比較好*：專案畫布目前是個**意外**——由「第一個開啟哪個檔案」決定
（`src/media.js:752`）。同一批素材，先開 4K 那支和先開 1080p 那支，合成基準就不一樣。
把它變成明確選擇之後，字幕從一開始就對著交付畫面排版、預覽看到的就是交付結果、
匯出只剩同比例縮放——裁切 vs 黑邊、0..1 位置以哪張畫布為準、字幕要不要重排，
這一整套新不變量全部不必發明。

**這件事不進本次範圍**（見下節）。

## 已知的下一件：專案畫布可設定

**與本次功能只有概念耦合**（D4 依賴「專案畫布是有意選的」），**沒有實作耦合**——
匯出端本來就只是收下 `W/H` 跑 filtergraph。分開發版是為了讓畫布改動能獨立、完整地
做三路驗證；§0.2 那一系列事故的教訓正是如此。

動手前要知道的四個代價：

1. **三路一致的驗證面積很大**：改專案畫布會連動預覽、字幕像素座標顯示（`posToPx`）、
   `_stageRect()`、mpv 那一路。不能只改一處就當作好了。
2. **視訊軌的 `scale` 目前夾在 ≤1**（`electron/main.js:663`）。橫式素材放進直式畫布只能
   上下留黑，**無法放大填滿**。要做直式交付得放寬這個夾制，並確認 overlay 的負座標裁切
   在視訊軌上也成立——圖片那條路的註解已寫明它可以（同檔 690 行），**視訊軌沒驗過**。
3. **中途改變畫布比例**時，既有字幕的 `posX/posY` 是百分比、數值不變，但相對畫面的落點會變。
   要決定是警告、是重算、還是不管。
4. **專案檔要新增畫布尺寸欄位**，舊專案沒有 → 開啟時用素材尺寸回填。

### D13 — 輸出 stream 編組屬於交付規格，專案音軌仍共用

`audioPlan` 是 `{ buses, streams }` 兩層（`electron/export-plan.js:48`），要分開的是第二層：

- **`buses`＝專案音軌**（A1、A2…）：**專案層級的事實**，八軌就是八軌，不因交付格式而改變。**共用。**
- **`streams`＝輸出編組**：把那些音軌分組成 5.1／Stereo／LtRt／Mono。**這才是交付相關的，進交付規格。**

每個匯出工作送出的是 `{ 共用的 buses, 該列自己的 streams }`——**`export-plan.js` 一行都不用改**，
它本來就是收下一組 `{buses, streams}` 就編譯。

真實案例（使用者提出的）：ProRes 那列 `streams = [5.1(6條), Stereo(2條)]`（八軌），
MP4 那列 `streams = [Stereo(2條)]`。

**既有驗證不會擋路**：「一條專案音軌不能同時指派到多條輸出 stream」
（`electron/export-plan.js:105`）是**針對單一 plan** 的檢查。MP4 那列的 2.0 用掉
ProRes 那列 5.1 也用到的音軌完全合法——兩份交付是兩個獨立的 plan。

**WAV 列沒有輸出編組**（WAV 只依 buses 順序收進同一個多聲道檔，`electron/main.js:604`），
該列音訊摘要顯示「全部專案音軌依序」，不提供編組編輯。

UI：
- 每列一行**音訊摘要**（例 `5.1 + 2.0（8 軌）`）＋「⚙」進入**該列**的編組設定，
  沿用現有 `AudioRouting` 面板，作用對象換成該列的 `streams`。
- **新增一列時預設沿用上一列的編組**（第一列沿用專案上次用過的）。最常見的情況是
  連續加兩三列同樣音訊、只換解析度。
- 「⚙」仍走「關閉再重開」那條路（`modalBg` 疊兩層是架構改動，不值得），
  但 **draft 必須帶整張清單，含每列的編組**——否則按一下聲道設定就清空剛排好的五列交付。

### D14 — 並行度預設 1、上限 3

真正會受益的組合只有一種：**一份走 GPU（H.264）、一份走 CPU（ProRes 無 GPU 編碼器）**，
此時搶的資源不同。其餘情況並行通常更慢：GPU 編碼器只有一組；ADR-0001 已接受
「N 份交付＝N 次完整讀取」，並行等於讓 N 次讀取同時打同一顆磁碟；
`electron/main.js:632` 的註解記錄過「重複開 input 建立過多 hwaccel 實例耗盡 VRAM」。

**設定旁要直接寫明「並行通常不會更快」**，不要讓使用者有機會把自己弄慢還不知道原因。

**匯出時不自動暫停預覽播放**（太侵入，使用者可能正想邊等邊校字幕），
改在監控視窗顯示一行「匯出中，預覽可能卡頓」。

## 建議的實作順序

每一步都應該可獨立驗證，不要等到最後才第一次跑起來。

1. **主行程的佇列骨架**：工作資料結構、狀態機（等待中／執行中／完成／失敗／來源遺失）、
   D7 的持久化讀寫。先不接 UI，用既有的 `outPath` 參數（`electron/main.js:580` 已支援
   跳過存檔對話框）從測試直接送工作進去。
2. **`runFF` 的進度契約**：唯一 jobId、`speed=` 解析、`elapsedMs`／`etaMs`，
   順手修掉 `duration || 0` 那個既有缺陷（D10）。
3. **D8 的錯誤記錄**：完整 stderr ＋ argv 落地成 log 檔。放在這裡是因為後面每一步的除錯
   都會用到它。
4. **監控視窗**（D6）：獨立 `BrowserWindow`、手寫 HTML。
5. **交付解析度**（D4／D11）：`W/H` 進交付規格，`_suggestMbps` 改吃交付解析度。
6. **匯出對話框改成交付清單**（D9／D13）：最後做，因為它依賴前面全部。

`electron/export-plan.js` 是純模組、零 `require`、可在 vitest 直接測——
**匯出參數相關的新邏輯（解析度換算取偶數、檔名生成、衝突偵測）應該落在那裡或同類的純模組**，
不要長回 `ipcMain.handle` 裡面。那正是它被抽出來的原因。

## 驗證要求

`AGENTS.md` §0.3 與 `docs/技術架構說明.md` §0.6：**「有產出」不等於「對」。**

- **交付解析度**：4K 與 1080p 各匯一份，抽同一格出來比對——字幕**相對畫面**的大小與位置
  必須一致（§0.2 的實測表就是這樣做的）。只看「有沒有匯出成功」不算驗證。
- **多份交付**：一次送出 ProRes + MP4，確認兩個檔案的**音訊 stream 數與 layout 各自正確**
  （`ffprobe` 看，不要看 UI 顯示）。
- **持久化**：排三份、關 app、重開——三份都在、狀態是等待中、不會自己開跑。
- **停止**：停止執行中的工作後，確認半成品輸出檔已被刪除。
- **錯誤記錄**：故意讓一份失敗（例如把來源檔改名），確認 log 裡有完整 stderr **與 argv**，
  且把那行 argv 貼到 shell 能重現同一個錯誤。
