# SUB Tool — 開發與驗證

> **接手本專案請先讀 [`技術架構說明.md`](技術架構說明.md) 的 §0「鐵律」。** 那一節列的是
> 「違反後會【靜默】壞掉」的不變量——畫面看起來正常、匯出卻是錯的。本專案絕大多數的 bug
> 都出在那幾條上，而且每一條後面都附了真實踩雷紀錄。
>
> AI 助理另見專案根目錄的 [`AGENTS.md`](../AGENTS.md)。

本專案為 **Vite + 原生 ES 模組**（無框架），打包後輸出**單一可雙擊的 HTML**
（`vite-plugin-singlefile` 把 JS/CSS 全部內嵌），兼顧可維護性與「免安裝、點開即用」。
同一份程式碼同時跑網頁版與 Electron 桌面版（以 `window.subtool` / `IS_DESKTOP` 分支）。

---

## 1. 指令

```bash
npm install           # 第一次（安裝 Vite / Electron / vitest 等）
npm run dev           # 開發：本機伺服器 + 熱更新 (HMR)，開 http://localhost:8777
npm run build         # 打包成單一檔 dist/index.html（內嵌 JS/CSS，可直接雙擊）
npm run preview       # 預覽打包結果
npm run electron      # 打包後以 Electron 桌面版開啟
npm run electron:dev  # Electron 連 dev server（會開 DevTools，驗證用）
npm run dist          # 明確鎖定 Windows x64：electron-builder 產生 NSIS Setup → release/
npm run native:prepare:mac # Apple Silicon：準備並驗證 arm64 ffmpeg / ffprobe
npm run dist:mac:test # Apple Silicon：產生 unsigned 本機測試用 DMG + ZIP
npm run release:prepare -- --version X.Y.Z --date YYYY-MM-DD --notes <notes檔路徑>
npm run release:verify-source # 封裝前核對版號、changelog 與 production source evidence
npm run release:verify-install # 發版前後確認捷徑／解除安裝資訊未指向原始碼工作區（Windows）
npm run lint          # eslint src electron（抓「用了沒 import 的名稱」＋兩道封裝圍籬）
npm test              # vitest run（純函式單元測試）
npm run test:watch    # vitest 監看模式
```

一般使用者：雙擊 `啟動網頁版.bat`（自動 build 並開啟 dist 單一檔）或
`啟動桌面版.bat`（build + Electron）。
開發時要熱更新則用 `啟動網頁開發版.bat`（等同 `npm run dev`，不 build）。

### 前置需求

- [Node.js](https://nodejs.org) 18+
- ffmpeg / ffprobe（桌面版 MXF / 多音軌需要）：Windows 發版機需備妥 `electron/ffmpeg/*.exe`；
  Apple Silicon 由 `npm run native:prepare:mac` 準備 `electron/ffmpeg/darwin-arm64/`。
  執行時若內建工具不可用，才回退環境變數、PATH、Homebrew／常見安裝路徑。
- mpv（Windows 秒開功能）：Windows 發版機需備妥 `electron/mpv/`。第一版 macOS 不啟用
  Windows HWND／named-pipe 專用的 mpv 嵌入，改走 ffmpeg 單次 ingest 與既有 HTML/WebCodecs 預覽。

## 2. 建置與發版流程

### Windows 正式發版

```bash
npm run lint && npm test && npm run build   # ① 三關全綠才繼續
#                                            ② 桌面版真機驗證（見 §3、§4）
# ③ notes 檔只寫版本區段內文（為什麼／怎麼驗），不要自行加版本標題
npm run release:prepare -- --version X.Y.Z --date YYYY-MM-DD --notes <notes檔路徑>
#   → transaction 只改兩份 manifest 版號，並在 changelog 導言後插入一個版本區段
npm run dist                                 # ⑤ 產出 release/SUB Tool Setup X.Y.Z.exe
#   → predist 先跑 release:verify-source，再跑 verify-native-binaries.js 核對本機
#     electron/ffmpeg/ 與 electron/mpv/ 齊全（這兩個目錄不進版控，見
#     Electron_維護手冊.md §4／§5）；缺檔或殘檔會讓這一步直接失敗並印出取得方式，
#     而不是悄悄產出一支少了 ffmpeg 或 mpv 的安裝檔
# ⑥ 正常執行新 Setup；UAC 後確認預設為 C:\Program Files\SUB Tool，並啟動確認 app 內顯示 X.Y.Z
npm run release:verify-install               # ⑥a 必須通過：捷徑／解除安裝資訊不可指向原始碼工作區
git status --short                           # ⑥b 只暫存已確認屬於此版的檔案，勿在共用工作樹直接 git add -A
git add <已確認的發版檔案> && git commit && git push origin main
# ⑦ 建立 GitHub Release，附上同一支 Setup .exe、tag 與面向使用者的變更說明
```

### Apple Silicon 本機測試版

macOS 產物必須在 **Apple Silicon Mac** 上建置。優先用 `git clone`／`git pull` 取得原始碼；
若從 Windows 複製整個資料夾，必須先移除 Windows 產生的 `node_modules`、`dist`、`release`，
再於 Mac 重新安裝。Mac 封裝規則只收 `electron/ffmpeg/darwin-arm64/`，不會把同資料夾內
被 Git 忽略的 Windows ffmpeg/mpv 一起塞進 DMG。

```bash
npm ci
npm run lint && npm test && npm run build
npm run dist:mac:test
# → release/SUB Tool-<版本>-mac-arm64.dmg
# → release/SUB Tool-<版本>-mac-arm64.zip
```

`dist:mac:test` 會依序下載與複製 arm64 ffmpeg/ffprobe、檢查 `ass`／`libx264`／
`prores_ks`／`pcm_s24le`／`mxf` 能力、核對檔案大小與執行權限，再建立 **unsigned**
DMG/ZIP。第一次開啟若被 Gatekeeper 擋下，僅在你確認這是自己剛建出的產物時，先嘗試開啟一次，
再到「系統設定 → 隱私權與安全性」選擇「仍要打開」；步驟以
[Apple 官方說明](https://support.apple.com/guide/mac-help/open-an-app-by-overriding-security-settings-mh40617/mac)為準。

這條流程只供本機功能驗證，不是可公開發佈的 Mac 正式版。第一階段刻意不提供看似正式的
Mac 發布指令；對外發佈流程必須另行加入 Developer ID 簽署、hardened runtime、Apple
notarization 的 fail-closed 驗證，並在乾淨帳號／另一台 Mac 驗證 DMG、App、檔案關聯與
實際版本。簽署與公證尚未在第一階段啟用。

> ### ⚠ 升版時絕對不要做版號的全域字串取代
>
> 文件裡的版號有兩種：`## [v4.31.2]` 標題、「v4.27 起的安裝版才開始壞」這類**歷史事實**
> （永遠不要動），以及少數的當前版本範例。全域取代會把前者一起改掉。
>
> **真實事故**：`17aa365` 升版時對 `版本變更紀錄.md` 做了全檔取代，95 筆歷史版號一次全毀，
> 內文還出現「v5.2.0 造成、v5.2.0 修復」這種自相矛盾的句子。v5.2.0 又重演一次。
> 已於 v5.2.2 從 git 還原。
>
> **各文件標頭刻意不寫版號**——`package.json` 是唯一真相來源。

`release:prepare` 會先找與 HEAD manifest 版號相同、內容一致且可由 HEAD 抵達的 Git tag；若該版
尚無 tag，則從 first-parent 歷史找出首次引入該版號的 commit。這個已發布邊界到目前工作樹之間的
`src/`、`electron/`、`shared/`、`scripts/` 才算 production source evidence，舊版本的 source diff
不可被下一版重複利用。只有文件變更、當前版本標題重複、`### 驗證` 沒有實際內容或 manifest
版號不一致都會 fail closed。三個目標檔案先在記憶體通過 content guards，寫入途中失敗則回復原內容。
`npm run dist` 會再次執行唯讀的 `release:verify-source`，所以 prepare 之後又被手改壞也無法封裝。

**變更紀錄請寫「為什麼」與「怎麼驗的」，不要只寫「修了 X」。** 這份檔案是本專案最有價值的
交接資產——很多坑（字型家族名、filtergraph 跳脫、CSS 蓋掉 `[hidden]`）都是靠它才沒有重踩。

> 本專案採 **main 直接發佈**。若工作樹混有未確認的修改，不能直接 `git add -A`，
> 必須先確認哪些檔案屬於這一版。**本專案由多個 AI 工具並行維護，這點特別重要**——
> 你看到的未提交變更可能不是你做的。

### 安裝器 smoke 的安全邊界

`release/SUB Tool Setup X.Y.Z.exe` 是**真正會修改系統安裝、捷徑與解除安裝登錄**的 NSIS 安裝器，
不是可隨意解壓的測試檔。正式版本採全機安裝，正常路徑為
`C:\Program Files\SUB Tool`，執行時會要求 UAC。

- **絕不可**對正式 Setup 使用 `/D=<原始碼工作區或暫存資料夾>`；這會把真正的安裝與公開捷徑改指向測試路徑。
- 若需要自動驗證封裝後的 Electron，請使用 electron-builder 的 unpacked `--dir` 產物，或在 Windows Sandbox／VM／隔離帳號執行 Setup；不可在日常開發機用 Setup 當 smoke 測試。
- 正式安裝完成後必跑 `npm run release:verify-install`。若它偵測到 SUB Tool 捷徑或解除安裝資訊指向原始碼工作區，先以該安裝的解除安裝程式完整移除，再重新安裝；不要直接刪資料夾。

## 3. 真機驗證（CDP）——本專案的主要驗證手段

單元測試只涵蓋純函式（時碼、格式、工具、資料完整性）。
**UI 與媒體行為一律以 CDP 驅動真的 Electron 視窗驗證**，不靠肉眼點一點就算過。

```bash
# 用【獨立的 user-data-dir】啟動 dev electron，切勿殺掉使用者安裝的 SUB Tool.exe
electron . --remote-debugging-port=9223 --user-data-dir=<暫存目錄> \
           --disable-background-timer-throttling --disable-renderer-backgrounding \
           --disable-backgrounding-occluded-windows
# 再用 CDP 連上去 Runtime.evaluate 一段 async IIFE，操作 UI 並回傳斷言結果
```

- 前端掛有 **`window.SUB`** 除錯把手：`State / Media / Wave / SubFormats / Project`
  與各渲染函式，另有 **`window.SUB.WC`**（WebCodecs 診斷）與
  **`window.SUB.SubStyle`**（樣式系統）。驗證腳本靠它建構情境（塞 cues、切軌、觸發渲染）
  再讀回結果。
- **互動要發真事件**（CDP `Input.dispatchMouseEvent`）。`Runtime.evaluate` 造假事件
  驗不到 pointer capture／pointer-events／hit-test——事件沒接上正是重構最常見的錯。
- **背景視窗的 `setTimeout`/`rAF` 會被節流** → 一定要加上面那三個 flag，並 `Page.bringToFront()`。
- **測試必須自己處理擋路的對話框**：例如 `openCueEditModal` 會先 `await ensureProjectSaved()`，
  全新實例下會跳「開始前先儲存專案」把後續視窗擋住。不處理的話，
  「前一輪剛好把專案標記成已存檔就過、換個乾淨實例就掛」——這種看時機決定過不過的測試比沒測還危險。
- **每支測試用全新實例跑**：共用同一個 app 實例時，前一支留下的選取狀態會污染後一支。
- **列表定位要驗最終幾何，不可只驗 `scrollIntoView()` 被呼叫**：至少建立兩軌、每軌 80 句的跨軌案例，點遠端字幕後等待兩個 `requestAnimationFrame`，再確認 `.sub-row.sel.primary` 的 `getBoundingClientRect()` 與 `#sublist` 可視範圍相交。不要在包裝的 `scrollIntoView()` 內讀列幾何或 `scrollHeight`；這會強迫版面配置並觸發 scroll anchoring，反而掩蓋 `content-visibility:auto` 的第一幀漂移。

### 3.1 現成工具：`scripts/acceptance/cdp-run.js`（v6.1.3）

把一段 JS 送進正在執行的視窗並取回結果，`console.log` 會轉發到終端機：

```powershell

& "C:\Program Files\SUB Tool\SUB Tool.exe" --remote-debugging-port=9223
```

```bash
# ② 送腳本進去
node scripts/acceptance/cdp-run.js scripts/acceptance/in-page/verify-v6-1-2-wiring.js 9223
```

`scripts/acceptance/in-page/verify-v6-1-2-wiring.js` 是 v6.1.2 的接線驗收（事件訂閱、按鈕不丟例外、
焦點軌配對、ASS 的 PlayRes）。要驗別的就自己寫一支 async IIFE 傳進去。

文本匹配的 TXT 匯入可在完成 `npm run build` 並以相同 CDP 方式啟動 Electron 後驗收：

```bash
node scripts/acceptance/verify-transcript-txt-import.js
```

這支腳本會啟動獨立 Electron，透過 CDP 真實滑鼠事件命中按鈕，再用
`DOM.setFileInputFiles` 匯入實體 5,000 行 TXT；同時檢查 `FileReader`、文字框、有效行數、
首末行及手動編輯後不再顯示過時摘要，不會呼叫雲端辨識 API。

辨識來源與文本匹配失敗診斷的聚焦契約可先用下列指令驗證：

```bash
npx vitest run tests/speechRecognition.test.js tests/speechRecognitionCancellation.test.js tests/speechRecognitionEngineCancellation.test.js tests/speechRecognitionWorkerRuntime.test.js tests/transcriptAlignment.test.js tests/transcriptAlignmentDiagnostic.test.js tests/whisperCloudChunking.test.js tests/speechAudioCompressor.test.js tests/speechPreloadBoundary.test.js --maxWorkers=1
```

驗收內容包括：8 個來源聲道的全部平均、單軌、最後兩軌會形成不同 WAV PCM；同一資源不會被重複加權；共用單聲道 URL 不顯示假的單軌選項；對話框選擇會真正傳到 provider 前的 AudioBuffer；OpenAI／Groq 長音訊會以 600 秒／10 秒 overlap 分段、每份 WAV 小於 20 MB、word 與 segment 加回正確全域時間，timestamp 抖動跨 core 不會重複且實際連說相同字仍保留；桌面 MP3 adapter 只接受受限 PCM WAV、以 64 kbps 壓縮並在成功／失敗後清除暫存，取消 IPC 會終止 ffmpeg 並立即以 `AbortError` 收斂；匹配失敗會列出一基行號，下載 JSON 只含白名單欄位且不含 API Key、素材路徑或音訊。人工驗收還應確認「最後兩軌」標籤只表示確切軌號，不把它宣稱為 Stereo。

完成 build 後，可再跑 Electron／CDP 真機路徑：

```bash
node scripts/acceptance/verify-recognition-audio-source.js
```

腳本以獨立 user-data-dir 建立 8 軌素材，透過真實右鍵、鍵盤與按鈕開啟辨識視窗，再攔截假的 Groq fetch；第一輪會檢查完整選單、選定「來源聲道 3」後的實際 WAV PCM 與成功建立的字幕軌；第二輪用低覆蓋稿件確認失敗面板顯示第 1、2 行且沒有新增錯誤字幕，再以真實滑鼠點「匯出診斷 JSON」、攔截下載邊界並解析內容，驗證行號、理由、稿件與敏感欄位排除；第三輪用 20 行高覆蓋但漏第 11 行（恰好 5%）的句級時間稿件確認建立完整初稿、視窗保留、正確顯示全 20 行都需抽查（其中第 11 行為推估）與「不是精準對齊」，且開始按鈕鎖為「已建立」避免重複寫入。它不會連線到外部服務、寫入下載檔或碰正式 API Key。

### 3.2 版面驗證：`scripts/acceptance/preview-queue-window.js`（v6.1.6）

```bash
node scripts/acceptance/preview-queue-window.js   # → dist/__queue-preview.html（已 gitignore）
```

把 `electron/queue.html` 注入假的 `queueAPI` 與各種極端資料（長檔名、五條字幕軌、
4K 大碼率、有／無 TC、執行中、WAV、失敗），產出可直接用瀏覽器開的檔案。

> **jsdom 測不到版面。** `tests/queueLayout.test.js` 驗得到 DOM 結構，
> 但 jsdom **不做版面計算**——元素被 flex 壓成省略號、或兩個標籤疊在一起，
> 它一律全綠。
>
> 真實事故（v6.1.5）：字幕標籤被壓成一個省略號還被「燒入 TC」疊住，測試全綠；
> 修的時候第一版又把窄視窗的按鈕疊到檔名上，同樣全綠。兩次都是靠這支預覽
> ＋ `getBoundingClientRect()` 量出來的。**改佇列 UI 後請至少在 1250px 與 980px
> 兩個寬度量一次**（斷點在 980px 與 620px）。

量測方式（瀏覽器 console 或用 §3.1 的 `cdp-run.js`）：兩兩比對
`getBoundingClientRect()` 是否重疊、`scrollWidth > clientWidth` 是否被截斷。
對應 §0.7「有沒有顯示只能量，不能用看的」。

**四個會卡住你的地方**（都實際撞過）：

| 症狀 | 原因 | 解法 |
|------|------|------|
| `Ctrl+Shift+I` 沒反應 | `main.js` 的 `win.setMenu(null)` 連帶移除了 Electron 內建的 DevTools 快捷鍵 | 用本節的 CDP 方式；安裝版沒有其他入口 |
| `localhost:9223` → `ERR_CONNECTION_CLOSED` | Windows 上 `localhost` 先解析成 IPv6 `::1`，但偵錯連接埠**只綁 IPv4** | 一律用 `127.0.0.1:9223` |
| 連接埠沒在聽 | **單一實例鎖**：舊實例還活著時，帶旗標的新實例會立刻退出並把焦點交給舊的 | 先確認行程真的結束（見下） |
| DevTools 開了又斷（`WebSocket disconnected`） | 同一目標只能接一個 DevTools 客戶端；Chrome 內建前端的版本也可能與 Electron 對不上 | 別用前端，直接走 CDP |

> **「看不到視窗」不等於「沒在跑」。** 這支 app 會為了匯出佇列監控把主視窗隱藏但保持執行
> （`_mainHiddenForQueue`）。動手前先確認：
>
> ```powershell
> Get-Process -Name "SUB Tool*"; Get-NetTCPConnection -LocalPort 9223 -State Listen
> ```

### 五個「驗證方法本身出錯」的案例（別再犯）

| 案例 | 當時檢查的 | 為什麼測了等於沒測 |
|------|-------------|-------------------|
| v4.33.2 預覽畫布全黑 | `getImageData` 讀得到像素、inline `style.display` 是 `''` | **隱藏的 canvas 照樣讀得到像素**；`''` 只代表沒有 inline 值，實際 computed 是 `none` |
| v4.34.1 編輯提示列藏不掉 | `el.hidden === true` | `.ts-line{display:flex}` 是作者規則，**蓋過 UA 樣式表的 `[hidden]{display:none}`**——屬性是 true，畫面上照樣看得到 |
| `audio:busChanged` 事件連線 | 用 `toMatch` 掃原始碼有沒有 `emit('audio:busChanged'` | **只證明字面沒被改掉**，被測函式一次都沒被執行到。改成 import 真模組、點真按鈕後，才發現得了退步 |
| 同上，重繪驗證 | 在 `tlLayer` 埋哨兵，看重繪後有沒有被沖掉 | `drawTimeline()` **不清 `tlLayer`**，它呼叫子函式各自重建自己的容器（`renderTrackRows()` 清的是 `tlTracks`）。哨兵埋在父容器 → **假陰性**，看起來像沒重繪 |
| v5.7.0 轉檔中關視窗要確認 | 用 CDP `Page.close`（或 renderer 的 `window.close()`）關監控視窗，看有沒有被攔下 | 兩者都等同 `win.destroy()`，**會跳過 `BrowserWindow` 的 `close` 事件**——只有 `closed` 會觸發。於是任何 `close` 攔截都驗不到，測試連續「失敗」而程式其實是對的。要驗 `close` 攔截只能送 **`WM_CLOSE`**（PowerShell + user32，等同使用者點 ✕） |

第五例的教訓與前四例相反但同源：**測試「失敗」不代表程式錯**——先確認你的驗證途徑
真的會走到被測的那條路。當時若相信那個失敗而去改程式，就會把正確的邏輯改壞。
（找出真相的方法是在主程序的 `close`／`closed`／`before-quit` 各插一行暫時性 log，
看見 `close` 從來沒印出來。）

前兩次都是**改用 computed display／截圖**才發現。判斷「有沒有顯示」請用
`getComputedStyle(el).display` 或 `getBoundingClientRect().height`。
判準詳見 [`技術架構說明.md`](技術架構說明.md) §0.6「有產出不等於對」與 §0.7。

**兩個可直接套用的手法**：

- **哨兵**：在會被清空的容器裡塞一個 `<i data-sentinel>`，操作後看它還在不在。
  比對 innerHTML 長度不可靠（重繪後長度可能一樣）。**前提是先確認那個容器真的會被清空**
  ——上表第四列就是踩在這裡。
- **突變測試**：測試綠燈後，故意把程式改壞再跑一次。**沒有變紅的測試等於沒有測試**。
  例：拿掉 `emit('audio:busChanged')` 應該讓事件測試紅燈；讓 `live` 分支也發事件，
  應該讓「拖曳不重繪」的測試紅燈。驗完記得還原。

>
> 別用 SendKeys 硬打路徑進那個對話框：時序沒抓準的話按鍵會落到別的視窗，
> 而且重複點擊會疊出好幾個對話框把 app 卡住。

## 4. 大檔人工驗證清單

以下這批**需要真實大檔、只能人工判讀**（媒體管線、混音、FPS 一致性）。
一般功能改動請用 §3 的 CDP 自動驗證。

啟動方式（看得到錯誤，建議開兩個終端機）：

```bash
npm run dev           # 終端機 1：vite dev server
npm run electron:dev  # 終端機 2：Electron 連 dev server（自動開 DevTools）
```

> **開檔有兩條路徑**：Windows 偵測到 **mpv** 時，非原生格式或多音軌會以 mpv **秒開**
> （嵌入式覆蓋視窗播放），音軌於背景抽取；無 mpv 則走 **ffmpeg 單次讀取轉檔**（有進度 %）。
> Apple Silicon 第一版固定走後者。兩種路徑的字幕編輯與混音器行為必須一致。

### 4.7 FPS / 時碼一致性

> 背景與設計原則見 [`FPS_時碼一致性.md`](FPS_時碼一致性.md)；程式關鍵點以 `FPS-SYNC` 標記。
> 建議用 **29.97fps NDF** 的長片（一小時以上）測，最容易暴露問題。

- [ ] **同格**：seek 到任一字幕起點並暫停 → 播放器大時碼 與 時間軸播放點正下方刻度的時碼**完全相同**。
- [ ] **逐格精度**：在高時碼處（如 01:20:00 之後）按 `→` 一次只前進**一格**、`←` 只後退一格。
- [ ] **刻度一致**：時間軸放大到「格」層級時，播放點所在刻度標籤 與 播放器時碼一致；字幕列表 In/Out 也同格。
- [ ] **mpv 沉降（Windows）**：以 mpv 路徑開檔，seek 後暫停反覆數次 → 播放器時碼不會偶爾多/少一格。
- [ ] **mpv 原生高速倒帶（Windows）**：以單一、未修剪、零位移的 MXF／AVI 在中段連按 `J`，畫面與 `Media.displayTime()` 應連續倒退，不能建立 30fps absolute seek 迴圈；按 `K` 後時間停穩、方向恢復 `forward`，再按 `L` 可正播。倒帶期間不得聽到正向音訊。
- [ ] **複雜時間軸倒帶 fallback**：將同素材修剪、位移或切成兩段後再按 `J`，必須回到以時間軸 `displayTime()` 驅動的逐格倒退，不能讓 mpv 原生倒播越過目前片段的 In／Out。
- [ ] **（正常現象，非 bug）** 29.97 **NDF** 在長時碼處，播放器時碼會比真實經過秒數**慢幾秒**（每小時約 3.6 秒）。要時碼≈牆鐘請改用 **29.97 (DF)**。

  監控數字必須是該範圍；音訊 plan 的尾端較長時，則應顯示實際較長的交付時長。
- [ ] 沒有完成工作時，「已完成」不得佔用獨立欄位；完成後才出現可收合的完成紀錄，展開後
  仍能開啟資料夾與清除紀錄。調整到最小視窗時，工具列與停止／重試按鈕仍須可見、可點。
- [ ] 完成一份短匯出後展開完成紀錄：應顯示實際完成的 `月日 · 時分 AM/PM`；關掉再重開
  監控視窗後，時間不得變成重新開窗的現在時間。
- [ ] 將並行數設為 2 或 3，對同一個輸出路徑連續送出兩份工作：第二份必須立刻回報
  「同一個輸出檔案已在匯出佇列中」，磁碟上只能有一支 ffmpeg 寫該檔。
- [ ] 執行一份時間足夠長的匯出，確認輸出檔與
  `<userData>/export-queue/output-leases/*.lock/owner.json` 已建立後，用工作管理員強制結束
  Electron 主程序；舊 ffmpeg 必須停止。以同一個 `user-data-dir` 重啟後，半成品與 lease
  必須消失，原工作應還原成暫停中的 `queued`，不可自動續跑。
- [ ] 從監控視窗按「停止」：狀態先進入 `stopping`，必須等 ffmpeg 真正關閉才刪半成品；
  清理完成後 lease 消失，之後才可再送出相同路徑。
- [ ] 用安裝版重做一份短 MP4 或 WAV 匯出，確認
  `app.asar.unpacked/electron/export-watchdog.js` 能啟動、工作完成後成品保留且 lease 清空。

### 4.15 轉檔中關閉程式與完成紀錄（v5.7.0）

這一節守的是「按下關閉＝放棄幾個小時的轉檔」這種安靜的資料損失。`prepareForShutdown()`
會停掉執行中的 ffmpeg 並清半成品，所以任何會結束程式的路徑都必須先擋下來。

- [ ] 送出一份時間夠長的匯出並讓它進入「執行中」，然後**關閉主視窗**：程式不可結束，
  必須自動叫出匯出佇列監控視窗、主視窗收起，ffmpeg 繼續跑（工作管理員看得到程序還在、
  監控視窗的進度持續前進）。
- [ ] 承上，此時**關閉監控視窗**：必須跳出確認對話框（「繼續轉檔」／「中斷並關閉」）。
  選「繼續轉檔」或按 `Esc` → 視窗留著、轉檔不受影響；選「中斷並關閉」→ 程式結束、
  半成品被清掉。
- [ ] 主視窗**還開著**時關閉監控視窗：不可跳確認（只是收起監控畫面，轉檔照跑）。
- [ ] 沒有任何工作在轉檔時關閉主視窗：維持原本的正常關閉流程，不可硬生出監控視窗。
- [ ] 完成一份匯出後**關閉程式並重開**：完成紀錄必須還在（顯示原本的完成時間與花費），
  且**不可**被當成等待中的工作重跑。按「清除完成」後再重開，紀錄必須真的消失
  （代表磁碟上的 `history.json` 也被清掉，不是只清畫面）。

### 4.16 Apple Silicon unsigned 測試版驗收

這一節必須在實體 M 系列 Mac 執行；Windows 的 lint/test/build 不能替代。先用乾淨 clone，
或確認複製來的專案已移除舊 `node_modules`、`dist`、`release`，再跑 §2 的
`npm ci` 與 `npm run dist:mac:test`。

- [ ] 終端機先通過 ffmpeg 能力探針與原生檔核對，最後同時產生 arm64 DMG、ZIP 及
  `release/mac-arm64/SUB Tool.app`；不能只有「有檔案」而未檢查前面的探針輸出。
- [ ] 執行下列命令，App 主程式與封裝內 ffmpeg 都必須顯示 `arm64`，且封裝內工具可回傳版本：

  ```bash
  file "release/mac-arm64/SUB Tool.app/Contents/MacOS/SUB Tool"
  file "release/mac-arm64/SUB Tool.app/Contents/Resources/app.asar.unpacked/electron/ffmpeg/darwin-arm64/ffmpeg"
  file "release/mac-arm64/SUB Tool.app/Contents/Resources/app.asar.unpacked/electron/ffmpeg/darwin-arm64/ffprobe"
  "release/mac-arm64/SUB Tool.app/Contents/Resources/app.asar.unpacked/electron/ffmpeg/darwin-arm64/ffmpeg" -version
  "release/mac-arm64/SUB Tool.app/Contents/Resources/app.asar.unpacked/electron/ffmpeg/darwin-arm64/ffprobe" -version
  ```

- [ ] 掛載 DMG、把 App 拖入 `/Applications` 後從該位置啟動；若 unsigned 測試版被擋，

  必須等於 `package.json`，不能只驗 `release/mac-arm64` 的 unpacked App。
- [ ] DevTools 執行 `await window.subtool.status()`：`platform === "darwin"`、
  `arch === "arm64"`、`ffmpeg/ffprobe === true`；`ffmpegPath` 必須指向 App 內建工具，
  `venc` 應為 `h264_videotoolbox` 或有證據的 `libx264` fallback。
- [ ] DevTools 執行 `await window.subtool.mpv.detect()`：必須回傳
  `{ supported:false, available:false }`。這是第一版刻意限制，不可誤啟動 Windows HWND／
  named-pipe 路徑；MXF 與多音軌應自動走 ffmpeg ingest，而不是停在「找不到 mpv」。
- [ ] 以 Electron 預設 1480×920 外框（renderer 約 1470×892）及 1024px 最小寬度檢查版面：

- [ ] 載入原生 H.264 MP4 與真實 44GB 多音軌 MXF：畫面、聲道數、聲道 7/8、seek、逐格、

- [ ] 載入真實 `5.1 FM + 2.0 FM` MP4（可使用約 6GB 的實際母檔）：必須依 stream 順序顯示

  內容都對應原始聲道。macOS 與 Windows 的聲道數、順序、標籤及行為必須相同，不可降混成 Stereo。
- [ ] 字幕在播放器上可直接拖曳、旋轉，選取時仍有「虛線框框和上面的點點」；把字級設為

- [ ] 各完成一份 MP4 H.264、ProRes 422 HQ 與 WAV 交付；用 ffprobe 檢查影片 codec、解析度、

## 5. 出問題怎麼回報

- **DevTools console** = renderer（前端）錯誤
- **終端機 2（Electron）** = main 行程 / ffmpeg 錯誤
- 把紅字訊息貼出來即可

### 預期效能

- **第一次**開檔會等單次轉碼完成（GPU 下 MXF 約 4–5 分、MOV 約 7–12 分，主要受讀取大檔的硬碟 I/O 限制）。
- **第二次以後**同一支片由快取秒開。

### 設計上的取捨（已知、非 bug）

- 採「單次讀取 + 進度條 + 快取」，**沒有**做「轉檔途中即可編輯」（那需要 HLS 串流，會造成時間軸累積漂移 5.9–7.4 秒，對逐格字幕是大忌）。
- 單一音訊素材一次只顯示 MIX 或一條指定來源聲道的波形；這是顯示選擇，不改變專案路由或輸出。
- 聲道分組（5.1 / 2.0）無法從中繼資料可靠判斷（`channel_layout` 常為 unknown），故一律逐聲道攤開。

## 6. 目錄結構與命名

| 位置 | 唯一職責 | 命名 |
|---|---|---|
| 根目錄 | 入口、套件／建置設定、共用規則、三支人類可雙擊的啟動器 | 不放實驗檔、暫存 patch 或一次性測試頁 |
| `src/` | renderer 的 ES 模組；大型實作依領域進 `actions/`、`decode/`、`loaders/`、`painters/`、`ui/` | 程式檔一律 `kebab-case.js` |
| `electron/` | 主行程、preload、原生工具 adapters 與獨立視窗 | 程式檔一律 `kebab-case.js`；視窗與 preload 同前綴 |
| `shared/` | renderer／主行程共用且零相依的 CommonJS 領域規則 | `kebab-case.cjs`；先讀 `shared/README.md` |
| `tests/` | Vitest 行為、契約、整合與 repository hygiene 測試 | `lowerCamelCase.test.js`；測試素材進 `tests/fixtures/` |
| `scripts/acceptance/` | CDP、真機接線與獨立視窗版面驗收 | Node 工具放本層；頁面載荷放 `in-page/` |
| `scripts/diagnostics/` | 效能、SMB、mpv、輸入與對話框的人工診斷 | `kebab-case.js`，檔頭寫可直接複製的用法 |
| `scripts/release/` | 原生二進位準備、封裝前檢查與正式安裝驗證 | 只由 `package.json` 發版 scripts 或對應測試呼叫 |
| `docs/` | 依 `AGENTS.md` §3 的唯一文件職責分流 | 使用既有中文文件名；ADR 用四位數編號 + `kebab-case` 標題 |
| `font/<顯示名>/` | 自備字型來源 | 子資料夾名刻意是 UI 顯示名，不套程式檔命名規則 |

`dist/`、`node_modules/`、`electron/ffmpeg/`、`electron/mpv/` 與 `release/` 的 builder 中間產物
（例如 `win-unpacked/`、`.blockmap`、`latest.yml`）都是可重建或本機準備的忽略內容，不是來源碼。
已完成正式驗收的 `release/SUB Tool Setup X.Y.Z.exe` 可暫留作交付證據；其餘由 `npm run dist` 重建。
一次性實驗請放系統暫存目錄；若結果值得保留，改寫成 `tests/` 的行為測試，不要把
`scratch/`、`scratch_*.py`、`test_*.html` 放進版控。

`src/logo.png` 與 `electron/logo.png` 內容相同但屬於兩個封裝 adapter：前者由 Vite 匯入，後者由
Electron 主行程與 electron-builder 以檔案路徑讀取。這是刻意的 runtime-local 副本，不要只因 hash
相同就刪掉其中一份。

音訊功能的資料邊界：`media.js` 保存素材與其時間軸 placement；`audio-routing.js` 保存專案 bus
與來源→bus 對應；`electron/main.js` 只依已編譯的 audio plan 執行 ffmpeg 匯出。
**不要把素材聲道順序當成輸出聲道順序。** 播放用逐聲道 `.m4a` 與影片 Proxy 只可用於預覽／波形；
匯出 plan 的 `file` 必須是母素材，主程序也會拒絕快取路徑。

## 9. 常見陷阱（改之前先知道）

- **Electron 停用了 `window.prompt()`**——用會靜默失敗（使用者按了「沒反應」）。要輸入請用
  `ui.js` 的 `promptModal()`。
- **`file://` 的 `@font-face { src:url(...) }` 會被 Chromium 擋**（"A network error occurred"），
  即使關掉 webSecurity 也一樣 → 字型必須用 **FontFace API + ArrayBuffer** 註冊。
- **mpv 是 OS 層的 always-on-top 視窗**，蓋在所有 HTML 之上 → 任何 HTML 疊層（字幕拖曳層、
  安全框）在 mpv 模式下都看不到也點不到，必須先讓 mpv 讓位。
- **預設值只准存在於 `STYLE_DEFAULTS`**：`newTrack()` 必須維持稀疏物件；專案存檔則用
  `trackStyleSnapshot()` 固化當下外觀。字級預設值曾同時寫在兩處，改一個忘了另一個。
- CSS 的**作者規則會蓋過 UA 樣式表的 `[hidden]`**——要用 `el.hidden` 藏一個有 `display:` 的
  元素，得自己補 `.那個class[hidden]{display:none}`。
- **「同一列」不要用盒頂座標比**——不同高度的元素垂直置中後盒頂本來就不同（分隔線 15px vs
  下拉 23px 差 4px）。比**垂直中心**，或量整行高度確認沒換行。
