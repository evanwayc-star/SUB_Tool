# SUB Tool — 技術架構說明

> **新進工程師請先讀 §0「鐵律」**——那些是違反後會【靜默】壞掉的不變量（畫面看起來正常、
> 匯出卻是錯的），本專案絕大多數的 bug 都出在那幾條上。

## 0. 鐵律（Invariants）

> 這一節不是風格建議，是**血淚**。每一條後面都附了「違反時實際發生過什麼」。

### 0.1 三路一致：預覽 ＝ mpv ＝ 匯出燒錄

字幕有三條渲染路徑，**必須長得一樣**：

| 路徑 | 實作 | 進入點 |
|------|------|--------|
| HTML 預覽 | `#videoSub` 疊層 | `video-renderer.js renderVideoSub()` |
| mpv（MXF 等非原生格式） | libass | `video-renderer.js refreshMpvSubs()` → `subSet(toASSFromState())` |
| 匯出燒錄 | ffmpeg `ass` 濾鏡 | `ffmpeg-export.js toASSFromState()` → Electron 匯出佇列 |

**三路都只准吃 `substyle.js effStyle()` 的結果。** 新增任何樣式欄位，必須同時接
`styleToCss()`（HTML）與 `styleToAssStyleLine()`／`cueAssTags()`（ASS）。

> 違反案例：v4.23 加直書時只做了 HTML 的 `writing-mode`，ASS 端留著「整段逐字疊成一柱」的
> 第一版 → 預覽 3 列、匯出 1 列 27 字衝出畫面（v4.29.3 才修）。

**這條鐵律靠三支契約測試守著**（v5.9.0 補齊）。它們的共同形狀是：
同一份規格必須被渲染成兩種不同的表達，無法合併成一份實作，
於是用**矩陣窮舉比對兩邊**，任一邊被改動而另一邊沒跟上就紅。

| 契約測試 | 守的是 | 兩邊 |
|---|---|---|
| `imageGeomContract.test.js` | 片段疊層幾何 | `shared/image-geometry.cjs` 的唯一公式 ↔ renderer／主程序 consumers |
| `subtitleStyleContract.test.js` | 字幕樣式 | `substyle.js styleToCss()` ↔ `styleToAssStyleLine()` |
| `clipFadeContract.test.js` | 片段淡入淡出 | `shared/clip-fade.cjs` 的唯一視窗規則 ↔ renderer／ffmpeg consumers |
| `channelLayoutContract.test.js` | 來源聲道展開順序 | `src/channel-layout.js` ↔ `electron/channel-layout.js` |
| `exportPathSafety.test.js` | 匯出檔名淨化與路徑圍堵 | `src/export-name-safety.js` ↔ `electron/export-name-safety.js` |

> **契約測試必須執行到真的那一份實作。** v5.10.0 之前，`exportPathSafety` 是在測試檔裡
> **自己宣告一份 `sanitize()` 副本**、再用正規表示式掃 `app.js` 的原始碼字面——
> 把字元類別改寬鬆但保持敘述形狀，兩道防線都不會紅。那正是 `docs/開發與驗證.md` §3
> 第三例記過的反模式，只是這次發生在安全規則上。現在兩側都是可 import 的模組。

> **樣式那一支是 v5.9.0 才有的**，而它守的正是本節在講的東西。
> 在那之前，幾何側有守衛、樣式側只靠自律——`styleToCss()` 被 **0 支測試**碰到。
> 補上之後立刻用突變測試確認有牙齒：把字級係數 0.75 改成 1、把 ASS 旋轉角的負號拿掉、
> 讓 CSS 外框不再乘 2、直書時不把 ASS `Spacing` 歸零，四種改法都會讓它紅。

### 0.2 縮放基準是「畫面高 ÷ PlayResY」，不是寬

ASS 的 **Fontsize／Outline／Shadow 全部相對 `PlayResY`**（`ScaledBorderAndShadow: yes`）。
HTML 預覽的 `ratio` 必須用 `stageH / ASS_PLAY_RES.y`。

> 違反案例：舊版用 `stageW / PlayResX`。16:9 時寬高等比例所以剛好對得上，**2.35:1 的片
> 字級大 33%**（實測佔畫面高 9.9% vs ASS 的 7.41%），而且與匯出不符。使用者回報是
> 「不同檔案格式大小不同」——其實與格式無關，是比例（v4.31.0 修）。

`ASS_PLAY_RES`（`substyle.js`）是**預覽與 `toASSFromState` 共用的唯一來源**，不可各寫一份。

**`stageH` 必須來自素材的真實尺寸**（`State.videoWidth/Height`），不可假設 16:9。
`app.js _stageRect()` 一度寫死 `vw=1920, vh=1080`，於是 2.35:1 的片預覽字級偏大約 32%、
`posY=91%` 在預覽落在黑邊上而匯出落在畫面內——與上面那個 v4.31.0 案例是同一個 bug 換個位置。
`_stageRect()` 是字幕層、安全框、圖片層與拖曳換算**共同的基準**，改它一處等於修好全部。

> **解析度無關、比例有關**（實測，內建 ffmpeg／libass，同一份 PlayRes 1920×1080 的 ASS）：
>
> | 輸出畫布 | 字塊像素 | 寬高比 |
> |---|---|---|
> | 1920×1080（16:9） | 193×55 | 3.509 |
> | 3840×2160（4K 16:9） | 387×111 | 3.486 ← 精準 2 倍 |
> | 2048×872（2.35:1） | 156×44 | 3.545 ← 未變形 |
>
> libass **依高度等比縮放**（0.807 倍 ≡ 872/1080），不會非等比拉伸。因此：
> - 4K／8K 專案不需要任何特殊處理，一切等比放大。
> - 日後若要開放**自訂匯出解析度**，只要**維持比例**就安全（4K → 1080p 全部等比跟著縮）。
> - 真正需要新規則的是**改變比例**（例如 16:9 交付成 2.35:1）：那是裁切／黑邊的決策，
>   不是縮放問題，位置的 0..1 比例語意會在該處失效。

### 0.3 ASS 的 Fontname 是「字型檔內部的家族名」，不是資料夾名

UI 顯示的是使用者自取的**資料夾名**（`font/台北黑體/`），libass／fontconfig 只認**檔案內部的
家族名**（`Taipei Sans TC Beta`）。必須經 `substyle.assFontName()` 轉換。

> 違反案例：v4.24～v4.29.2 直接把資料夾名填進 ASS → libass 配不到 → **靜默**退回微軟正黑體。
> 七個字型全中，預覽正確、匯出全錯，毫無錯誤訊息。更陰的是「標楷體」：資料夾名剛好也是系統
> 既有字型 → 不算退回、卻換成了微軟標楷體。

判斷字重要讀 **OS/2 的 `usWeightClass`**，不能看 name table 的 subfamily：CJK 字型每個字重
各自是一個「家族」、subfamily 一律寫 `Regular`（`Noto Sans CJK TC Black` 的 nameID2 也是
`Regular`）→ 分不出來（v4.31.1）。

### 0.4 filtergraph 的 Windows 路徑要跳脫【兩層】

`-filter_complex` 裡的選項值若含磁碟機冒號，字面上必須是 `C\\:/...`（兩個反斜線）。
filtergraph 先拆選項、選項值再拆一次。

> 違反案例：`fontsdir=C\:/...`（單反斜線）→ ffmpeg 把 `:` 當選項分隔符 → **整條 filterchain
> 解析失敗 → 完全無法匯出影片**。此參數只在 `font/` 存在時才加，所以 v4.27.0 把字型打進安裝包
> 之後，安裝版的匯出才開始壞（v4.31.2 修）。
>
> **這個坑騙過人**：手動在 shell 跑 ffmpeg 也會撞到同一個錯，很容易誤判成「PowerShell／MSYS
> 吃掉跳脫字元」。用 `spawn`（無 shell 介入）重測才能確認是程式的問題。

### 0.5 時間域：對外一律「時間軸時間」，播放器內部一律「來源時間」

`source = timeline - clip.offset + clip.in`。轉換**只准**發生在 `sequence.js` / `media.js` 的序列層。
`Media.displayTime()` 與 `Media.tlTime()` 是時間軸時間；`Media.vTime()`、`video.currentTime`、
mpv `time-pos` 只供播放器／音訊同步內部使用。`Media.seek()`、`Media.scrubAudio()` 的輸入也是
時間軸時間。JKL 倒播、備註、FPS 重繪、原生 `seeked` 等 UI 入口不可讀來源時間。

播放目標與呈現位置是兩個狀態：`Media.requestPresentation()` 接受時間軸目標，但在 HTML video
畫格回呼、mpv 同一請求的 per-frame `time-pos`／`playback-restart`，或 WebCodecs 所有可見圖層完成繪製前，
不得先把該目標寫成 `Media.displayTime()`。播放器回報來源時間後，也只准在 `media.js` 邊界轉回
時間軸時間。完整取捨見 [ADR-0003](adr/0003-倒帶以實際呈現畫格節流.md)。
`media-presentation-core.js` 的 presentation session 是這段工作的單一 owner：in-flight／latest-wins、
WebCodecs takeover、合成畫格 waiter、取消與 reset 都在同一個 lifecycle；`Media` 只提供序列時間映射
與目前播放器 adapter，不可再平行保存 waiter Map 或 takeover 旗標。

mpv live ASS 同樣遵守「邊界才轉換」：先以 `Media.displayTime()` 在原始 `State.cues` 的時間軸
篩選視窗，再由 `Seq.timedRangesForSource()` 映射成目前 clip 的來源時間。若先轉換再用時間軸
播放頭篩選，帶 offset/in 的片段會把本來就在附近的字幕錯誤排除。

### 0.6 「有產出」不等於「對」

驗證必須看**內容**，不是看有沒有報錯：
- 匯出 → 抽格出來看字幕真的燒進去、字型真的是選的那個。
- 字型 → 讀 libass 的 `fontselect:` 判定（**退回旗標 1 ＝ 沒配到**），不能只看有沒有 crash。
- 直書／座標 → 把 ASS 燒成 PNG，與預覽的 DOM 量測逐項比對。

> 反例：v4.27／v4.29.3 兩次「修好字型」都只驗了 libass 配對，從沒跑過應用程式自己的匯出 →
> 匯出其實整個是壞的，過了四個版本才被使用者發現。
>
> 另一個反例：拿「有／無 fontsdir 兩張圖比對」判斷字型有沒有生效——但那台機器七個字型全都
> 已安裝，兩邊都找得到、圖當然一樣，測了等於沒測。

### 0.8 音訊素材、專案 bus 與匯出聲道不可混為一談

每個影音／音訊素材保有自己的來源聲道與時間軸 placement；`audio-routing.js` 再把來源聲道映射到**專案輸出 bus**。混音器、影片輸出與 WAV 輸出都必須讀同一份編譯後的 audio plan，不能直接把某個素材的 Web Audio track 順序當輸出順序。

解除影音後產生的音訊必須有自己的 `AudioElement` 群組與 placement，不能和影片容器共用 seek 位置。MXF／部分 MOV 不可直接交給 Chromium `<audio>`，應使用 ffmpeg 已抽取的逐聲道快取；`preferCache` 必須寫入專案，以便重開後仍走同一條可靠路徑。

**預覽快取與交付輸入必須分離**：逐聲道 `chN.m4a` 與 `proxy.mp4` 只用於播放／波形；匯出時 renderer 只把母素材路徑與 `sourceStream/sourceChannel` 交給 main process。main process 在跳出存檔對話框前會拒絕任何 cache 路徑，並能重用已開啟的母素材視訊 input 讀取其音訊，避免為相同 MXF/MOV 再讀一次。MP4 因混音與聲道編組必須重新編 AAC（Mono 192k／Stereo 320k／5.1 640k），完成後以 ffprobe 回報檔案實測 bitrate；ProRes 與 WAV 則使用 24-bit PCM。

### 0.9 靜態圖片也是時間軸片段，不是播放器的一格畫面

圖片 clip 必須保留 `type: 'image'`、`in / out / offset / vtrack` 與自身的 `scale / posX / posY`，並在**預覽、專案儲存、Undo／Redo 與匯出**各路徑都完整傳遞。匯出主程序看到 `type: 'image'` 才能對 ffmpeg 輸入加 `-loop 1`；若只傳圖片路徑，它只會解一格，畫面看似「輸出只剩開頭第一格」。

> **v5.8.0：影片段也有自己的 `scale / posX / posY`，與圖片走同一條公式。**
> 在此之前影片沒有逐片段幾何——匯出是 `scale=SW:SH:force_original_aspect_ratio=decrease`
> ＋ `pad` 置中，預覽則是「素材直接 contain 進畫布再乘軌 scale」。兩者少了**軌影格**
> 那一層，素材比例＝專案比例時剛好一致，所以長期沒被發現；素材比例不同且該軌是 PiP
> 或非置中時，**預覽與匯出實測差 120px**（4:3 素材、軌 scale=0.5、posX=1）。
>
> 正確的模型是兩層，順序不可顛倒：
> 1. **軌影格**＝軌 `scale` 決定大小、`posX/posY` 以**可用空間比例**定位（`(W-w)*px`）
> 2. **片段方框**＝`scale` × 軌影格，素材 contain 進方框，方框以**中心**對到 `(posX,posY)`
>
> 三路都必須用 `image-geometry.js` 的 `trackFrame()` / `imageBox()` / `imageBoxOnStage()`，
> 不可各自手刻。另外**預覽要把片段裁進軌影格**——匯出是把片段疊在軌影格大小的透明底上
> 再疊到畫布，超出的部分本來就會被切掉；預覽不裁就會溢出（實測差 24px 寬、54px 高）。

mpv 是 OS 層原生子視窗，主視窗 DOM 不能直接放到它上面。需要顯示圖片框、控制點或監看時間碼時，使用**透明 guide BrowserWindow**；`electron/mpv-host.js` 擁有該視窗與 mpv process／pipe 的生命週期。

- **guide 視窗刻意【永久穿透】；`#imageLayer` 是唯一的互動 state machine。** guide 固定呼叫 `setIgnoreMouseEvents(true, { forward: true })`，主 renderer 的 `#imageLayer` 則無條件建立（不看有沒有 mpv）。圖片的選取、拖曳、縮放、history 與字幕命中都只在這一條 DOM 路徑處理。
- `mpv:setImageGuide` 只傳 `{ html, rect }` 供 guide 在原生畫面上繪製；guide **沒有** preload pointer API、`enter/leave` 事件或回送 IPC。OS 視窗無法只讓其中一塊 DOM 點穿透，任何「游標進圖片才讓 guide 接管」的設計都會和 `#imageLayer` 爭奪同一個 gesture，並讓字幕／右鍵選單靜默失效。

這是單一互動責任的約束：HTML overlay 的外觀可在兩個視窗各畫一次，但資料改動只能由主 renderer 的 DOM 操作產生。若將來需要 native hit testing，必須先替換整個 DOM 路徑並做 Windows 真機拖曳驗收，不可新增平行 IPC 通道。

**判斷元素在畫面上看不看得見，一律用 `getComputedStyle(el).display` 或量
`getBoundingClientRect()`。** 讀 inline `style.display`、讀 `el.hidden`、讀 canvas 像素
——這三種都測不到「有沒有真的顯示在螢幕上」。

| 案例 | 當時檢查的 | 為什麼測了等於沒測 |
|------|-----------|-------------------|
| v4.33.2 預覽畫布全黑 | `getImageData` 讀得到像素；inline `style.display` 是 `''` | **隱藏的 canvas 照樣讀得到像素**；`''` 只代表沒有 inline 值，computed 其實是 `none`（`.preview-canvas` 的 CSS 基礎規則就是 `display:none`） |
| v4.34.1 編輯提示列藏不掉 | `el.hidden === true` | `.ts-line{display:flex}` 是**作者規則**，蓋過 UA 樣式表的 `[hidden]{display:none}`；屬性是 true，畫面上照樣看得到 |

推論：**要用 `el.hidden` 藏一個自己設過 `display:` 的元素，必須補一條
`.那個class[hidden]{display:none}`**，否則藏不掉。

另外「同一列」不要用盒頂座標比——不同高度的元素垂直置中後盒頂本來就不同（分隔線 15px vs
下拉 23px 差 4px）。比**垂直中心**，或量整行高度確認沒換行。

## 1. 專案概覽

本專案採 **Vite + 原生 ES 模組**（無框架），以 `vite-plugin-singlefile` 打包成**單一 HTML**
（JS/CSS 內嵌），同時支援網頁版與 Electron 桌面版。renderer 模組持續依領域拆分，並以「事件匯流排 +
單向依賴」解耦。

Electron 端由主行程接線（`electron/main.js`）負責 ffmpeg／ffprobe、檔案對話框、路徑白名單與字型掃描；Windows mpv 的 child process／pipe／原生視窗 aggregate 在 `electron/mpv-host.js`——見 `Electron_維護手冊.md`。

## 2. 核心模組索引

這裡只列需要理解邊界與不變量的核心模組，不是逐檔清冊；完整檔案集合以版控中的
`src/`、`electron/`、`shared/` 為準。小型 action、painter 與 view 不逐檔抄進文件，避免清單與
真實目錄漂移；可達性與命名由 repository tests 守住。

| 模組 | 職責 |
|------|------|
| 協調與事件 | `app.js` 只負責頂層接線；`commands.js` 將 command ID dispatch 到 `actions/` 的唯一 behavior graph；`events.js` 解耦下層；`media-view.js`、`app-ticker.js` 是專責上層 bridge。 |
| 狀態與專案 | `state.js` 是全域狀態；`project.js`／`project-load-session.js` 管存讀交易；`history.js` 管 Undo/Redo。 |
| 時間軸 | `timeline.js` 是逐一列名的 façade；renderer、layout、interaction、transport 與兩種 transaction 各有單一職責。 |
| 媒體與音訊 | `media.js` 協調播放器；`playback-sync-engine.js` 擁有 clip／gap／外部音訊 activity transition；`audio-engine.js` 擁有 AudioContext、buffer clock 與 drift correction；`loaders/media-loader.js` 與 `media-intake-session.js` 管 renderer 的 latest-wins 載入；Electron 的 `media-intake-runtime.js` 擁有快取與串流 ingest 生命週期；`project-audio.js` 是可聽性與交付音訊的唯一解讀器。 |
| 字幕與樣式 | `subtitles.js` 管列表；`sub-parse.js` 管匯入；`formats.js` 管格式；`substyle.js` 與 `video-renderer.js` 維持三路樣式一致。 |
| 語音辨識／文本匹配 | `speech-recognition-engine.js` 統一音訊前處理與 provider adapter；`transcript-alignment.js` 將固定逐行文字稿對到相對時間證據；`transcript-alignment-diagnostic.js` 以白名單建立可下載的失敗診斷；本機 Transformers.js 由 `speech-recognition-worker*.js` 隔離執行；`speech-recognition.js` 只協調設定視窗、素材讀取與字幕軌注入。 |
| 匯出 | `subio.js` 收集 UI；`delivery-job.js` 凍結專案快照；`export-job-builder.js` 產生 jobs；Electron queue 排程，`ffmpeg-execution.js` 統一 stderr／progress／log／outcome 並依工作類型選擇 watchdog 或 direct child。 |
| WebCodecs | `decode/` 依序分離 demux、sample index、decoder、preview player 與 diagnostics。 |
| 共用規則 | 跨 renderer／主程序的唯一純規則放 `shared/`；兩側只保留 adapter 或不同表達。 |

### 2.0 `shared/` — 兩個行程共用的領域規則（v6.1.2）

renderer 是 ESM、主程序是 CommonJS，兩邊無法互相 import。於是三條領域規則長期
**各自維護一份手抄實作**，靠契約測試矩陣窮舉比對兩份輸出：

| 模組 | 規則 | 以前的兩份 |
|------|------|-----------|
| `shared/channel-layout.cjs` | 來源聲道展開順序、`ch_NN.m4a` 檔名 | `src/channel-layout.js` ↔ `electron/channel-layout.js` |
| `shared/image-geometry.cjs` | 片段疊層幾何 `imageBox` / `trackFrame`（§0.9） | `src/image-geometry.js` re-export 與 `electron/export-plan.js` consumer |
| `shared/clip-fade.cjs` | 片段長度下限與淡入淡出視窗 | `src/clip-fade.js` ↔ `electron/export-plan.js`（內聯三處） |

那些契約測試證明的是「兩份副本目前一致」，不是規則本身正確。一支**零相依的 `.cjs`**
兩邊都吃得下（Vite 會 bundle 進 `dist/index.html`、主程序直接 `require`），
規則因此只需要一份。契約測試保留下來，但守的東西變了：從「兩份有沒有漂掉」
變成「兩側的取用路徑有沒有接對，以及各自表達的那一層有沒有跟上」。

**限制**（違反會在其中一側爆掉，而另一側完全正常）：

- **零相依**：不可 `require` 任何東西。eslint 擋得下 `process`／`Buffer`
  （該 block 刻意不給 node globals），但擋不下 `require`——那由
  `tests/packageBuildConfig.test.js` 全面掃描守著。
- **必須是 `.cjs`**：打包 glob 是 `shared/**/*.cjs`，`.js` 會被漏掉。
- **必須進安裝檔**：主程序在啟動時就 require 它們，沒打包進去會**在任何 UI 出現之前就死**。
  `package.json` 的 win 與 mac `files` 都已加入，並由測試鎖住。

> **不是所有「看起來成對」的東西都該收進來。** `src/export-name-safety.js`
> 與 `electron/export-name-safety.js` 不是同一條規則的兩份副本——前者做**檔名淨化**、
> 後者做**路徑圍堵**（需要 `path.resolve`），是兩層不同的防線，兩邊都必須存在。
> `substyle.js` 的 `styleToCss()` ↔ `styleToAssStyleLine()` 同理：那是同一份規格的
> 兩種無法合併的表達，矩陣契約測試是正確做法。詳見 `shared/README.md`。

### 2.1 其他重要模組入口

下面幾條是最容易被誤用的能力邊界：

- `loaders/media-loader.js` 是 `Media` 的內部實作，只有 eslint 白名單內的檔案可碰 `Media._*`。

- `subimport.js` 區分自產 ASS 中繼資料與外部檔最佳努力解析，見 [ADR-0002](adr/0002-自產-ass-無損往返.md)。

### 2.1.2 `electron/export-queue.js`（v6.1.7）

每份交付各自使用一個 ffmpeg 程序，決策理由與代價見
[ADR-0001](adr/0001-每份交付各自一個-ffmpeg-程序.md)。

**匯出佇列**：排程（並行度／暫停）、持久化、重啟恢復、關機收尾。

原本住在 `main.js`，而它需要的狀態是**模組層的 `let`**——
`EXPORT_QUEUE_DIR` / `_queuePaused` / `_queueConcurrency` / `_activeQueueCount`。
於是 `main.js` 一度成為唯一持有狀態的地方，而它同時還持有媒體快取、字型掃描、
本機 HTTP 伺服器、mpv 整合⋯⋯十種互不相關的狀態。
**現在佇列自己擁有那些狀態**，外界要問就呼叫方法（`isPaused` / `concurrency` /
`jobs()`），要改就走 `setPaused` / `setConcurrency`。

留在 `main.js` 的是另外兩項職責，由 `onChanged` 與 `runJob` 注入：
佇列監控**視窗**的生命週期（`BrowserWindow`、關閉確認）與 `_runJobLogic`
（spawn／log 檔／進度回報）。

工作狀態與排序／重試／取消／交付更新等 mutation 也都由 queue 的公開方法完成：先做合法狀態
轉移與持久化，成功後才送新快照、通知監控視窗並排程下一份工作。一般 mutation 寫失敗會回滾
in-memory job；`done`／`failed`／`stopped` 則先寫 `.queue-terminal-outcomes` 終態意圖 journal，
清除工作則先寫 `.queue-pending-deletes`，兩者 durable commit 成功後才可對外通知。重啟時 journal 與
工作 JSON 會在進入 State 前共同對帳；journal 無法讀取時佇列 fail closed，不會把可能已完成或已刪除的工作重新排程。
其中 `failed`／`stopped` 的 outcome 是可重試紀錄：它保留 frozen payload、ASS 參照與錯誤，重啟後
回到同一個非排程 collection。重試先原子寫入遞增 attempt 的 queued snapshot，舊 outcome 清理失敗時
恢復邏輯讓較新 attempt 勝出，避免 tombstone 吃掉新工作。
關機收尾會等待 queue runner（不只 watchdog child）寫完 log 並回報終態；若 outcome journal 仍不可寫，queue
會拒絕退出，而不是把可能已交付的工作改寫成 queued。被中斷工作改回 queued 的 snapshot 同樣必須 durable，
否則也拒絕退出；runner 收尾逾時亦會取消退出，待其真正結束後再以原子 snapshot 收斂。
使用者先要求停止的工作則保留 `stopped` outcome，即使之後立即關閉程式也不可改成 queued。
`main.js` 不再直接碰 queue state 或 active process map。

> 先前排程行為只能靠 `electronQueueLifecycle.test.js` ——它會真的啟動 Electron，
> 慢、會 flaky，而且 payload 從未走過字幕燒錄／多聲道／ProRes／WAV 任何一條分支。
> 抽出後併發、暫停、失敗分類、完成收尾、關機落回 queued、恢復時的暫停判斷
> 與持久化失敗時的回滾，都能直接測（`tests/exportQueue.test.js`、
> `tests/exportQueueTransaction.test.js`）。

後續再把 ffmpeg execution 抽到 `ffmpeg-execution.js`，把媒體快取與本機 HTTP 串流 registry
抽到 `media-intake-runtime.js`。`main.js` 只建立兩者並接上 Electron／FileAuthority／queue；
仍留在 `main.js` 的是字型 sfnt 解析與這些模組的頂層組裝。

### 2.1.3 `electron/mpv-host.js`

**Windows 原生 mpv aggregate**：一個 child process、named pipe、嵌入 HWND 的透明宿主視窗，以及只畫 overlay 的透明 guide 視窗。這些資源必須作為同一個生命週期建立、替換與釋放；若 `main.js` 各自保留 process／socket／window 的 module-level `let`，換檔或關窗時就會留下晚到 pipe callback 指向已銷毀視窗的風險。

`main.js` 只保留 FileAuthority、平台閘門與 IPC adapter；host 透過注入的 `BrowserWindow`／spawn／named pipe／主視窗 getter 工作。這不是為尚未驗證的 macOS 嵌入建立假 adapter：`mpvEmbeddingSupported()` 仍在非 Windows fail closed。`tests/mpvHost.test.js` 用假 native runtime 守 launch、換媒體、pipe 回覆、宿主／guide bounds 與 quit cleanup。

### 2.1.4 `electron/ffmpeg-execution.js`

**ffmpeg execution 的唯一 owner**：解析 stderr、回報進度、寫入 queue log、分析錯誤並收斂
成功／失敗 outcome。交付工作使用 `export-watchdog.js`，可重建的 proxy／ingest 使用 main
直接 child；呼叫端只傳工作語意與生命週期 callback，不再各自重建 parser／log／錯誤協定。

### 2.1.5 `electron/media-intake-runtime.js`

**原生媒體 intake aggregate**：快取 identity／metadata／清理、fragmented-MP4 HTTP Range
registry，以及 batch／stream ingest 的 commit／cancel 生命週期由同一個 runtime 持有。
`media-ingest-coordinator.js` 決定 replace／enqueue 順序，FileAuthority 決定可讀與可清理能力，
`main.js` 的 IPC handler 只把 session 與參數交給 runtime。

`State` 物件包含所有可變資料：

```js

  tracks: [],        // [{name, visible, locked, ...可選的 STYLE_DEFAULTS 欄位}]

  activeEdge: 'start',// 上下鍵步進中停在 start 或 end
  pxPerSec: 80,      // 時間軸縮放（每秒像素數）
  viewStart: 0,      // 時間軸左緣對應秒數
  exportIn: null,    // 輸出範圍 In（時間軸秒數，可 Undo/Redo）
  exportOut: null,   // 輸出範圍 Out（時間軸秒數，可 Undo/Redo）
  inPoint: null,     // I 按下但尚未 O 的暫存起點

  videoTracks: [],   // 視訊軌：visible / locked；圖片可獨立放在最上層
  externalAudioState: [], // 可重建的外部／解除音訊 placement（不含 runtime Audio）

```

`exportIn/exportOut` 是專案時間軸狀態，不是只有播放器控制元件的暫存值；因此它們進入
`history.js` 快照、`.subtool` 儲存資料與匯出範圍。反之，`timecodeWatermark` 是使用者的
監看偏好，只由桌面版 `config/settings.json`（網頁版為 localStorage）保存；是否把 TC 燒進影片是每一次匯出對話框的選項，兩者不可混用。

圖片幾何也屬於**每個 clip**，不是整條視訊軌的全域屬性：`{type:'image', scale, posX, posY,
in, out, offset, vtrack}`。這個區分讓同一軌的兩張圖片可以有不同大小與位置，並確保
History、Project 與 export filtergraph 使用同一份資料。

**工具函式**：
- `newTrack(name)` — 建立軌道物件
- `setFps(v)` — 設定影格率（同步更新 UI 下拉選單與時碼顯示）
- `snapFps(v)` — 將任意 fps 值對齊到允許集合（23.976/24/25/29.97/30）
- `ensureTrackCount(n)` — 確保至少有 n 條軌道（新專案/init 用）
- `DESK` — Electron `window.subtool` 橋接物件（`null` 表示瀏覽器模式）
- `IS_DESKTOP` — 布林，是否為 Electron 模式

### 桌面／網頁分支：哪些是真接縫，哪些不是

`DESK` / `IS_DESKTOP` 的分支散在很多地方，但**不是每一處都值得抽成 adapter**。判準是
「有幾種實作」：

- **設定儲存是真接縫**（桌面 IPC vs 網頁 localStorage 是兩種實作）→ 已抽到
  `settings-store.js`。`makeSettingsStore(desk, storage)` 兩者皆可注入，所以能在
  vitest 用假 adapter 測，不必跑 Electron。以前 `loadConfig` 把欄位映射寫了兩份
  （桌面一份、網頁一份），改一個欄位漏改一處就會「桌面存得到、網頁存不到」。
- **mpv / ingest / probe / exportVideo 不是接縫**：它們**只有桌面一種實作**，
  網頁版根本沒有對應行為。為只有一種實作的東西建 adapter 是投機的抽象——
  那些分支就讓它們是 `if (IS_DESKTOP)`，不要包裝。

新增設定種類：在 `settings-store.js` 的 `SETTINGS_SLOTS` 加一列
（邏輯名 → `deskLoad` / `deskSave` 方法名 + `localStorage` 鍵），不要再手寫分支。

### `formats.js`（字幕格式解析/序列化）

`SubFormats` 物件包含四種格式的解析器與序列化器：

| 格式 | 解析 | 序列化 |
|------|------|--------|
| SRT | `parseSRT(text)` | `toSRT(cues)` |
| ASS | `parseASS(text)` | `toASS(cues, fps, tracks, ...)` |
| Adobe Encore | `parseEncore(text, fps, df)` | `toEncore(cues, fps, df)` |
| 純文字 | `parseTXT(text)` | `toTXT(cues)` |

四個 parser 共用 `decodeLegacyLineBreaks()`：URI token（例如 `https://host/a//b`、
`file:///C:/media//clip`）內的雙斜線必須原樣保留；只有 URI 外的 `//` 與兩個反斜線
才沿用舊版「人工換行」語意。`subio.js` 不可在 parse 後再做第二次裸字串取代。

ASS Dialogue 文字由 scanner 解碼，不可用 `\{[^}]*\}` 之類的 regex：未跳脫 `{...}` 是
override tag，應移除；`\{`／`\}` 是可見的字面括號；`\N`／`\n`／`\h` 是 ASS 控制碼。
`assEscapeText()` 插入的零寬切斷標記則代表使用者真的輸入了這些字面序列，round-trip 時要
移除標記並還原文字，不可誤當控制碼。

**ASS 輸出細節**：
- 每個字幕軌道對應一個 `Style: Track{N}` 樣式
- `WrapStyle: 2` 關閉 libass 自動折行；手動換行仍以 `\N` 保留
- 字級一律取 `effStyle()` 的 `fontSize`，再以固定 `PlayResY=1080` 為縮放基準；不可改用影像寬度
- 位置一律取 `effStyle()` 的 `posX/posY`，輸出為 `\pos(x,y)`；`posPct` 只保留給舊專案遷移

### `media.js`（媒體引擎、外部音訊素材與解除影音）

`Media.loadDesktopMedia()` 與瀏覽器的 `loadVideoFile()` 都由 `MediaIntakeSession` 配發 ownership token。`stat`、
`probe`、mpv detect/launch、`ingest`、file URL、metadata 與波形解碼的每個 await 邊界都要先確認
token；使用者在 A 尚未完成時載入 B，A 的晚到結果只能被丟棄，不能再寫入 `video.src`、
`State.clips` 或 Web Audio tracks。mpv 的 launch／quit 另外走同一條 exclusive system-effect lane：
舊 launch 完成後先關閉其 native runtime，才允許新 launch 進主程序，避免兩個 IPC handler
交錯改寫同一個 mpv process/window。五條逐聲道載入路徑共用
`materializeAudioElements()`，失去 ownership 時會清空已建立元素的 `src`，停止背景緩衝。

瀏覽器的 ffmpeg.wasm 只有一個 worker、logger 與虛擬檔案系統，所以 `Media.runWebFfmpeg()` 是
ffprobe、母素材轉檔與抽音軌的唯一 serial lane（影片交付不支援 web）。資源 loader 本身不回寫 intake UI；只有在
await 後仍持有 token 的呼叫端才可顯示「就緒／失敗」，避免 A 的下載結果覆寫 B 的狀態。
另外，外部音訊、圖片、影片段與 Wave registry 使用 `ResetEpoch`：它不會讓同一專案的兩次素材加入
互相取消，但 reset／換專案後，舊世代不得再寫 `State`、Web Audio track、波形或共享播放器。

專案音訊的可聽性不在 `media.js` 與 `delivery-job.js` 各算一次。`project-audio.js` 以純資料
`ProjectAudioInterpretation` 同時回答：來源聲道的全專案 Solo/Mute、外部 placement gain、
bus/route 有效增益、電平表應讀哪些聲道及其完整 gain，以及交付 audioPlan。runtime 控制軌
一建立，Solo／Mute／volume 就生效；逐聲道 m4a 只負責播放，不能成為控制狀態的存在條件。
交付 input 永遠是母素材 path + `sourceStream/sourceChannel`。Solo 是全專案狀態，不能按每支
母素材各自判斷，否則 A 的 Solo 會讓 B 在預覽靜音、交付卻仍出聲。

#### Media 物件

管理影片播放、Web Audio 多軌混音、ffmpeg 整合。

**音軌種類**（`track.kind`）：

| kind | 說明 |
|------|------|
| `native` | 原生影片立體聲 L/R（`_connectStereo()` 分頻） |
| `element` | `<audio>` 元素（外部音檔或抽取聲道） |
| `buffer` | AudioBuffer（ffmpeg.wasm 解碼後存入記憶體） |
| `nativeTrack` | 瀏覽器原生多音軌（少數瀏覽器支援） |

**虛擬播放模式**（`video.src` 為空時）：
- 以 `performance.now()` 計時模擬播放位置
- `_vTime` + `_vStart` 維護當前時間

**seek 精準對齊**：每次 `seek(t)` 都呼叫 `snapTimeToFrame(t, fps, df)` 確保落在整格。

**空專案 seek**：`State.duration === 0` 時允許 `Math.max(0, t)` 而不 clamp 至 0，讓空專案可移動播放點先排字幕。

**靜態圖片**：圖片是 `Seq` 的視覺片段，不交給 `<video>` 或 mpv 解碼／時鐘。
`video-renderer.js renderImageOverlays()` 在播放時間落於圖片 clip 的 `offset + (in…out)` 範圍時
建立可操作的疊層；一般預覽直接以 DOM 操作，
mpv 原生預覽則由透明 guide 照同一份幾何畫出視覺，而主 DOM 保留唯一 pointer state machine。
新增第一支主影片時，`Media` 會保留
既有 image-only timeline，不能因初始化序列而清掉圖片。

#### `waveform-decoder.js` 的 Wave 物件

波形峰值資料管理。

| 方法 | 說明 |
|------|------|
| `compute(ab, chIdx)` | 從 AudioBuffer 計算 min/max 峰值桶（100 桶/秒） |
| `computeFromWav(buf)` | 直接從 WAV ArrayBuffer 解析（不需 decodeAudioData，供 Electron 快取讀取） |
| `initLive()` | 長片模式：初始化空白峰值陣列，播放時由 `captureLive()` 逐桶填入 |
| `captureLive()` | 由 `app-ticker.js` 呼叫，從 AnalyserNode 擷取即時波形 |
| `registerSources(wavePath, channels)` | 記錄多音源（主混音 + 各聲道），驅動波形來源選擇器 |
| `selectSource(idx)` | 切換顯示哪個聲道的波形（延遲解碼，含競爭條件保護） |

### `timeline.js` / `timeline-renderer.js`（時間軸）

`timeline.js` 是相容 façade，逐一列名 re-export `timeline-renderer.js`、`timeline-interaction.js`、
`clip-model.js` 與 `clip-view.js` 的公開入口。真正的時間軸繪製與 DOM 互動由 renderer 單一擁有；
不可再建立第二個 renderer。字幕／視訊軌列頭的 `visible`、
`name`、`locked`、`height` 則只准交給 `timeline-edit-transaction.js` 改動：按鈕與改名是單次
transaction，高度拖曳在 mousemove 只 preview、mouseup 才 commit 一筆 History。若 gutter
直接改 State 而不立刻 commit，下一個無關操作會把它一起吞進快照，造成一次 Undo 回復兩件事。
preview 只更新狀態並由 renderer 的 `requestAnimationFrame` 局部呈現，不發
`timeline:invalidate`；完整 `drawTimeline()` 僅在 commit／cancel 邊界執行，避免每個
mousemove 重建全部軌道與字幕 DOM。

字幕、影片與外部音訊的拖曳則各自仍由 renderer 進行預覽，但一律先以
`timeline-gesture-transaction.js` 捕捉可回復欄位。`mouseup` 才 commit；`blur` 或
`pointercancel` 一律交給 `cancelTimelineGesture()`，由同一 lifecycle 依序 restore preview、移除
copy-drag 新建物件、重算片段映射、重繪並同步 selection，且**不得**留下 History。renderer 只提供
DOM／播放 adapters；測試必須直接執行此 interface，不可再用 regex 掃接線字串。
播放時間的可測純規則則放在 `timeline-transport.js`：外部 API 一律交時間軸時間，HTML video／mpv
driver 一律交來源時間，只有 transport 注入的 sequence 映射可跨越這條邊界。

#### 座標系統

Y 軸由 `timeline-layout.js` 的純函式分層：36px 時間尺 → 可選視訊軌 → 可捲動的來源音訊 viewport
→ 字幕軌；音訊區會為字幕保留最小高度。X 軸只用 `timeline-interaction.js` 的
`timeToX()`／`xToTime()`，不得在 painter 或事件 handler 另寫換算。

#### 主要渲染函式

| 函式 | 說明 |
|------|------|
| `drawTimeline()` | 全量重繪（layout + ruler + wave + track rows + playhead） |
| `drawRuler()` | Canvas 繪製時間尺刻度與備忘三角標記 |
| `drawWave()` | Canvas 繪製波形（逐像素查峰值桶，跨桶取極值） |
| `renderTrackRows()` | DOM 重建軌道列、gutter（名稱/眼睛/鎖定/拖曳把手） |
| `renderCueBlocks()` | DOM 重建字幕區塊（含磁吸/重疊偵測） |
| `updatePlayhead()` | 僅移動播放頭位置（非全量重繪） |

#### 拖曳互動

`mousedown` → 判斷目標（字幕區塊邊緣/中心、時間尺、空白軌道）→ 設定 `drag` 狀態：
- `move`：群組移動（多選），磁吸播放點 + 其他字幕邊界，防同軌重疊
- `l`/`r`：縮放左/右邊界，同樣磁吸
- `scrub`：拖曳時間尺移動播放頭
- `rubber`：框選（矩形範圍選取）

拖曳期間優化：只更新 `.cue-block` 的 `style.left/width`，不全量重繪。`mouseup` 才呼叫 `renderAll`。

#### 字幕資料結構

```js
{
  id: 'c1',          // 唯一 id（newId() 遞增）
  start: 10.5,       // 起點秒數
  end: 13.2,         // 終點秒數
  text: '你好世界',  // 字幕文字（換行用 \n）
  track: 0,          // 軌道索引（0-based）

```

#### 主要函式

| 函式 | 說明 |
|------|------|
| `renderSubList()` | 全量重建字幕列表 DOM，包含重疊偵測、搜尋高亮、字數超限標記 |
| `renderSubRow(id)` | 單條更新（拖曳時用，避免全量重建） |
| `selectCue(id, opts)` | 選取邏輯（單選／加選／範圍選、自動切換列表軌道；非 `preventScroll` 時同步揭示並在下一個 rAF 依完成後的版面再揭示） |

| `deleteSelected()` | 刪除選取（刪後自動選相鄰條目） |

| `copyCues()` / `pasteCues()` | 複製貼上（貼上時以播放點為基準位移時碼） |

字幕列表以**事件代理**（Event Delegation）處理：click（時碼內嵌編輯）、mousedown（選取）、dblclick（文字編輯）、contextmenu（右鍵選單）、input/focusout（同步 `c.text`）。

時間軸字幕區塊的普通點擊必須保留「點擊／拖曳」生命週期：未選取的 cue 可在 `mousedown`
立即選取；已位於 selection 的 cue（包括已是單選）則先保留原狀，超過 3px 門檻就作拖曳，
直到 `mouseup` 確認沒有移動才再次呼叫 `selectCue()`。多選因此收斂為該句單選並切換
`listTrack`；已是單選時則重新揭示列表列。第一次專案儲存守衛只攔下破壞性拖曳，不得吞掉
非破壞性的選取回饋。

字幕列使用 `content-visibility:auto` 與 `contain-intrinsic-size`。跨軌重建大量列表時，同步的
`scrollIntoView()` 可能先依預估列高定位，下一幀實際列高完成後讓選中列移出 viewport；
`refreshSelectionUI()` 因此先同步揭示，再於下一個 `requestAnimationFrame` 重新查詢當前
`selectedId` 的列並揭示一次。若 selection 或後續捲動意圖已改變（例如同一句改用
`preventScroll`），延後工作必須放棄，不能執行已過期的揭示。

`subtitle-analyzer.js` 的「連續相同」報告同時保留完整的相同編號，以及「文字相同且前句 Out／
後句 In 落在同一影格」的黏接編號集合。判定使用 `getExactFps()` 的影格索引，不直接比較浮點秒數；
檢查面板只替黏接集合中的**前後兩個編號**加上深綠 class，其餘相同字幕維持橘色。

### `keyboard.js`（鍵盤 + I/O + JKL）

#### JKL 穿梭輪

```
J 鍵：-1 → -5（每按一次 -0.5）— 符合資格的 mpv 單片走原生 backward；其餘走時間軸 seek fallback
K 鍵：暫停（_jklSpeed = 0）
L 鍵：+1 → +5（每按一次 +0.5）— 正速度以 Media.setRate 加速
空白鍵：切換播放/暫停（重置 JKL 到 ×1）
```

`ReverseShuttleSession` 擁有倒帶的 start／update／stop、倍率、取消與原生倒播健康監看；
`transport-controller.js` 只把 JKL／方向鍵意圖送進 session，不持有 timer、epoch、watchdog 或
seek 佇列。所有持續倒帶都停止 Web Audio／外部音訊並讓影片靜音；按 K、空白鍵、逐格鍵或切回
正播時，session 必須暫停、恢復 `forward`／`rate=1`、取消未完成的呈現請求並還原使用者靜音。
單按一次方向鍵仍可播放 80ms scrub 音訊，不能被持續倒帶的靜音規則一起取消。

原生倒播只准在「mpv、單一非圖片片段、未修剪、`offset=0`、`in=0`、`out≈dur`、沒有 gap、
WebCodecs 未接管」全部成立時啟用。這時來源時間與時間軸時間是恆等映射。session 在**整段**
倒帶期間監看實際呈現位置是否持續下降；任何時刻停住都切到時間軸 fallback，不能只驗開始後
第一個 0.4 秒。

背景 ingest 會為 mpv 素材準備每 0.5 秒一個 keyframe 的 720p preview Proxy。Proxy 就緒後，
`Media.setPlaybackDirection('backward')` 先在同一來源時間 `loadfile` 到短 GOP Proxy，停止倒帶再於
同一時間載回母素材；字幕也在兩次切換後重新送入。Proxy 只改善預覽解碼，禁止進入 delivery。
母素材尚未有 Proxy 時仍可嘗試原生倒播；第一次畫格有 1.2 秒 GOP 暖機寬限，一旦開始出畫，
後續仍以 0.4 秒無進度判定 stall。

fallback 依 monotonic elapsed time × 倍率計算時間軸目標，再用專案精確 FPS 吸附，不得寫死
30fps。`Media Presentation Core` 同時最多處理一個呈現請求，等待期間只保留最新目標；舊中間
目標可丟棄，且只有 presenter 回報實際畫格後才提交 `displayTime()`。HTML video、mpv、
WebCodecs 的完成訊號與責任見 [ADR-0003](adr/0003-倒帶以實際呈現畫格節流.md)。

#### 主要快捷鍵（預設值；可於快捷鍵設定自訂）

比對規則（`matchAction`）：含 `code` 的綁定只比對實體鍵（`NumpadX`）；**數字鍵盤的字元鍵不會命中 `key` 綁定**——主鍵盤上排數字與數字鍵盤完全分離（`NumpadEnter`、NumLock 關閉時的方向鍵不受限）。

| 鍵 | 功能 |
|----|------|
| `I`（或 `Q`） | 設定選取字幕起點（無選取則新建） |
| `O`（或 `W`） | 設定選取字幕終點（上字幕模式下自動跳下一句） |
| `←/→` | 逐格跳（1格）；+Shift = 1秒；+Ctrl+Shift = 5秒 |
| `↑/↓`（或 `E`/`D`） | 步進邊界點（起點→終點→下句起點…） |
| `Ctrl+↑/↓` | 跳到同軌上一句/下一句並選取 |
| `Shift+↑/↓` | 跳到影片開頭/結尾 |
| `Ctrl+Shift+↑/↓` | 跳到同軌第一/最後字幕 |
| `Num 5`/`Num 2` | 跳至上一句/下一句字幕起點前 5 格（僅數字鍵盤） |
| `Num 7`/`Num 8`/`Num 9` | 開關紀錄/備註/字幕檢查面板（僅數字鍵盤） |
| `P`（或 `R`） | 多選位移：將選取字幕整體移到播放點（不裁切被重疊的鄰居） |
| `Delete` | 刪除選取 |
| `Ctrl+Z/Ctrl+Shift+Z` | Undo/Redo |
| `Ctrl+A` | 全選當前軌道 |

### `subio.js`（匯入/匯出）

`subio.js` 是字幕 I/O 與匯出對話框 façade；格式偵測與匯入交易在 `sub-parse.js`。

**格式自動辨識** (`sub-parse.js detectSubFormat`)：依副檔名優先，次以文字特徵（`[Script Info]` → ASS；`\d+ --> \d+` → SRT；時碼模式 → Encore；其餘 → TXT）。

**匯入流程**：
1. 取得文字（Web: `FileReader`；Desktop: IPC）
2. 若尚未載入影片，彈窗詢問 FPS
3. 解析字幕（含換行符號 `\\`/`//` → `\n` 轉換）
4. 彈窗選擇目標軌道（可新增軌道或附加到現有軌道）
5. `snapTimeToFrame` 對齊影格後寫入 `State.cues`

**匯出流程**：
1. 彈窗選擇格式與軌道（多軌時每軌各一個檔案）
2. 序列化 → `encodeUTF16LE` → 下載（Web）或 IPC 寫檔（Desktop）

**序列影片／WAV 匯出**（桌面版）：`subio.js` 只收集對話框選項；`delivery-job.js` 凍結經過輸出
`[In]/[Out]` 裁切後的片段、視訊軌、專案音訊路由與可見字幕，`export-job-builder.js` 再從同一份
submission 產生 queue jobs。圖片 clip 必須明確傳
`type:'image'`、`scale`、`posX`、`posY`，主程序才會將來源作為 `image2 -loop 1` 輸入，而不是只
解一格。交付用 TC 只在影片格式可選，起點由 `export-job-builder.js buildExportJobs()` 以
`secToEncore(exportIn, fps, dropFrame)` 計算；它位於
ASS 字幕之上，字型使用更紗黑體的等寬數字字型。影像與音訊輸入均為母素材，不能把預覽 Proxy／快取傳入匯出 handler；同一素材若同時輸出影像與音訊，主程序重用同一 input。WAV 是多聲道 PCM，不支援字幕或 TC。

`.subtool` 格式為 **UTF-16 LE + BOM** 的 JSON，結構：
```json
{
  "app": "SUB Tool",
  "version": 3,
  "media": { "name": "film.mp4", "path": "C:\\...", "size": 4000000000 },
  "fps": 24,
  "dropFrame": false,
  "duration": 5400.0,
  "playhead": 3610.5,
  "pxPerSec": 80,
  "trackCount": 2,
  "exportIn": 3600.0,
  "exportOut": 3720.0,
  "videoTracks": [{ "name": "視訊軌 1", "visible": true, "locked": false }],
  "videoTrackCount": 1,
  "vtracksCollapsed": false,
  "clips": [{ "type": "image", "path": "C:\\logo.png", "in": 0, "out": 10,
              "offset": 3605, "vtrack": 1, "scale": 0.25, "posX": 0.9, "posY": 0.1 }],
  "tracks": [...],
  "notes": [...],
  "cues": [{ "start": 10.5, "end": 13.2, "text": "...", "track": 1, "timed": true }],

  "externalAudioSources": [...]
}
```

- `exportIn` / `exportOut` 只有設定過才寫入（`null` 時整個鍵不出現）。
- `videoTrackCount` 是給舊版讀取用的向下相容欄位，新版一律以 `videoTracks` 陣列為準。
- `vtracksCollapsed` 保存視訊軌工作區的收合狀態；舊專案缺少此欄位時預設展開。
- `audioProject` 與 `externalAudioSources` 只存**可序列化的純資料**；
  `AudioElement`、波形與 ffmpeg 快取絕不寫入（見 §0.8）。

注意：`cues.track` 在 v2/v3 格式中為 **1-based**（載入時 -1 轉為 0-based）。v3 的 clip 會保留
圖片型別與幾何；桌面版保留來源絕對路徑以便重開，網頁版仍需使用者重新連結本機素材。未能立即
重建的圖片／外部音檔會保存在 `ProjectLoadSession` 的明確 restore plan，下一次儲存也不得遺失；
不可把暫存資料塞回 `State`。

專案開啟是 **latest-wins 的序列交易**：`ProjectLoadSession` 讓每個 `load()`／`loadDesktop()` 取得
遞增 generation，並把 `Media.reset()`、主影片載入、pending clip 與外部音訊重建排在同一條 Promise tail。
較舊請求在每個 `await` 後發現 generation 已過期就停止 finalize，下一個請求則必須等舊 runtime
完整收尾才進場，避免兩次 reset/load 交錯。找不到原影片時的按鈕 callback 也必須加入同一條 tail
並捕捉原 generation；瀏覽器檔案選擇器返回後要再檢查一次。使用者選「稍後」後，`app.js` 必須把
同一份 `{ generation, plan }` 顯式傳給下一次主媒體載入；完成 pending clips、外部音訊與播放點
還原後才呼叫 `finishMediaRelink()`。「開新專案」也必須先遞增 generation，再排入同一條 tail 清空狀態，
不可讓舊載入稍後蓋回空專案。

**自動備份**：第一次編輯前顯示「請先儲存」提示（`ensureProjectSaved`），儲存後每 3 分鐘自動備份一次。桌面版寫入專案旁的 `.subtool_AutoSave/` 子目錄；瀏覽器版改存入 `localStorage`（靜默更新，額度不足時靜默失敗）。

### `history.js`（Undo/Redo）

```js
History = {
  stack: [],    // [{label, snap}]，最多 120 步
  hi: -1,       // 目前所在位置
  snap()        // structuredClone(cues/tracks/notes/FPS/輸出範圍/clip 幾何/音訊 placement)
  record(label) // O(1) 結構比對後才 JSON 比對；相同則不記錄
  restore(i)    // 還原到第 i 步
  undo() / redo()
}
```

`recordHistory(label)` 為對外包裝函式，由各模組（timeline/subtitles/keyboard 等）在每次狀態變更後呼叫。
軌道 metadata transaction 則發出同步 `history:record`；`app.js` 在同一 call stack 內建立快照，
因此 preview 不製造歷史噪音、commit 也不會延後到下一個使用者操作。
其中 `clipGeo` 只保存可編輯的影片／圖片幾何，`externalAudioState` 只保存可重建的音訊 placement；
真正的 `AudioElement`、波形與快取不能寫入快照。還原後以事件通知 `Media` 重用或重建 runtime
音源，避免復原後畫面已變、聲音仍停留在上一個路由。專案載入的 `History.reset()` 必須等
主影片與 pending 影片／圖片全部還原完畢才建立基準；序列 Undo 則以
`media:sequenceWillRestore`／`media:sequenceRestored` 讓 Media 保存時間軸位置並重新 seek，
同時移除已不存在的 `clip:*` 音軌、為復活的桌面 clip 重建 ingest runtime，不可只還原
`State.clips`。原影片稍後才重新連結時，`media:projectReady` 只攜帶這次從專案 pending
資料真正重建的片段，並將它們 rebase 進先前尚無影片的歷史步驟；不可傳入當下完整序列，
否則等待重連期間由使用者新增的圖片會被錯誤補進更早的 Undo。因此重連不會犧牲先前已做的
字幕或圖片 Undo。

### `speech-recognition-engine.js` / `transcript-alignment.js` / `transcript-alignment-diagnostic.js` / `speech-recognition.js`（語音辨識與文本匹配）

- `transcribeAudioStream()` 是所有 provider 的單一入口；呼叫端只交 AudioBuffer、來源區間、語言與 provider 設定，不解析供應商回應。
- OpenAI Whisper-1／Groq 以 600 秒 window、10 秒 overlap 依序送出；16 kHz mono PCM16 WAV 的實際 `Blob.size` 必須低於 20,000,000 bytes。兩者固定要求 `verbose_json` 的 word + segment 時間，chunk-relative segment／word 只在引擎內加回來源區間偏移；相鄰 window 先以 overlap 中點形成不重疊 core，再比對兩邊完整 word 序列。只有正規化文字相同、時間差不超過 1.25 秒，而且該 word 在雙向都只有一個候選時才視為同一證據；同字候選不唯一時保守地不去重，避免其中一段漏辨時靜默刪掉實際連說兩次的單字。進度按實際送出秒數（含 overlap）計算，所有 await 前後仍檢查同一 AbortSignal。
- 桌面版在每個 Whisper window 送出前，才透過 `speech:compressAudio` 將**已混好的** WAV 壓為 16 kHz mono、64 kbps MP3；preload 在 structured clone 前限制 bytes 大小，`electron/speech-audio-compressor.js` 不接受 renderer 路徑，只接受小於 20 MB 且 header 精確符合 PCM16 WAV 的 bytes。每次 IPC 都有唯一 requestId；取消會讓 renderer 立即以 `AbortError` 收斂、通知 main 終止對應 ffmpeg，關閉程式也會取消並等待所有辨識壓縮。輸入／輸出均使用 app 內部暫存路徑並在成功或失敗後清除；壓縮不可用時 renderer 退回原 WAV window，網頁版也只走 WAV，不可改拿母素材第一軌繞過辨識來源選擇。
- Azure adapter 使用 GA `2025-10-15` Fast Transcription。Region 只能是 Azure identifier，主機名由程式固定組成 `https://<region>.api.cognitive.microsoft.com`，避免把 Speech Key 送往任意 URL。
- `parseAzureTranscriptionResponse()` 把 `offsetMilliseconds + durationMilliseconds` 轉為來源音檔的相對秒數，保留逐字時間、locale、speaker／channel 與 confidence；**不可**在 parser 加時間軸 offset 或逐格化。
- Azure request 固定啟用 diarization（最多 10 位講者）。`refineAzureSubtitleSegments()` 只在 Azure 提供有效 `words` 時做字幕斷句：句末標點或逐字停頓達 0.75 秒時切開，無標點長句限制為 24 個中日韓字元／14 個英文單字／6 秒；相隔不超過 0.45 秒且前句尚未結束的片段，只有在 speaker 明確存在且與 channel 都相同時才可合併。細分後的 In／Out 必須取首末 word 的時間；缺少 words／speaker 時保留原 phrase 邊界，禁止用平均分配偽造時間碼或跨講者合併。
- Azure Region 的單一預設來源是 `DEFAULT_AZURE_SPEECH_REGION`（目前 `japaneast`）。它只供全新或空白設定使用；已儲存的其他合法 Region 必須保留，否則會讓該區域綁定的 Speech Key 立即失效。
- runtime 素材讀取優先沿用 `Media.sourceChannels()` 已建立的 buffer／AudioElement／ffmpeg 逐聲道快取；`recognitionTracks` 必須依 `(sourceStream, sourceChannel)` 排序後才建立辨識來源選項。預設 `all-source-channels` 會把所有實際來源聲道等權平均成 mono（8 軌就是 8 軌平均）；明確的 `source-channels` 可選單軌，三軌以上另可選排序後最後兩軌。最後兩軌只是 UI 展開的座標組；恰好兩軌時與全部相同，不得重複顯示或推論為 Stereo／5.1，也不得讀取專案 bus、mute／solo、波形顯示或交付聲道設定。
- 同一 buffer／URL 的重複 runtime 描述在全部混音時只能計入一次；若同一多聲道 buffer 有可驗證且不重複的 `sourceChannel`，才可投影成真正不同的單軌選項。共用而不可拆的單聲道 URL 不得製造看似不同、實際 PCM 相同的選項。`preferCache` 尚未就緒時應提示等待，不可回頭把 MXF／部分 MOV 母容器交給 Chromium 解碼。來源選擇只活在本次對話框，不可寫入全域 ASR 設定或套到下一個素材。
- `speech-recognition.js` 讀取右鍵指定的真實素材，將相對時間加到素材的 timeline offset。最後且只在 `insertAsrSubtitles()` 以 `snapTimeToFrame()` 對齊專案影格；素材 `in` 已於音訊擷取時消化，不可再加一次。
- `transcript-alignment.js` 是純函式的文本匹配接縫：輸入使用者的逐行文字稿與 `transcribeAudioStream()` 回傳的相對時間證據，輸出仍是相對秒數的 `{ start, end, text }`。它不可讀寫 `State`、不可加素材 offset，也不可逐格化。
- 文本匹配的**每個非空白輸入行就是固定 cue 邊界**。文字框可直接貼上，或透過既有 `readFile()` + `decodeText()` 匯入 UTF-8／UTF-16 TXT；不得另寫一套編碼判斷。輸入階段忽略純空白行並裁掉每行首尾空白；比對正規化只可忽略繁簡、大小寫、標點及空白差異。輸出 `text` 必須使用裁切後的使用者原行，不得依標點、長度或辨識 segment 重新拆句／合句，逐行文字稿也不得寫入 localStorage。
- 比對採有界的單調 token alignment：漢字逐字、英文／數字逐詞，避免 ASR 漏字把下一行的同字提前吃掉。時間邊界優先取 exact pair；距離很遠的 substitution 不得把單句拉成數十秒，低覆蓋行的 exact pair 若分成相隔超過 8 秒的群組，只保留最密集（同數時靠後）的連續群並標示 `review`。被捨棄的 exact word 群只可回填緊鄰的漏句，不可跨可靠行任意重配；segment 內比例時間不得冒充 word timestamp。
- Azure、OpenAI／Groq 與本機 timestamped Whisper 的 `words` 首末時間是逐字證據；沒有 words 的 provider 只能在原 segment 內取得句級估算。初始結果若 coverage ≥ 90%、unmatched ≤ `floor(總行數 × 5%)`、單一連續 run ≤ 5 且沒有 ambiguous，可進入稀疏恢復：選定連續群中的部分 exact word 證據先成為 `partialEvidenceLines`；其餘零證據行依 token weight 切分前後錨點空間，以可靠行的 median seconds/token（限制在 0.18–0.8 秒/token）決定置中的短 cue，不可填滿 8–40 秒空窗。估算行必須標成 `review/interpolated`，列入 `estimatedLines`，且不得提高原 coverage；任一 run 缺少雙側錨點、連續 6 行以上或無正時間空間就維持 failed。門檻不提供「至少 1 行」例外，因此少於 20 行的稿件漏 1 行即超過 5%，必須 failed。
- `aligned` 是直接可用結果；`recovered` 是保留每行但含推估／局部／不連續證據的完整初稿；`failed` 表示無法安全替全部行建立時間碼。所有狀態都必須公開 `completeSegments`，其長度、文字、順序與 `transcriptLineIndex` 一對一對應裁切空白後的原稿行；不可靠行固定為 `{ start: 0, end: 0, timed: false }`。`usableSegments` 仍只包含具有有效時間且不在 `unmatched`／`ambiguous`／`low-coverage` 集合的行，供診斷與演算法測試使用。這是 provider-neutral 契約，本機、Groq、OpenAI、Azure 與 Google 不可各自決定是否丟句。
- recovered UI 必須列出一基需校對行號、明說「不是精準對齊」、保留診斷下載並鎖定開始按鈕以免重複建立。failed UI 也必須注入整份 `completeSegments`；若 provider 請求或本機推論整次失敗，則把全部原稿行建立成未定時字幕，而不是拋棄使用者已提供的稿件。
- `insertAsrSubtitles(requireValidTimes)` 在新增軌道前驗證有限時間，逐格化後仍須 `start < end` 且 timed cue 全域不重疊。一般完整結果維持 fail-closed；文本匹配另以 `preserveUntimedSegments` 把原本已標示未定時、吸附後零長度或與上一個已接受 timed cue 重疊的單句轉成 `timed:false`，並透過 `onSkippedSegment` 回報原稿行號。它不可補成 0–1.5 秒假字幕，也不可改變句數、文字順序或原編號；歷史快照必須在軌道與字幕一起寫入後才記錄。
- failed／部分成功 UI 必須以一基行號列出 `unmatched`／`ambiguous`／`low-coverage` 行，另合併影格吸附階段轉為未定時的行；recovered 診斷另列 `partial-evidence`／`estimated`／`discontinuous-evidence`。`timed:false` 是正式的未定時 cue：字幕列表顯示 `--:--:--:-- → --:--:--:--`，相對順序與編號保持不變，使用者設定 In／Out 後才成為 timed cue；時間軸、預覽與影片燒錄必須忽略它，Encore／Excel 匯出則保留無時間碼佔位符。`transcript-alignment-diagnostic.js` 只能逐欄白名單複製稿件行、相對時間證據、分數、理由、既知 provider／language 與純數字來源座標；不得從 config、clip、Error、Request／Response 或任意物件遞迴帶入 Prompt、Phrase List、檔名／路徑／URL、API Key／headers、AudioBuffer／Blob／WAV。診斷刻意保留完整稿件與辨識文字，因此這兩個核准文字欄位本身若含路徑／網址字串仍不改寫；必須由使用者主動下載並在 UI 明示分享前檢查，不得自動保存或上傳。
- 文本匹配首版一次只接受一個素材。同一份稿件不可在既有逐素材迴圈中重複套用；成功時透過 `insertAsrSubtitles()` 的命名選項建立「文本匹配」軌，所有行仍只在該注入邊界加 timeline offset 並對齊專案 FPS。
- Provider capability 同時控制導引欄位的顯示與送出：Google 使用一般 Prompt；Groq／OpenAI 使用前文與專有名詞 Prompt；Azure 使用獨立保存的 phrase list；本機模型不顯示 Prompt，送出時也必須強制為空。Azure 的「語言」是 source locale：`zh → zh-TW`、`en → en-US`；`auto` 省略 locales，不可把「請輸出繁中」之類指令塞進 phrase list。
- 本機 Transformers.js pipeline 只在 `speech-recognition-worker.js?worker&inline` 的 Dedicated Worker 執行；`&inline` 是單一 HTML 交付契約的一部分。正常完成會保留 Worker／模型 session 供下一段重用；取消或 Worker 錯誤則由 client `terminate()` 整個執行環境，下一次建立新 Worker，不能退化成只關視窗或丟棄結果。
- 本機執行配置由 `resolveBuiltinExecutionPlan()` 統一決定。設定值仍保留舊 model key 以相容既有 localStorage，但實際載入對應的 `_timestamped` ONNX model id。Whisper Small 在 WebGPU 使用 `encoder_model: fp32`、`decoder_model_merged: q4`；Tiny／Base 為相容既有設定保留全 `fp32`；Large v3 Turbo 目前是相容性與速度優先的全 `q4` 版本，UI 不得宣稱它必然比 Small 準。WASM fallback 一律使用 `q8`。不可把整套 `q8` 模型交給 WebGPU。pipeline cache key 必須同時包含實際 model id、device 與 dtype，切換配置前要 dispose 舊 pipeline。
- 本機 pipeline 固定要求 `return_timestamps: "word"`。`normalizeBuiltinAsrSegments()` 先驗證並修補零長度／倒退時間，再依句末標點、超過 1.25 秒停頓、12 秒上限或 40 個 word 組成 segment；每段仍保留 `words[]` 供文本匹配，不可把 word 丟掉後再用字數平均偽造時間。
- 本機進度在第一個 29 秒 window 完成前是 indeterminate；解碼中由 streamer 顯示目前段落、已產生 token 與經過時間，完成比例只以每個外層 chunk 的 `end()` 計算，不能填入固定 10%／50% 當成實際進度。29 秒 window、左右各 5 秒 stride 的 jump 是 19 秒；`max_new_tokens: 256` 是異常內容未產生 EOS 時的單段保險上限。
- 每次辨識由 UI 建立單一 `AbortController`，同一 signal 傳到本機 Worker 或雲端 fetch；取消按鈕、`Esc`、點背景都走 `openModal.onDismiss`。每個 await 後仍必須檢查 signal，確保不合作或晚到的 provider 結果不會寫字幕、toast、關閉後來開啟的 modal。
- 選擇 `zh` 時，所有 provider 的 segments 在 parser 完成後、字幕注入前統一經 OpenCC `cn → twp` 轉成台灣繁體；轉換只可改 `text`，必須原樣保留 start、end、confidence、words 等時間與辨識欄位。這是書寫系統正規化，不是重新辨識，不能用來掩蓋聲學誤判。

## 6. Electron 與瀏覽器雙模式差異

### 偵測方式

```js
// state.js
const DESK = window.subtool?.isDesktop ? window.subtool : null;
const IS_DESKTOP = !!DESK;
```

### 核心差異

| 功能 | 瀏覽器版 | Electron 桌面版 |
|------|---------|----------------|
| **開啟影片** | `<input type=file>` / 拖放 → `URL.createObjectURL` | `DESK.openMedia()` 對話框，或**拖放**（`DESK.getFilePath` = `webUtils.getPathForFile` 解析路徑）→ 皆走 `loadDesktopMedia()` |
| **MXF / 大檔支援** | ❌ ffmpeg.wasm 限 1.6 GB | ✅ 平台原生 ffmpeg，無瀏覽器記憶體上限 |
| **多音軌** | ffmpeg.wasm 逐一抽取（阻塞） | DESK.ingest() 單次多輸出，並行抽取 |
| **mpv 秒開** | ❌ 不支援 | Windows 偵測到 mpv.exe 時啟用；Apple Silicon 第一版走 ffmpeg ingest/proxy |
| **波形** | 整檔 decodeAudioData（<500MB）或播放時即時擷取 | 平台原生 ffmpeg 抽出 8kHz mono WAV 後解析 |
| **匯入字幕** | `FileReader` | `DESK.importSub()` IPC |
| **匯出字幕** | `URL.createObjectURL` 觸發下載 | `DESK.exportSub()` IPC 寫檔至磁碟 |
| **存/讀專案** | 下載檔案 | `DESK.saveProject()` / `loadProject()` IPC |
| **自動備份** | 每 3 分鐘靜默存入 `localStorage` | 每 3 分鐘寫入 `.subtool_AutoSave/` 子目錄 |
| **Video 安全性** | `webSecurity: true`（受 CORS 限制） | `webSecurity: false`（允許 `file://` 媒體） |

## 7. 關鍵流程說明

### 7.1 字幕渲染流程

字幕在兩個地方渲染：**字幕列表**（側欄 DOM）與**影片疊層**（`#videoSub` 絕對定位 div）。

**影片疊層渲染（`renderVideoSub`）**：
1. 取得當前播放時間 `t = Media.displayTime()`
2. 對每個可見軌道，篩選 `c.start <= t <= c.end` 的字幕
3. 以 `effStyle(cue, track)` 取得字級、`posX/posY`、錨點與其餘生效樣式
4. 設定 `#videoSub` div 的 innerHTML（escapeHTML + `\n` → `<br>`）

**換行是使用者資料，不是排版器決策**：HTML `.line` 使用 `white-space:pre`；自產 ASS
使用 `WrapStyle: 2`。沒有 `\r`／`\n` 的 cue 即使包含一般空格也只能形成單一視覺行；只有
來源換行轉成的 `<br>`／`\N` 才能產生多行。mpv live ASS 與匯出燒錄共用同一份 ASS 規則。

**mpv 模式字幕渲染（`refreshMpvSubs`）**：
1. 以 `SubFormats.toASS(State.cues, fps, tracks, ...)` 序列化全部字幕
2. base64 編碼後透過 IPC 傳給 Electron 主程序
3. 主程序呼叫 mpv `sub-reload` → 載入暫存 .ass 檔案

防抖 100ms 避免快速連續輸入時頻繁重建。

### 7.1b 圖片與時間碼 overlay 流程

1. `renderVideoSub()` 依 `Seq.isActiveAt(clip, Media.displayTime())` 取得作用中的圖片，建立
   `.img-wrap`、虛線選取框與控制點；拖曳只修改該 clip 的 `scale/posX/posY`。
2. 一般 HTML 與 mpv 模式都由主 renderer 的 `#imageLayer` 取得 pointer capture。mpv 模式只將同一份圖片 HTML／矩形送給
   `mpv:setImageGuide` 畫在原生畫面上方；guide 永久穿透，不接收或回送 pointer。
3. 監看 TC 也使用 `Media.displayTime()`：HTML 預覽顯示 DOM overlay，mpv 預覽交給 guide。
   這是監看偏好，不會變成 ASS 字幕，也不會因為開啟監看而影響匯出。
4. 匯出時 `subio.js` 另行傳送 `timecodeWatermark`；主程序把 `drawtext` 接在 ASS 之後，並以
   `font/更紗黑體/sarasa-mono-tc-nerd-regular.ttf` 保持數字等寬。這才是不可逆的交付 burn-in。

### 7.3 音訊混音 Web Audio 圖形

```
video element
  └→ createMediaElementSource
       └→ ChannelSplitter(2)
           ├→ GainNode(L) ──→ ChannelMerger → master GainNode → destination
           ├→ GainNode(R) ──→
           ├→ AnalyserNode(L)  ← 電平表用（不影響輸出）
           └→ AnalyserNode(R)

外部音檔 element
  └→ createMediaElementSource
       └→ ChannelSplitter(N)
           ├→ GainNode(ch0) → master
           ...
           └→ AnalyserNode(chN)
```

**靜音/獨奏邏輯（`applyGains`）**：
```
anySolo = tracks.some(t => t.solo && !t._srcHidden)
for each track:
  audible = anySolo ? track.solo : !track.muted
  gain.value = audible ? track.volume : 0
  if kind === 'native' && activeMix: gain.value = 0  // 有 mix 軌則壓制原生音
master.gain.value = State.muted ? 0 : 1
```

素材增刪會同時改變 Web Audio 圖與原生播放器是否應被壓制；因此刪除外部音訊、History 還原外部音訊、
影音分離與片段切換完成後都必須走 `syncMuteState()`，不可只呼叫 `applyGains()`。mpv 的 mute 以目前
作用中片段是否已有 element／buffer 接管或已解除影音為準。圖片沒有音訊來源，刪除圖片不可取消主影片
仍在進行的 `pendingChannels`／ingest 完成監聽；這些工作只在真正移除最後一個 `video` 母來源時清理。

## 8. 字幕樣式系統（v4.23 起；`substyle.js`）

### 資料模型：三層合成

```
STYLE_DEFAULTS  （模組常數，全部欄位的預設值）
      ⊕ track[k]        （軌道級：State.tracks[i] 上的同名欄位）
      ⊕ cue.style[k]    （逐句覆蓋：只存差異，限 CUE_STYLE_KEYS）
      ＝ effStyle(cue, track)   ← 三路唯一的輸入
```

- **單一預設來源**：目前出廠字級／位置為 `fontSize=80`、`posX=50`、`posY=90`；
  `newTrack()` 只建立名稱／顯示／鎖定欄位，缺少的樣式全部由 `STYLE_DEFAULTS` 後援。
- **專案外觀不可漂移**：存檔以 `trackStyleSnapshot(track)`（內部為
  `styleSnapshot(effStyle(null, track))`）展開當下生效樣式；
  讀檔只複製實際存在的 canonical 欄位。舊 `fontScale`／`posPct` 僅在
  `fontSize`／`posY` 缺少時遷移，不可覆蓋舊專案明確存下的數值。
- **undo 零改動**：`history.js` 用 `structuredClone({cues, tracks, …})`，新欄位自動入快照。
- 樣式面板的編輯對象由 `app.js styleTarget()` 決定：**有選取字幕就寫該句的 `cue.style`，
  沒選才寫軌道**（v4.31.0）。面板九個控件全部收斂到單一 `tsSet()`——之前各自
  `State.tracks[i][k]=v`，等於「改樣式一律套全軌」。

### 座標與對齊

- `posX/posY` 存**百分比**（解析度無關、專案可攜），UI 與摘要以**像素**顯示（`posToPx()`）。
- `align/valign` ＝ 多行多句彼此的對齊，**同時**是文字塊貼齊座標的那一側（＝ASS `\an` 語義）。
  `align=center + valign=middle` 時，座標就是文字塊正中心。
- HTML：容器 `left/top` ＋ `translate(-ax%, -ay%)`；ASS：`\pos(x,y)` ＋ Style `Alignment`。
  兩邊的錨點由 `anchorPct()` 共用。
- **旋轉支點是錨點，不是方塊中心**：ASS 的 `\frz` 繞 `\org`（預設＝`\pos`）轉。CSS 的
  `transform-origin` 必須跟著設成錨點，否則只有「左右中＋上下中」時兩者才重合（v4.30 修）。

### ASS 的表達力邊界（哪些能 inline、哪些只能 Style 行）

| 欄位 | 逐句覆蓋怎麼做 |
|------|----------------|
| 字型/字級/顏色/粗斜/字距/框線/陰影/角度 | inline tag（`cueAssTags()`：`\fn \fs \c \b \i \fsp \bord \3c \shad \frz`） |
| 對齊 `align/valign` | inline `{\anN}`（`assAlignN()`） |
| 座標 `posX/posY` | inline `{\pos(x,y)}`（`cueAssPos()`） |
| **背景色塊** `bgBox/bgColor/bgAlpha` | **只有 Style 行有（BorderStyle=3／BackColour），無 inline tag** → 有覆蓋的句子由 `formats.js` 額外生一條 `Cue_<id>` Style（`STYLE_ONLY_KEYS`） |

標準 `BorderStyle=3` 會替每一行各畫一個背景盒：短行會縮窄，而且半透明盒相交時會形成較深橫帶；
這與 HTML 預覽的單一 multiline `<span>` 矩形並不等價。水平字幕的正式路徑因此由
`subtitle-background-layout.js` 用 Chromium 只選出最寬行，並凍結 CSS 共用的 line-height、錨點偏移與
逐行座標；**不可凍結 Chromium 的數值字寬**。`formats.js` 再把該行交給 libass，以輸出時真正使用的
字型排出寬度，利用單一、置於整段字幕中心的 `BorderStyle=3` Dialogue；字形保持 `fscy=100`，
再以 `xbord/ybord` 從單行文字盒向外擴張成整段方角底框，避免 libass 與 VSFilter/PotPlayer 對
縮放後 ascender／descender 與 top alignment 的解讀差異使底框上移，最後以
`TrackN_Text` Style 疊回逐行文字；mpv 與交付燒錄都吃同一份結果。HTML 底框也維持方角。
這同時避免跨字型引擎的寬度誤差集中到左／右錨點、保證各行底色等寬，且使用者在送出後再改字幕
不會改到佇列中已凍結的垂直幾何。

`subtitleBackgroundGap()` 仍是 HTML line-height、水平文字 spacer 與直書列距的共用安全下限；
直書因採一列一個 Dialogue，維持既有 `BorderStyle=3` 路徑。低階 `SubFormats.toASS()` 若沒有收到
明確背景幾何也會安全退回標準 ASS 表達，而不臆測字型寬度。

### 直書（v4.29.3）

- HTML：`writing-mode: vertical-lr`（**第一行在最左**，非 CJK 書籍的右→左傳統）。
- ASS 無 writing-mode → **一列一個 Dialogue**（`verticalAssCols()`）：
  - **y 交給 libass**：`valign` → `\an`（上8/中5/下2），每列各自貼齊同一基準線
    ＝「多列之間上/中/下對齊」的語義，**完全不必估算文字高度**（各列長度不同、ASS 行高
    也不等於字級，硬估必歪）。
  - **x 自己算**：列距 ＝ `fontSize × effectiveSubtitleLineSpacing()`，保留使用者行距並套用背景盒
    不重疊的安全下限；它恰為 CSS `line-height:<number>` 在直書時的水平步進。整塊寬 ＝ 列數 ×
    列距，再依 `align` 決定哪一側對齊 `posX`。
- 字距／行距語義：直書時 `letterSpacing` ＝ 字間（縱）、`lineSpacing` ＝ 列間（橫）。

### 字型管線（v4.24 起）

```
font/<資料夾名>/<字型檔>          ← 資料夾名＝UI 顯示名（使用者自取）
   ↓ electron/main.js fonts:list
{ name: 資料夾名, file, family: 檔案內部家族名 }   ← fontNamesOf() 解析 sfnt name table
   ↓                              ↓
FontFace(name, ArrayBuffer)    substyle.assFontName(name) → family
（HTML 預覽）                   （ASS Fontname → libass 靠它比對）
```

- **一個資料夾只取一個檔**：`pickRegularFace()` 挑最接近 Regular（`usWeightClass` 離 400 最近、
  非斜體）的那個。多放字重沒有作用，只會讓安裝檔變大。
- CSS `@font-face { src: url('file://') }` 會被 Chromium 擋（"A network error occurred"）→
  必須用 **FontFace API + ArrayBuffer**。
- 主行程的檔案能力權威：`fonts:list` 只授予已掃描字型根的唯讀能力，renderer 才取得到該字型的
  `fs:fileURL`；不可因 renderer 查詢某條路徑就把整個資料夾升格為可讀。
- 打包：`package.json` 的 `extraResources` 把 `font/` 送進 `resources/font`；`fontsRoot()` 依
  dev（專案根）→ `resources/font` → 安裝目錄 順序尋找。

### 常用樣式庫（presets；v4.33.3 起含內建）

```
BUILTIN_PRESETS  ← 模組常數，唯讀。目前一筆「預設字幕樣式」＝ { ...STYLE_DEFAULTS }
      ＋
_presets         ← 使用者自訂，桌面存 config/settings.json 的 subPresets 鍵、瀏覽器存 localStorage
      ＝ getAllPresets()   ← UI 列表／名稱比對用（內建永遠在最前）
```

- **內建務必寫成 `{ ...STYLE_DEFAULTS }`，不要另抄一份數值**——抄一份就等於兩個真相來源，
  改了預設值而忘了改內建（或反之）就會漂掉。使用者要求的規格與現行預設值本來就一致。
- `getPresets()` **只回使用者清單**，`savePresets()` 也**只寫使用者清單**並先
  `filter(!isBuiltinPresetName)` —— 否則使用者存一筆同名的就把內建蓋掉，「回出廠設定」失效。
- UI 列表用 `getAllPresets()` 的索引 `i`，但改名／刪除／編輯按鈕帶的是**使用者清單索引**
  `i - BUILTIN_PRESETS.length`（要跟 `getPresets()` 對得上）。新增內建筆數時這裡自動跟著調整，
  但**任何直接拿列表索引去 splice 使用者清單的新程式碼都會錯位**。

#### 編輯常用樣式（v4.34.0；`app.js _presetEdit`）

「編輯」不另做一份樣式編輯 UI，而是**暫借目前軌道當草稿**：把該 preset 套到目前軌，使用者
就用原本那套面板控制項邊調邊看即時預覽（三路照常運作）。

```
_presetEdit = { name, ui, before, trackIdx, targets:{tracks[],cues[]}, old }
                              ↑ 進入前的軌道樣式      ↑ 進入前就符合舊樣式的軌與句
```

- 進入編輯時**先掃出 `targets`**——套上草稿之後就分不出誰原本符合了。
- **編輯期間 `styleTarget()` 強制回整軌**（`if(_presetEdit) return {cues:[]}`），否則使用者
  剛好選著一句時，改動會跑進 `cue.style` 逐句覆蓋、按完成時從軌道抓不到草稿。
- 完成：寫回 preset ＋ 把 `targets` 全部換成新樣式；**目前這軌若不在 `targets` 內就還原**
  ——它只是借來當畫布，不該被順手改掉。取消：只還原 `before`。
- 「誰套用了這組樣式」用**全欄位相符**判定，判準只有 `substyle.js` 的
  `styleMatchesPreset()` 一份（v5.10.0 起）。
  **資料模型裡沒有「這條字幕套用了哪個 preset」的欄位**，只能靠比對；
  要改成存名稱的話，改那一支即可。

  > 這一行原本寫的是「與 `subtitles.js _trackPresetName` 同一套判準」——
  > 而 `_trackPresetName` **早就改名**成 `_getPresetNameForStyle` 了，文件與程式碼裡的
  > 兩則註解都沒跟上。當時全專案有**三份**相同的謂詞靠這幾句話維持同步，
  > 指路的名字卻是錯的。這就是為什麼判準要收斂成一份、而不是靠註解。

- 逐句覆蓋若與所在軌道的生效值相同，會由 `pruneRedundantCueStyle()` 清掉
  （清空後連 `cue.style` 一起移除）。**只清沒有作用的欄位**——真正與軌道不同的覆蓋
  一律保留，那是使用者要的釘選，軌道樣式日後改變時不該跟著跑。
  沒有這一步的話，對某一句「套用軌道正在用的那組樣式」會寫進 19 個毫無作用的覆蓋，
  外觀完全沒變、列表卻多一個 ✱。

### 樣式面板版面（`index.html #trackStyle`）

欄位順序由使用者指定，改動前先確認需求（歷經 v4.34.0～v4.34.4 多次微調）：

```
行1  大小 60/80＋數值 ｜ B I ｜ 對齊 [上下▼][左右▼] ｜ 直 ｜ 字色＋三色鈕 ｜ 字型▼
行2  座標 X Y ｜ 角度 ｜ 字距 行距 ｜ 框線＋框色 陰影 ｜ 底＋底色＋不透明度
行3  常用樣式 [套用▼] ☆存為常用 ⚙管理 ｜ 全軌套用 ｜ 全軌套用-排除座標
```

- 正常模式沒有任何已選字幕時，`styleDisplayTarget()` 只供顯示目前軌道的生效值；
  `styleTarget()` 必須回傳 `null`，並由 `setStylePanelInteractivity()` 停用所有可寫控制，避免操作
  無聲地落到整軌。只有明確的常用樣式編輯 draft 可在沒有字幕選取時維持可編輯。
- 兩個全軌動作都必須先有來源字幕：`全軌套用` 包含幾何，`全軌套用-排除座標` 保留各句的
  座標與角度。圖示不同只是辨識輔助，實際語意仍由 style assignment plan 決定。
- 字型下拉**只列 `font/` 掃出來的**（v4.34.4 拿掉「自訂…」；手打系統字型名匯出時常配不到，
  見 §0.3）。但**保留「字型不在清單時動態補一個 option」**——舊專案存過已移除／改名的字型
  時要照實顯示，否則下拉會跳到別的字型，看起來像被程式偷改。
- 重排面板後**務必逐一確認每個控制項的事件還接得上**（改一遍值再讀 `effStyle`）；只看 DOM
  順序不夠。另見 §0.7：「同一行」要比垂直中心，不是盒頂。

## 9. WebCodecs 預覽引擎（v4.20 起；`decode/player.js`）

自寫播放器，取代「原生 `<video>` 只能顯示單軌」的限制，做到**多軌即時合成預覽**
（疊層／透明度／子母畫面／淡入淡出／真溶接），且**與匯出一致**。

```
每個來源檔一個 SourceStream
  demux（索引，見 §10）→ VideoDecoder → frames[] 淺佇列 → 取最接近 t 的 frame
rafLoop 每幀 tick()：
  Seq.clipsAt(t) 由下而上 → 逐層取 frame → Canvas2D 合成 → #previewCanvas
```

要點與踩過的坑：

- **`<video>` 仍負責聲音與時鐘**（`media.js` 完全不動）；canvas 不透明蓋在它上面。
- **畫布 ＝ 專案輸出解析度**（`State.videoWidth/Height`），與匯出同一張畫布 → 字幕大小不隨各片
  解析度／比例改變。曾用「第一層的解析度」當基準 → 疊加不同片時字幕大小不同。
- **預設軟解**（`hardwareAcceleration: 'prefer-software'`）：部分環境硬解連續解碼會卡死
  （約第 18 幀）；720p 軟解 >3000fps，夠用。
- **跳轉偵測要比對 keyframe 索引，不能比距離**：長 GOP 從頭重解時，用「目標 vs 已餵位置」的
  距離會每幀誤判成再次跳轉 → 無限 reseek、永遠吐不出 frame。
- **B-frame 的首幀 cts 常 >0**：`SourceStream.startUs` 要夾住下界，否則 `t=0` 被誤判成後退。
- **沒有任何可解圖層時要 `_hideCanvas()`**：不透明畫布留著會蓋成全黑（曾出現「看得到字幕、
  看不到影像」）。
- 只有 `!layers.length` 才讓回 mpv；頂層暫時解不出來時**保留上一幀**，否則 HTML 字幕層會被
  一起藏掉（曾出現「疊加後字幕消失」）。

### 為什麼【不】做 WebGL 合成（原 #26，已結案不做）

曾規劃「階段4：改用 WebGL 合成」當作效能優化。**實測後結論是不值得做**：

| 情境（3 軌重疊、含 scale 0.5＋opacity 0.7） | tick 平均 | 繪圖（fillRect＋drawImage） |
|---|---|---|
| 畫布 974×592（一般視窗） | 0.353 ms | **0.302 ms/幀** |
| 畫布 2894×1743（**8.7 倍面積**） | 0.380 ms | **0.315 ms/幀（+4%）** |

- 合成只佔 60fps 預算（16.7ms）的 **約 2%**。
- **面積放大 8.7 倍，成本只增加 4%** → 瓶頸不是填像素，而是每次呼叫的固定開銷。
  也就是說 **Canvas2D 早已在 GPU 上合成**，WebGL 沒有東西可優化（它自己還要付每幀貼圖上傳）。
- 代價卻是：多一條渲染路徑要維護、context lost 處理、驅動相容性問題。

> 量測方式：包住 `previewCanvas` 的 2D context 與 `WCPreview.tick`，靜止在三層重疊區內統計
> 543 幀（rafLoop 不論播放與否每幀都會完整合成）。
> **注意兩個會讓量測失效的坑**：①片段只有 2~3 秒，一播就播完 → 後半段全是黑幀、數字被稀釋；
> ②三段若各自接續而非重疊，`clipsAt(t)` 只會拿到一段 → `mode` 是 `black`＝根本沒量到合成。
> 量測前後都必須斷言 `mode==='wc'`，並檢查「繪圖呼叫數 ÷ 幀數 ＝ 1＋層數」。

## 10. 串流式 demux（v4.29 起；`decode/demux.js`）

長片的 720p proxy 實測 **2.6–4.25 Mbps**（CRF26 ＋ 每 0.5s 一個關鍵幀），**兩小時＝2.3–3.7GB**
——整檔讀進記憶體不可能。

```
demuxIndex(url)
  ├─ rangeWorks()：先用 1KB 探針確認此來源支援 Range
  ├─ 取檔頭（4MB → 24MB 兩級）餵 mp4box → onReady → buildSampleLists()
  │    每顆樣本的 offset/size/cts/is_sync 全在 moov（stco/stsz/stts/ctts/stss），不需要 mdat
  └─ 回 { config, index[], keyIdx[], maxEnd }        索引 10 萬顆樣本僅約數 MB

SampleReader：對齊格線的「樣本視窗」按需抓位元組（上限 48 顆或 4MB，常駐 4 個視窗）
退路：moov 不在檔頭（非 +faststart 的外來檔）→ 明確失敗 → player 靜靜退回整檔路（1.5GB 上限）
```

**Range 的坑（重要）**：Chromium 的 `file://` loader **會套用 Range，但回 200 且不給
`Content-Range`**；而真正忽略 Range 的實作會回**整個檔案**——兩者狀態碼相同，**只有長度能分辨**。
所以 `fetchRange()` 一律用長度把關，長度不符即報錯，**絕不把「整檔」當「某一段」餵進 decoder**
（那會解出花屏，而且錯得很安靜）。

實測（1.66GB／67 分鐘／100,500 幀）：索引 39ms、常駐位元組 2.5MB、JS heap 30MB。

### 索引上的算術都在 `decode/sample-index.js`（v5.11.0 起）

索引一旦建好，剩下的全是算術：目標時間落在哪個 GOP、一次抓哪一段樣本、位元組區間與位移、
誰先被丟掉。這些原本內聯在 `SampleReader` 與 `player.js` 的 `_keyBefore` 裡——而那兩支都需要
真的 mp4 位元組、`fetch` 與 `VideoDecoder` 才跑得起來，**等於完全沒有測試**。
抽成純函式後以合成索引陣列測（不必把媒體檔放進版控），17 個突變全部轉紅。

> **抽出來當下就抓到一個真的 bug：高位元率原生檔的預覽會永久卡住。**
> 視窗同時受「48 顆樣本」與「4MB」兩個上限拘束。每顆樣本 1MB 的原生檔，
> 一個格子 48 顆卻只裝得下 4 顆——而舊寫法拿**格線起點**當視窗的鍵，
> 於是樣本 4…47 全部指向鍵 0，鍵 0 的視窗卻只涵蓋 `[0,4)`。
> `ensure()` 查到鍵 0 已存在就直接返回，那些樣本的位元組**永遠不會被抓**，
> `data()` 永遠回 `null` → 該層預覽就停在那一格畫面上，不報錯也不會恢復。
> 修法是 `planWindow()`：格子被位元組上限切斷時，後續視窗從切斷處接續。
> 沒被切斷的常見情形（proxy 檔 48 顆 ≈ 1MB）行為完全不變，各層仍共用同一個視窗。

## 11. 驗證方式（CDP 真機）

單元測試（`npm test`，vitest）只涵蓋純函式。**所有 UI／媒體／字型／匯出的行為一律真機驗證**：

```bash
# 用【獨立的 user-data-dir】啟動 dev electron，切勿殺掉使用者安裝的 SUB Tool.exe
electron . --remote-debugging-port=9223 --user-data-dir=<temp> \
  --disable-background-timer-throttling --disable-renderer-backgrounding \
  --disable-backgrounding-occluded-windows
```

- `window.SUB` 是除錯把手（`app.js` 尾端），暴露 State/Media/render*/toASSFromState/_stageRect/
  WC/SubStyle 等。
- 互動要發**真事件**（CDP `Input.dispatchMouseEvent`）——`Runtime.evaluate` 造假事件驗不到
  pointer capture／pointer-events／hit-test。
- **背景視窗的 setTimeout/rAF 會被節流** → 一定要加上面那三個 flag，並 `Page.bringToFront()`。
- **測試必須自己處理擋路的對話框**：`openCueEditModal` 會先 `await ensureProjectSaved()`，
  全新實例下會跳「開始前先儲存專案」把後續視窗擋住。不處理的話，「前一輪剛好把專案標記成
  已存檔就過、換個乾淨實例就掛」——這種看時機決定過不過的測試比沒測還危險。
- **每支測試用全新實例跑**：共用同一個 app 實例時，前一支留下的選取狀態會污染後一支。

判準請見 §0.6「有產出不等於對」。

## 12. 快捷鍵綁定（v5.11.0 起；`src/keybinding.js`）

一個**綁定**是 `{ key?, code?, ctrl?, shift?, alt? }`；整份 keymap 是 `{ 動作名: 綁定[] }`
（每個動作最多三組，見設定視窗）。對這個資料結構要做五件事：從鍵盤事件錄出一個綁定、
判斷是否與別人重複、顯示成文字、拿真實事件比對整份 keymap、匯入時與預設合併。

**這五件事現在只有 `keybinding.js` 一份實作**，`settings.js`（前四項）與 `keyboard.js`（比對）
都從這裡取用。

### 數字鍵盤的約定（v4.4.2 起）

NumLock 開時，數字鍵盤的字元鍵 `key` 值與主鍵盤**完全相同**（Numpad2 → `'2'`），只有 `code`
分得出來。所以：

- 數字鍵盤一律以 **code**（`NumpadX`）綁定，主鍵盤以 **key** 綁定；
- 數字鍵盤產生的**字元**事件不得命中 key 綁定，否則按數字鍵盤 2 會觸發主鍵盤 2 的 `zoom_in`。

### 比對分兩輪：先 code、再 key

> **這是 v5.11.0 修掉的一個真 bug。** 舊寫法是單輪掃描，「code 綁定贏過 key 綁定」只在
> **該動作剛好排在 keymap 物件前面**時才成立。預設表裡 `next_cue_5f {code:'Numpad2'}` 排在
> `step_boundary_next {key:'arrowdown'}` 之前，所以 NumLock 關著按 Numpad2 是對的——
> 靠的是物件鍵的順序。
>
> 而 `NumpadEnter` 的 `key` 是 `'enter'`（長度 > 1，不受「字元鍵」那條保護），
> 而 `toggle_play_pause {key:'enter'}` 是預設表的**第一項**。於是使用者把 NumpadEnter
> 指派給任何動作，按下去都只會播放／暫停——而且設定視窗的重複檢查也不會提醒
> （一個比 code、一個比 key，不算重複）。NumLock 關著的 `NumpadDecimal`（key 為 `'delete'`）同理。

分兩輪之後，「明確指定 code 的綁定優先」成為規則本身，不再依賴物件順序。
`tests/keybinding.test.js` 保留一份**舊實作**當參考，對整份預設表逐鍵（數字鍵盤 16 鍵 ×
NumLock 開關 × 5 種修飾鍵，加上主鍵盤所有已綁定的鍵）比對兩者的判定——
除了上面那個 bug 之外**沒有任何現行行為改變**。
