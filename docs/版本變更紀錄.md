# CHANGELOG — SUB Tool

所有版本的重要變更紀錄，依時間倒序排列。

> **⚠ 絕對不要對這個檔案做版號的全域字串取代。**
> 這裡的每一個版號都是**歷史事實**：`## [v5.3.0]`、「v5.2.0 起的安裝版才開始壞」等，永遠不要動它們。

## [v5.11.10] — 2026-08-03

* **右鍵快速定位**：在時間軸上的所有影片、圖片片段，以及下方獨立的外部音軌區塊，點擊右鍵選單新增了「📂 用 檔案管理器 打開」的選項，方便您快速在檔案總管/Finder 找到並管理原始素材。

## [v5.11.9] — 2026-08-03

* **自動重新連結遺失素材**：當 `.subtool` 專案檔或其所在資料夾被重新命名、移動時，如果在開啟專案時找不到原始影音檔案，軟體現在會自動在專案檔所在的資料夾，以及往下的 3 層子資料夾內尋找同名檔案，並自動完成修復與載入，不再頻繁跳出「找不到原影片」的警告。

## [v5.11.8] — 2026-08-03

* **架構重構 (Phase 1: AudioPipeline)**：將原先與 `Media` 緊耦合的專案音訊匯流排邏輯 (Routing) 抽離至獨立的 `AudioPipeline` 模組，並準備引入 `WebAudioAdapter` 與 `FFmpegAdapter`。
* **環境清理**：清理專案中多餘的測試與暫存檔案 (`tmp_profile` 與 `test-media`)。

## [v5.11.7] — 2026-08-03

* **直書排版修正**：徹底解決直排字幕（writing-mode: vertical-lr）因 Chromium 排版引擎底層 bug 導致文字截斷、虛線框只顯示一半且無法選取／拖曳的問題。改用「橫排維度轉換測量法」，精準抓取文字真實邊界尺寸，確保直排字幕虛線框精準包覆文字且支援正常滑鼠互動。
* **墨水溢出包覆**：擴大字幕測量的安全緩衝區 (12px)，解決部分字體在橫書時因 ascender/descender 超出標準行高，導致虛線框切過字體底部的視覺瑕疵。
* **設定文字精簡**：微調 `settings.js` 中的快捷鍵提示文字，使其更簡潔。



* **UI 調整**：修訂時間軸與工具列文字，將「+軌道」改為「+字幕軌」、「解除影音連結」改為「影音分離」、「切割片段」改為「切割」，並優化自訂播放速度的對話框文字。
* **介面修正**：修復時間軸縮放調整條的圓鈕無法切齊邊緣的視覺問題，加入專用的 `range` 樣式。
* **超高速播放支援**：解決使用快捷鍵 (J/L) 或自訂速度設定超過 4 倍速時，Chromium 引擎因底層 `preservesPitch` 限制導致卡頓或失步的問題。當速度 > 4x 時，自動關閉音高修正以確保影音能順暢高速播放，並將播放速度的介面上限與快捷鍵上限放寬至 16x（Chromium 引擎的最高支援極限）。

## [v5.11.5] — 2026-08-03

* 調整匯出檔名產生邏輯：自動移除音軌設定名稱中的小數點（.）與減號（-），改為更簡短的標示（例：2.0-ME 變為 20ME，5.1-FM 變為 51FM）。

## [v5.11.4] — 2026-08-03

根據使用者音軌設定自動套用交付檔名後綴：
* 多軌 Mono 會統一名稱為 `NCH-Mono`（如 `8CH-Mono`）。
* 多軌包含名稱時（如 `2.0-ME`, `2.0-FM` 等）會依照 UI 的自訂名稱組合寫入檔名，例：`_5.1-FM+2.0-ME.mp4`。
* 預設沒有自訂名稱時，會以 Layout 自動對應為 `2.0-FM`、`5.1-FM` 或 `1.0-FM`。

## [v5.11.3] — 2026-08-03

這一版深化了音訊載入與時間軸編輯架構。此為一系列底層重構的延續，確保了路由判定的唯一性與時間軸狀態變更的單一入口。

### 🏗 架構深化與修正

* **音訊路由與增益（Media Routing）**：`Media.routedTrackStatesForBus` 現在會回傳該 bus 真正收到的完整增益（包含 route、placement 與 bus gain）。`mixer.js` 不再自己解讀與過濾 `Media.tracks`，全面改用 `ProjectAudioInterpretation`，讓判定的唯一真相收斂至 `media.js`。
* **時間軸編輯狀態（Timeline Edit Transaction）**：統一了軌道編輯（例如軌道高度調整、鎖定、隱藏等）的狀態寫入與重繪機制：
  * 在連續拖曳調整大小時能即時預覽，但只會產生單一筆復原（undo）紀錄，且能正確取消多餘的預覽畫面更新（RAF）。
  * 隱藏視訊軌時，不會再連帶觸發不相關的 mpv 字幕更新。
  * 鎖定視訊軌時，會自動清除「屬於該軌但正被選取」的片段狀態，避免隱式修改。
* **修正 Intake Session**：修復了 `MediaIntakeSession` 的非同步清理機制，確保在前一次載入中斷並啟動清理時，相關程序會在下一次載入啟動前完整執行完畢。

### ✅ 驗證

* 測試環境：確保 Windows x64 平台完成測試及打包。

## [v5.11.1] — 2026-08-01

這一版把 Apple Silicon 的本機測試版建置接進既有 Electron 架構，並修正多音軌素材在
桌面版與網頁版之間容易被誤解成「兩條 Stereo 音軌」的問題。核心定義維持不變：
**素材來源聲道、專案 Mono bus、交付輸出 stream 是三件不同的事**；桌面版匯入時，
每個 audio stream 裡的每個 channel 都必須先成為可獨立配線的 Mono 來源聲道。

### 🍎 Apple Silicon unsigned 測試版

* 新增平台感知的 ffmpeg／ffprobe 尋址與能力驗證。Windows 仍使用既有 x64 原生工具；
  Apple Silicon 只封裝 `darwin-arm64` 工具，不會把 Windows ffmpeg／mpv 混進 App。
* 新增 `npm run native:prepare:mac` 與 `npm run dist:mac:test`：在 M 系列 Mac 上準備 arm64
  原生工具、驗證 `ass`／`libx264`／`prores_ks`／`pcm_s24le`／`mxf`，再產生 unsigned
  DMG 與 ZIP。這是本機功能驗證版，**尚未包含 Developer ID 簽署與 notarization**。
* macOS 第一版刻意不啟用 Windows HWND／named-pipe 專用的 mpv 嵌入；MXF、多音軌與
  非原生格式統一走 ffmpeg ingest + HTML/WebCodecs 預覽，避免假裝跨平台但實際誤走
  Windows 專用路徑。

### 🔊 多音軌逐聲道載入

* Windows 與 macOS Electron 現在共用 `buildAudioIngestPlan()`。例如一支
  `5.1 FM + 2.0 FM` MP4 會依 stream 順序拆成 `S1 Ch1–6`、`S2 Ch1–2`，共 **8 個
  獨立 Mono 來源聲道**；每條都有自己的 `sourceStream/sourceChannel`、快取檔與
  FFmpeg `pan=mono` 映射，可獨立路由、Mute、Solo 與匯出，不會降混成兩聲道。
* 兩條 Electron ingest 路徑（一般單次 ingest 與邊轉邊播 stream ingest）不再各自維護
  一份 filtergraph 迴圈，避免 Windows／macOS 或兩種開檔路徑日後靜默漂移。

### 🌐 6GB 網頁版能力提示

* 大型原生 MP4 仍可用瀏覽器播放，但只明確承諾 **Stereo 預覽**；畫面會持續引導使用
  macOS／Windows 桌面版載入全部 Mono 聲道，而且提示不會再被「N 條專案音訊軌」或
  即時波形文字覆蓋。
* 大型 MXF 等非原生格式無法送入 ffmpeg.wasm，現在會誠實顯示「網頁版無法載入」，
  不再錯稱仍有 Stereo 預覽。

### ✅ 驗證

* `npm run lint`、`npm test`（70 個測試檔／1007 項）、production build 全數通過；
  新增測試會逐條比對 `sourceChannel n → cN → coN`，並涵蓋 `audioTracks` 提早返回、
  6GB 原生／非原生分支與警告清除。
* 用內建 FFmpeg 產生內容各異的 `5.1 + Stereo` MP4，再執行產品實際 ingest filtergraph：
  8 個輸出均為 Mono，八條頻率標記依序對回原始聲道，混合波形也有內容。
* 打包後的單檔 `dist/index.html` 已以真正 Headless Chrome 驗證兩種大型檔提示皆為
  computed `display:block`；並做過突變測試，故意把八軌全接 `c0` 或清掉警告都會讓測試轉紅。
* Apple Silicon 的 DMG、實際 6GB 母檔與交付輸出仍須在實體 M 系列 Mac 執行
  `docs/開發與驗證.md` §4.16 的真機驗收；Windows 的 lint／test／build 不能取代。

## [v5.11.0] — 2026-08-01

延續 v5.9.0、v5.10.0 的方向的第三輪架構深化。**這一版沒有新功能**，
但在抽出模組的過程中撞到**兩個真的 bug**——這正是「抽出來才測得到」的意義。

### 🐛 三個 bug

* **空專案按空白鍵之後停不下來**（v5.9.0 引入的迴歸，v5.9.0 與 v5.10.0 都中）。
  還沒載入任何媒體時按空白鍵會開始跑虛擬時鐘（這是刻意的——空專案可以先排字幕），
  但**再按一次要暫停時整個 `pause()` 會在中途丟 TypeError 中斷**：
  `Media.pause()` 把 `_activeClip()` 的結果交給 `TimelineTransport.sourceTime()`，
  而空專案時那是 `null`，`Seq.toSource(t, null)` 就去讀 `null.offset`。
  後面的 `video.pause()`、`this.playing = false`、按鈕改回 ▶ 全部沒執行——
  **播放頭停不下來，而畫面上沒有任何錯誤訊息**。
  這個轉換原本內聯在 `pause()` 裡、帶著 clip 判斷，v5.9.0 抽進 transport 時守衛掉了；
  同一支檔案的 `timelineTime()` 有守、`sourceTime()` 沒有。已補上並加迴歸測試。
  *（這是這一版打包後真機驗證時撞到的——不是靠讀程式碼發現的。）*

* **高位元率原生檔的即時預覽會永久卡住**。串流式 demux 的位元組視窗同時受
  「48 顆樣本」與「4MB」兩個上限拘束。每顆樣本 1MB 的原生檔，一個格子 48 顆
  卻只裝得下 4 顆——而舊寫法拿**格線起點**當視窗的鍵，於是樣本 4…47 全部指向鍵 0，
  鍵 0 的視窗卻只涵蓋 `[0,4)`。`ensure()` 查到鍵 0 已存在就直接返回，
  那些樣本的位元組**永遠不會被抓**，`data()` 永遠回 `null`
  → 該層預覽就停在那一格畫面上，**不報錯、也不會恢復**。
  修法是 `planWindow()`：格子被位元組上限切斷時，後續視窗從切斷處接續。
  本專案自己產的 proxy（48 顆 ≈ 1MB）不會踩到，所以一直沒被發現。
* **`NumpadEnter` 沒辦法指派給任何動作**。快捷鍵比對原本是單輪掃描，
  「數字鍵盤專屬的 code 綁定贏過主鍵盤的 key 綁定」只在該動作**剛好排在
  keymap 物件前面**時才成立。而 `NumpadEnter` 的 `key` 就是 `'enter'`，
  `toggle_play_pause {key:'enter'}` 又是預設表的**第一項**——所以不管指派給誰，
  按下去都只會播放／暫停。設定視窗的重複檢查也不會提醒（一個比 code、一個比 key，
  不算重複）。NumLock 關著的 `NumpadDecimal`（key 為 `'delete'`）同理。
  改成兩輪（先 code 再 key）後，優先順序成為規則本身，不再依賴物件鍵的順序。

### 🧹 六處架構深化

* **匯出工作的狀態機收斂成單一定義**（`electron/export-job-status.js`）。
  七種狀態原本是散在 `electron/` 的 **46 處字面字串**，而「這個狀態算什麼」的分類
  有五份、分別住在 `queue-store.js`、`main.js`、`export-queue-state.js` 三支檔案裡。
  新增一種狀態時，沒有任何機制告訴你「還有三個地方要表態」——而漏掉 `terminal` 那一份的
  後果，正是 v5.7.0 記過的「已完成的工作重啟後被當 `queued` 重跑，
  以 `-y` 覆寫掉已經交付出去的成品」。
* **快捷鍵綁定規則抽成共用純模組**（`src/keybinding.js`）。錄製、重複判斷、顯示、
  比對、匯入合併五件事原本分散在 `settings.js` 與 `keyboard.js`，
  **兩邊各有一套「數字鍵盤怎麼算」的理論而且不一樣**——上面那個 bug 就是這麼來的。
* **淡入淡出補上吃時間軸時間的入口**（`fadeAlphaAtTimeline`）。三個預覽呼叫端拿到的
  都是時間軸時間，於是三處各寫了一次 `fadeAlphaAt(c, t - c.offset)`——而且寫法不一致：
  兩處是 `c.offset || 0`，一處是 `c.offset`。遇到沒有 `offset` 欄位的片段，
  前者當 0、後者算出 `NaN` → **整段變全透明**。鐵律 §0.5：時間域轉換不該散在呼叫端。
* **復原快照補上往返測試**。`History.snap()` 收 12 個欄位，而 `restore()` 是另一份
  **手寫清單**，兩者沒有任何機制對齊。在 `snap()` 加了欄位卻忘了在 `restore()` 讀回來，
  結果是「Ctrl+Z 之後有一半沒回來」，而且不會報錯。現在每個欄位都跑
  「設成 A → 記錄 → 設成 B → undo → 應為 A → redo → 應為 B」。
  順帶連 `Seq.snapshot()` ↔ `Seq.restore()` 一起守住（clipGeo 是唯一由另一支模組序列化的）。
* **預覽拖曳補上測試**（`pointer-interaction.js`，先前完全沒有）。四角縮放的方向係數、
  倍率夾限（0.02–8）、位置夾限、字幕旋轉的 15° 吸附與角度正規化——這些壞掉的樣子
  都不會報錯：往外拉反而縮小、圖片被拖到畫面外、角度累加成 350° 讓匯出的 ASS `\frz` 也跟著錯。
* **demux 索引上的算術抽成純模組**（`src/decode/sample-index.js`）。關鍵幀二分搜尋、
  視窗規劃、位元組區間與位移、LRU——原本內聯在 `demux.js` 與 `decode/player.js` 裡，

### 🧭 三路一致終於有守衛了（§0.1）

`§0.1 三路一致`（HTML 預覽 ＝ mpv ＝ 匯出燒錄）是本專案最重要的一條鐵律，
但在這之前，**只有幾何側有機制擋漂移，樣式側完全靠自律**——
`styleToCss()` 被 **0 支測試**碰到過。

現在三支契約測試補齊，形狀都一樣：同一份規格必須渲染成兩種不同的表達，
無法合併成一份實作，於是用矩陣窮舉比對兩邊，任一邊被改而另一邊沒跟上就紅。

| 契約測試 | 守的是 | 兩邊 |
|---|---|---|
| `imageGeomContract`（既有） | 片段疊層幾何 | `imagegeom.js` ↔ `export-plan.js` |
| **`subtitleStyleContract`（新，173 筆）** | 字幕樣式 | `styleToCss()` ↔ `styleToAssStyleLine()` |
| **`clipFadeContract`（新，33 筆）** | 片段淡入淡出 | `clip-fade.js` ↔ `export-plan.js` 的 `fade`／`afade` |

樣式契約鎖住的是每一項會**靜默**壞掉的對應關係：字級（CSS px ＝ ASS Fontsize × 0.75，
因為 libass 把 Fontsize 當 pt）、旋轉方向（CSS 順時針為正、ASS 逆時針為正，兩者互為相反數）、
外框（ASS 向外擴 N、CSS 是置中描邊所以要 2N）、直書時 ASS `Spacing` 必須歸零、
背景色塊走 `BorderStyle=3`、以及對齊的 numpad 對應。

淡入淡出的長度與視窗原本散在三處（預覽的 alpha、匯出的影像 `fade`、匯出的音訊 `afade`），
三份都各自寫著 `Math.max(0.001, c.out - c.in)`。現在規格集中在 `clip-fade.js`，
匯出側各自套用在自己的 filtergraph 上，由契約測試鎖住。

### 🧹 交付規格的規則不再困在對話框裡

- 順帶修掉一個會越播越慢的效能問題：找關鍵幀本來是逐顆掃，長片（兩小時＝17 萬顆）每一幀、每一層都要掃一次。

> **Range 的坑**：Chromium 的 `file://` loader 會**套用 Range 卻回 200 且不給 `Content-Range`**（實測），而真正忽略 Range 的實作會回整個檔案——兩者狀態碼相同，**只有長度能分辨**。故 `fetchRange` 一律用長度把關，長度不符即報錯，絕不把「整檔」當「某段」餵進 decoder（那會解出花屏，而且錯得很安靜）；並在開場先用 1KB 探針確認此來源真的支援 Range。
> **退路**：moov 不在檔頭（非 +faststart 的外來檔）→ 明確失敗並靜靜退回原本的整檔路（1.5GB 上限仍適用於此路）。本專案產生的 proxy 一律 `+faststart`，走主路。
> 真機驗證：①索引正確性——只讀檔頭建的索引與整檔 demux **逐顆比對 500/500 全等**（時間戳／類型／大小／keyIdx／avcC），位元組 **500 顆 byte-for-byte 相同**。②真長片——`stream_loop` 造出 **1.66GB／67 分鐘／100,500 幀**（超過舊上限）：索引 **39ms**、片頭／33 分／65 分三處 seek 全部解出正確幀、常駐位元組 **2.5MB**、**JS heap 30MB**。③端到端——當成真媒體載入，三處 seek 皆 `mode:wc`（引擎真的接管、非退回）、畫面有內容、連續播放 fedIdx 正常推進（≈26fps）；燒錄時碼佐證：seek 到 3900 秒、素材 20 秒迴圈，3900÷20 整除 → 應落在迴圈第 0 幀，畫面顯示 `00:00:00.000` 完全吻合。④退路——84.6MB 非 faststart 檔：`demuxIndex` 明確失敗、自動退回整檔路後仍 `mode:wc` 並畫出真畫面。

### 修復（桌面版 mpv／MXF）— 加入影片後無法播放的真正主因
- **mpv 多音軌濾鏡在跨檔切換時失效**：mpv 啟動播放多音軌影片時會帶 `--lavfi-complex=[aid1][aid2]…amix`（把多條音軌混音）。當序列跨段切換到**音軌數不同**的另一支影片（`loadfile`）時，這個全域濾鏡引用了不存在的音軌 → mpv 濾鏡圖初始化失敗、**整段完全無法播放**，且過程無聲無息（錯誤被吞掉）。現在**換檔前一律清空 lavfi-complex**，換檔後音訊由已抽取的逐聲道音軌接管。此為「加入其他影片後無法播放」的根本原因。（以雙音軌 MXF＋單音軌 MXF 於桌面版實機驗證：跨段連續播放、雙向切換、移除後回歸皆正常）
- **失敗不再無聲**：`loadfile` 失敗或 mpv 回報播放錯誤（`end-file reason=error`）時，狀態列與提示會明確顯示，並在主控台記錄檔名，便於診斷。
- **除錯把手常駐**：`window.SUB` 於桌面版也保留（單機工具無安全顧慮），方便遇到問題時開 DevTools 檢視狀態或遠端協助診斷。

## [v4.6.2] — 2026-07-09

### 修復（桌面版）
- **加入影片後無法播放**：加入序列會觸發新段的背景轉檔（音軌/波形抽取），而轉檔管線原本「新工作強制終止舊工作」——把**正在餵播放器的邊轉邊播串流**（或主媒體的音軌抽取）殺掉，導致播放中斷。序列「加入」的轉檔現改為**排入佇列**：不搶佔、待進行中的工作完成後依序執行（磁碟 I/O 也不再互相干擾）。取代式載入仍維持搶佔（換檔理應釋放資源）。
