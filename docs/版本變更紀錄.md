## [v4.34.7] — 2026-07-19

### 修正與優化：即時樣式預覽卡頓與半透明外框問題

- **效能優化 (app.js / subtitles.js)**：
  - 修復在拖曳或調整軌道樣式數值時，因為大量重繪 UI 與產生龐大的 ASS 檔而導致主線程卡死的問題。
  - 導入了 **Live 模式即時防抖 (Throttling)**：在樣式面板拖曳數值時，預覽引擎現在「只會計算並轉換當下影片時間點前後 5 秒內」的字幕。
  - 將下方字幕列表的小字樣式摘要 (Style Summaries) 更新加上 200ms 防抖，大幅減輕主線程的 DOM 更新壓力，確保樣式調整能達成絲滑的 60fps 體驗。
- **樣式修正 (substyle.js / app.js / index.html)**：
  - 修正了在 ASS (MPV) 渲染器下，當開啟背景底色 (`BorderStyle=3`) 且附帶框線 (`Outline`) 時，外框被渲染為不透明並覆蓋住半透明底色的問題。現在會自動將外框色強制同步為含 Alpha 透明度的底色，讓底色完美向外延伸長大。
  - 移除了網頁端預覽中強制覆蓋 `padding` 的寫死邏輯，改為由 `substyle.js` 同步計算 `margin` 與 `padding`，讓網頁預覽也能正確反映框線所撐大的底色範圍，且不會因為負邊距出錯而產生位移。
  - 將「編輯常用樣式」裡的範例文字輸入框從單行 `<input>` 改為多行 `<textarea>` 並加高，方便多行編輯。
  - 為範例文字輸入框加上了獨立的 `keydown` 攔截 (`stopPropagation`)，避免在修改多行預覽文字時，按下 `Enter` 換行或方向鍵被底層的快捷鍵捕獲而觸發播放跳轉。

## [v4.34.6] — 2026-07-19

### 修正：首幀代理影片載入無限後退、接管時字幕尺寸跳動與無法拖曳

- **player.js**：
  - 修復 _discarded 與 GOP 起點邏輯，改以 GOP 關鍵影格實體索引 (ki < this._fedFrom) 判斷跨區塊後退尋址，徹底解決時間軸首幀無限 reseek 重設解碼器的 Bug，確保初始載入能立刻接管。
  - 增加 needsComposite 判斷：單一全螢幕無特效影片不再走 WebCodecs 接管合成，交由 mpv 直接呈現，解決單影片模式下 WebCodecs 與 libass 比例不一導致的尺寸跳動。
  - 修正 _setTakeover：交回 mpv 呈現時（單影片），保留 HTML 字幕的 DOM 命中層，並加上 .mpv-hit-layer 讓字幕變透明但仍可捕捉滑鼠事件，達成 mpv 畫面中直接拖曳字幕定位的絕妙手感！
- **styles.css**：
  - 新增 .vsublayer.mpv-hit-layer .line 透明點擊層樣式。
  - 修正 .vsub-track .line 為 white-space: pre，確保多餘空白不被吞噬。
- **media.js**：
  - mpv 啟動後強制送出 emit('render:videoSub') 建立 DOM 字幕命中層。
  - 代理影片轉檔完畢後主動呼叫 	his.seek(this.displayTime()) 強制觸發畫面接管。
- **substyle.js**：
  - 修正底色與陰影映射：底色邊距改從 padding 計算並帶入 outline 大小；背景色塊啟動時，陰影改映射至 box-shadow 而非 text-shadow。
- **subtitles.js**：
  - 樣式快取 _getPresetNameForStyle 提升比對效能；樣式提示完整支援粗斜體，並在覆蓋相符時提示。

## [v4.33.2] — 2026-07-18

### 修：**WebCodecs 預覽畫布從來沒有真正顯示過**（自該功能上線起就存在）

- 症狀：開任何面板／視窗時「播放器影像不見、只剩字幕」；安全框看不到；字幕拖曳抓不到。
- 根因：`.preview-canvas` 的 **CSS 基礎規則就是 `display:none`**，而 player.js 要「顯示」畫布時寫的是 `canvas.style.display = ''` —— 清掉 inline 樣式會**回退到那條 CSS 規則**，所以畫布**永遠是隱藏的**。偏偏 `_wcTakeover` 為真時 `_syncMpvPanel` 會讓 mpv 讓位 → **mpv 藏了、畫布也沒顯示＝黑畫面只剩 HTML 字幕層**。
- 修：改為明確寫 `display='block'`。
- **為什麼過去所有驗證都沒抓到**：先前都用 `getImageData` 讀畫布像素（**隱藏的畫布照樣讀得到**）或檢查 inline `style.display`（值是 `''`，看起來「不是 none」）。兩種都測不到「有沒有真的顯示在螢幕上」。教訓已納入 `技術架構說明.md` §0.6。

### 修：對話框開著時 mpv 一律讓位，蓋掉 v4.33.1 的 keepVideo

- `_syncMpvPanel` 只要偵測到 `modalBg.show` 就隱藏 mpv，會把「編輯字幕文字視窗保留畫面」的修法覆蓋掉。改為**比照浮動面板：只有對話框真的蓋到影片區才讓位**（keepVideo 對話框靠右停、不重疊 → mpv 續留）。

> 驗證：直接證明機制——`.preview-canvas` CSS 規則為 `none`；`display=''` → computed **`none`**（畫布隱藏）；`display='block'` → computed **`block`**（顯示）。另於 mpv 模式實測到壞狀態：`wcMode:'wc'`＋`_wcTakeover:true`＋畫布 computed `none`（＝黑畫面只剩字幕）。

## [v4.29.0] — 2026-07-17

### 修：長片的即時合成預覽（疊加／溶接／子母畫面）本來一定失效
- 之前預覽引擎要把整個 proxy 讀進記憶體，**上限 1.5GB**；但實測 proxy 位元率是 **2.6–4.25 Mbps**（720p CRF26＋每 0.5 秒一個關鍵幀），**兩小時的片就是 2.3–3.7GB**——也就是說**任何一部長片都必然超標**，預覽只能退回 mpv，v4.20–4.22 做的疊加／溶接／子母畫面**真預覽全部看不到**。
- 改為**串流式讀取**：只讀檔頭建索引，影像位元組**播到哪抓哪**。現在**多長的片都能即時合成預覽**，且**記憶體與片長無關**。
- 順帶修掉一個會越播越慢的效能問題：找關鍵幀本來是逐顆掃，長片（兩小時＝17 萬顆）每一幀、每一層都要掃一次。

> 技術：新增 `demuxIndex(url)`——只取檔頭（4MB→24MB 兩級）餵 mp4box，靠 `buildSampleLists()` 從 `stco/stsz/stts/ctts/stss` 算出每顆樣本的 `offset/size/cts/is_sync`（**這些全在 moov 裡，不需要 mdat**），索引僅約 10 萬顆×數十 byte。`SampleReader` 以「對齊格線的樣本視窗」按需抓位元組（上限 48 顆或 4MB，常駐 4 個視窗），同來源疊多軌時共用。`_keyBefore` 改在 `keyIdx` 上二分搜尋。
> **Range 的坑**：Chromium 的 `file://` loader 會**套用 Range 卻回 200 且不給 `Content-Range`**（實測），而真正忽略 Range 的實作會回整個檔案——兩者狀態碼相同，**只有長度能分辨**。故 `fetchRange` 一律用長度把關，長度不符即報錯，絕不把「整檔」當「某段」餵進 decoder（那會解出花屏，而且錯得很安靜）；並在開場先用 1KB 探針確認此來源真的支援 Range。
> **退路**：moov 不在檔頭（非 +faststart 的外來檔）→ 明確失敗並靜靜退回原本的整檔路（1.5GB 上限仍適用於此路）。本專案產生的 proxy 一律 `+faststart`，走主路。
> 真機驗證：①索引正確性——只讀檔頭建的索引與整檔 demux **逐顆比對 500/500 全等**（時間戳／類型／大小／keyIdx／avcC），位元組 **500 顆 byte-for-byte 相同**。②真長片——`stream_loop` 造出 **1.66GB／67 分鐘／100,500 幀**（超過舊上限）：索引 **39ms**、片頭／33 分／65 分三處 seek 全部解出正確幀、常駐位元組 **2.5MB**、**JS heap 30MB**。③端到端——當成真媒體載入，三處 seek 皆 `mode:wc`（引擎真的接管、非退回）、畫面有內容、連續播放 fedIdx 正常推進（≈26fps）；燒錄時碼佐證：seek 到 3900 秒、素材 20 秒迴圈，3900÷20 整除 → 應落在迴圈第 0 幀，畫面顯示 `00:00:00.000` 完全吻合。④退路——84.6MB 非 faststart 檔：`demuxIndex` 明確失敗、自動退回整檔路後仍 `mode:wc` 並畫出真畫面。

## [v4.6.3] — 2026-07-09

### 修復（桌面版 mpv／MXF）— 加入影片後無法播放的真正主因
- **mpv 多音軌濾鏡在跨檔切換時失效**：mpv 啟動播放多音軌影片時會帶 `--lavfi-complex=[aid1][aid2]…amix`（把多條音軌混音）。當序列跨段切換到**音軌數不同**的另一支影片（`loadfile`）時，這個全域濾鏡引用了不存在的音軌 → mpv 濾鏡圖初始化失敗、**整段完全無法播放**，且過程無聲無息（錯誤被吞掉）。現在**換檔前一律清空 lavfi-complex**，換檔後音訊由已抽取的逐聲道音軌接管。此為「加入其他影片後無法播放」的根本原因。（以雙音軌 MXF＋單音軌 MXF 於桌面版實機驗證：跨段連續播放、雙向切換、移除後回歸皆正常）
- **失敗不再無聲**：`loadfile` 失敗或 mpv 回報播放錯誤（`end-file reason=error`）時，狀態列與提示會明確顯示，並在主控台記錄檔名，便於診斷。
- **除錯把手常駐**：`window.SUB` 於桌面版也保留（單機工具無安全顧慮），方便遇到問題時開 DevTools 檢視狀態或遠端協助診斷。

## [v4.6.2] — 2026-07-09

### 修復（桌面版）
- **加入影片後無法播放**：加入序列會觸發新段的背景轉檔（音軌/波形抽取），而轉檔管線原本「新工作強制終止舊工作」——把**正在餵播放器的邊轉邊播串流**（或主媒體的音軌抽取）殺掉，導致播放中斷。序列「加入」的轉檔現改為**排入佇列**：不搶佔、待進行中的工作完成後依序執行（磁碟 I/O 也不再互相干擾）。取代式載入仍維持搶佔（換檔理應釋放資源）。

### 重大修復
- **24 / 30fps 時碼漂移回歸**：修復 v4.3.1 統一 `getExactFps` 時容差設定過寬（0.05）導致整數影格率被誤判為 NTSC 分數影格率的問題（24 → 23.976、30 → 29.97，時碼每小時漂移約 3.6 秒）。容差收緊為 0.01，24/30fps 專案時碼恢復精準；29.97/23.976 的實測值（如 ffprobe 的 29.97002997）仍正確對應。
- **桌面版拖放影音未觸發轉檔**：拖放匯入的影音現在與「🎬 影音」按鈕走同一條桌面路徑（ffprobe 實測 FPS、系統 ffmpeg 背景轉檔／多音軌抽取、mpv 秒開）。先前拖放一律落到瀏覽器路徑，MXF 等非原生格式會卡在 ffmpeg.wasm 的 1.6GB 上限而無反應。（Electron 32 起 `File.path` 已移除，改由 preload 的 `webUtils.getPathForFile` 解析路徑）
- **關閉程式時的存檔競態**：關閉前選「儲存」現在會等存檔真正完成才關閉視窗；在存檔對話框按取消則返回編輯畫面。先前固定 500ms 後強制關窗，新專案可能在挑選路徑時被關閉而遺失資料。

### 行為修訂
- **調整持續時間（修訂 v4.2.0 規則）**：「已重疊的字幕保留不動」現在只適用於**加長**；**縮短**（負值或百分比 < 100）照常執行，並以下一句 in 點為下限——因此可以用縮短功能順勢修復既有重疊。狀態列同時改為回報實際調整條數與跳過條數（例：「已調整 60 條…跳過 40 條已重疊」）。
- **位移政策統一**：鍵盤 `P` 位移與調整視窗的位移行為一致——皆不再自動裁切／刪除被重疊到的鄰居字幕（v4.2.0 政策延伸至快捷鍵路徑）。

### 修復
- **切換 FPS／開啟專案時的內部錯誤**：修復時碼對齊影格後因呼叫到不存在的函式而中斷重繪、時間軸區塊與列表時碼不同步的問題。
- **FPS 自動偵測（網頁版）**：偵測值不再先四捨五入成整數，29.97／23.976 影片可正確辨識（不再被判成 30／24）。
- **多關鍵字搜尋高亮**：以 `||` 搜尋多個關鍵字時，後面的關鍵字不再命中前面插入的高亮標記本身而拆壞列表顯示。
- **複製軌道**：新軌道現在會正確帶上來源軌道的字級（先前一律變回預設 60）。
- **Excel 匯出**：軌道名稱含引號時不再產生損毀的 .xlsx。
- **無音軌影片（網頁版）**：非原生格式且沒有音軌的影片不再誤報「轉檔失敗」，片長與時間軸正常更新。
- **軌道拖曳重排**：重排後字幕列表跟隨原本顯示的那條軌道，不再停在舊位置顯示別軌內容。
- **文字編輯**：失焦存回文字時的尾端換行處理與輸入過程一致，不再多出一個空行。

### 內部
