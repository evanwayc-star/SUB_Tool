# ADR-0001：每份交付各自一個 ffmpeg 程序

## 狀態

已接受（2026-07-25，設計階段；尚未實作）

## 背景

匯出佇列要能同時產出多份交付（不同格式、不同交付解析度）。ffmpeg 支援
**單次讀取、多路輸出**——一個程序讀一次來源、用 `split` 分岔濾鏡、寫出多個檔案。
本專案的典型素材是 44GB MXF 與 186GB ProRes，讀取成本極高，這個作法很有吸引力，
而且先前的匯入實測已驗證過它可行。

但使用者對匯出流程的要求是：逐份暫停／繼續／停止、隨時追加新的交付、
一份失敗不影響其他、每份各自顯示進度與預估時間。

## 決策

**一份交付起一個 ffmpeg 程序。** 佇列預設同時只跑 1 個，並行度可調。

## 理由

單一 ffmpeg 多輸出的 argv 在啟動時就固定了，因此：

- 無法只暫停或只停止其中一份，只能整批一起；
- 無法在執行中追加交付；
- 一份輸出失敗會讓整個程序倒掉，其他份一起賠上；
- 只有一條總進度，給不出逐份的 ETA。

這四點正好是使用者要的互動性的全部內容。換句話說，單一 ffmpeg 多輸出換來的是一個
**無法互動的黑盒批次**，與需求直接牴觸。

並行度預設 1 而非「全開」，是因為 `electron/main.js` 既有註解記錄過的教訓：
同一實體檔案重複開 input 會建立過多 hwaccel 實例耗盡 VRAM。兩個 NVENC 匯出同時跑，
在大型 MXF 上很可能比排隊還慢，還會把預覽播放拖垮。並行度給使用者當旋鈕，不當預設。

## 代價

**N 份交付＝N 次完整讀取＋N 次合成＋N 次字幕燒錄。** 在 44GB MXF 上這不是零頭。
我們明確接受這個定價，換到的是第一份交付的完成時間不被其他份拖住，以及全部的互動性。

## 未來若總批次時間真的痛

解法是加一層**共用中間母帶**：先合成一次無損／ProRes 母帶，各份交付再從母帶轉。
仍是 N 趟，但每趟讀的是便宜很多的來源，而且每份交付依然獨立可停。

**不要因此回頭改用單一 ffmpeg 多輸出**——那會把上面四項互動性一起退回去。
