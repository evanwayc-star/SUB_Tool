# 語音辨識引擎改善評估

初次研究：2026-08-25。文件、主要來源與目前工作樹重新查核：2026-10-21。

本文供維護者判斷改善方向，區分目前實作與尚未完成的提案。範圍為 OpenAI、Groq、Gemini、本機 Transformers.js／Whisper；Azure Speech 與 ElevenLabs 不做本次供應商比較。操作入口見[使用說明](../使用說明.md#8-語音辨識與文本匹配)，實作變更日期見[版本紀錄](../版本變更紀錄.md)。

## 1. 先分開評估三種品質

| 品質 | 要量測的內容 |
|---|---|
| 文字 | 繁中 CER、英文 WER、專有名詞、重複與幻覺文字 |
| 時間 | 起訖誤差、倒退、負時長、重疊、跨越長靜音 |
| 斷句 | 語意邊界、顯示時間、閱讀速度與需人工修整比例 |

模型產生一段好讀的文字，不能證明每個字幕邊界準確。原生 word timing、段落時間、提示詞估計時間應保留不同的證據等級。

## 2. 供應商能力與實作狀態

| 路徑 | 主要來源支持的能力 | SUB Tool 目前行為 |
|---|---|---|
| OpenAI | `whisper-1` 提供 word／segment timestamps，但官方已公告 2027-02-26 關停；`gpt-transcribe` 提供文字轉寫與 prompt、keywords、languages 上下文 | 目前雲端字幕路徑仍使用 `whisper-1`，請求 `verbose_json` 與 word＋segment；未新增 `gpt-transcribe` 選項 |
| Groq | Whisper API 可要求 word 與 segment，並回傳段落品質 metadata | 使用 `whisper-large-v3`；保留逐字證據與長音訊分段去重 |
| Gemini | 音訊理解可按提示轉寫；structured output 可限制 JSON 結構 | 設定 JSON MIME，尚未加入 response schema；模型需同時通過明確音訊能力清單與 Models API 的 `generateContent` 准入，已拒絕缺值、非有限、負值與倒置時間 |
| 本機 Whisper | Transformers.js 可使用 timestamped 模型與近似 word timing | 使用 timestamped Tiny／Base／Small／Large v3 Turbo；29 秒 chunk、5 秒 stride，保留 WebGPU→WASM 退路 |

OpenAI 的時間碼與上下文能力依[檔案轉寫指南](https://developers.openai.com/api/docs/guides/speech-to-text)及[Create transcription 規格](https://developers.openai.com/api/reference/resources/audio/subresources/transcriptions/methods/create)查核；Groq 依[Speech to Text](https://console.groq.com/docs/speech-to-text)；Gemini 依[音訊理解](https://ai.google.dev/gemini-api/docs/audio)與[structured outputs](https://ai.google.dev/gemini-api/docs/structured-output)；本機能力依 [Transformers.js 3.3.3 pipeline](https://github.com/huggingface/transformers.js/blob/3.3.3/src/pipelines.js)及 [timestamped 模型卡](https://huggingface.co/onnx-community/whisper-small_timestamped)。

### OpenAI：文字優先與字幕時間應分開

官方指南將逐字／逐段時間的相容路徑保留給 `whisper-1`，並已公告其於 2027-02-26 關停。這是既有功能的遷移期限，尚不代表目前請求已失效。`gpt-transcribe` 的上下文參數不是逐字時間碼；`languages` 與舊模型的單一 `language` 也不是同一契約，不可直接共用請求欄位。[官方指南](https://developers.openai.com/api/docs/guides/speech-to-text)

可研究獨立的文字優先選項；若需要文字與另一輪 timing 對齊，必須量測額外成本、延遲與兩份文字差異，不預設增加第二次雲端請求。這是產品提案，尚未實作。

### Groq：先評估現有 words 與品質資訊

現有模型已能提供較細的時間證據，下一步應用固定驗證集校準異常標記，不憑任意常數判定低品質。供應商的多音軌處理不能代替本專案的來源聲道選擇；應檢查實際送出的 PCM／WAV。[Groq 官方文件](https://console.groq.com/docs/speech-to-text)

### Gemini：格式有效不等於邊界準確

2026-10-19 查核時，本專案 resolver 仍優先 2.5／2.0，並保留 1.5 候選；Google 音訊範例當時已使用 `gemini-3.8-flash`，停用表也列出 2.0 Flash 在 2026-06-01 關停。這是當時實作的問題紀錄。[音訊範例](https://ai.google.dev/gemini-api/docs/audio)、[生命週期表](https://ai.google.dev/gemini-api/docs/deprecations)

2026-10-21 的修復保留 2.5 Flash 的優先順序，但只有帳號分頁列表實際列出、宣告 `generateContent`，且已核對官方音訊輸入及結構化文字輸出能力的模型才能送出。已移除任意 Flash／第一個模型與停用型號 fallback；候選能力清單集中於既有 adapter。Models API 只有生成方法欄位，不能從 `generateContent` 單獨推定音訊能力。[Models API](https://ai.google.dev/api/models)、[2.5 Flash 能力](https://ai.google.dev/gemini-api/docs/models/gemini-2.5-flash)、[音訊範例](https://ai.google.dev/gemini-api/docs/audio)

原本缺時間或非有限數字會被補造起訖，倒置時間也可能在後續映射變成正常外觀。現在 Google adapter 只接受有限、非負且終點大於起點的證據，保留合法零與數字字串；混合結果略過壞時間，全無有效時間則明確失敗。真 provider → session → commit 回歸核對未建立假 timed 字幕；這是受控回傳資料的驗證，沒有使用雲端金鑰實測。權限、金鑰、流量與一般請求錯誤直接保留，僅模型不存在或明確音訊不支援才嘗試另一個已准入候選。

Response schema、來源範圍、單調性與品質檢測仍是提案。依公開介面的保守推論，提示生成的段落時間不應宣稱為原生逐字 offset；schema 也只約束資料結構。[Structured outputs](https://ai.google.dev/gemini-api/docs/structured-output)

### 本機：保留近似時間的限制

Whisper word timing 是對齊推定值，應量測實際邊界誤差。已採用的 timestamped 模型與 word 模式，不代表每個字都能可靠定位；注意缺失、零長度與跨段重複。首次模型下載、記憶體與推論時間也應納入比較。[Transformers.js pipeline](https://github.com/huggingface/transformers.js/blob/3.3.3/src/pipelines.js)

## 3. 已有的共用處理

目前程式可直接核對：

- [speech-recognition-engine.js](../../src/speech-recognition-engine.js)：來源混音與 16 kHz mono、雲端請求、600 秒／10 秒 overlap、跨 core 唯一逐字證據去重、OpenCC 字形轉換。桌面可暫壓 MP3，網頁或壓縮失敗保留 WAV 分段。
- [speech-recognition-worker-runtime.js](../../src/speech-recognition-worker-runtime.js)：本機分段與生成參數。
- [transcript-alignment.js](../../src/transcript-alignment.js)：優先利用 words 對齊逐行稿；缺少可靠時間時保留原稿及未定時佔位。
- [speech-recognition-session.js](../../src/speech-recognition-session.js)：工作所有權、取消、結果審閱與提交。

OpenCC 統一顯示字形，不能算作修復辨識錯字。辨識輸入的全部來源混音／指定來源聲道，只影響本次分析；不改專案 bus、監聽或交付配線。最後兩軌選項使用確切來源座標，不猜測 Stereo／對白等語意。

## 4. 尚待驗證的改善

| 優先 | 提案 | 驗收重點 |
|---|---|---|
| P0 | Gemini schema、來源範圍與單調性驗證 | 在已完成模型准入及基本時間驗證之外，檢測跨越來源範圍與異常順序 |
| P0 | provider-neutral word splitter 與 timingEvidence | 共用斷句；估計時間不偽裝原生逐字證據 |
| P1 | OpenAI 文字優先、可選雙階段對齊 | 同一素材比較文字、時間、成本與延遲 |
| P1 | 本機英文模型選項、近似時間品質標記 | 下載與記憶體可接受；實際誤差有量測 |
| P1 | 段落品質 metadata 轉人工複核提示 | 閾值由繁中／英文樣本校準 |

建議的統一證據結構含 `text`、`words`、`segments`、`timingEvidence`、`providerMetadata`。這是設計提案，不能當成目前所有 adapter 都已提供的欄位。

逐行稿的每一非空行應完整保留，不合併、不重斷句；無可靠時間就保留未定時狀態。少量漏句的受限插值必須清楚標為待校對，缺少可靠雙側錨點不得補造精準時間。領域定義見 [CONTEXT.md](../../CONTEXT.md)，提交政策以目前 session 與 commit engine 為準。

## 5. 評測與重新查核

固定繁中／英文樣本應涵蓋多人、快速語速、背景音樂、專名、長靜音與長片，記錄文字錯誤率、起訖絕對誤差、無效時間數、人工修整比例、推論時間、峰值記憶體、下載量與雲端成本。逐行稿另核對輸出行數及文字完整性。

本次僅重新查核文件與程式，不宣稱完成跨供應商品質排名。API、模型、套件或音訊前處理變更時，重查主要來源並重跑同一批樣本；帳號實際可用模型仍須由該帳號驗證。
