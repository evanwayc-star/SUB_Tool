# 語音辨識引擎改善評估

> 研究日期：2026-08-25
> 範圍：OpenAI、Groq、Google Gemini 與本機 Transformers.js / Whisper；Azure Speech 不在本次供應商評估範圍。
> 資料原則：只使用供應商官方文件、官方 API 規格與官方原始碼；API 與模型狀態會變動，實作前應再核對。

## 1. 結論摘要

SUB Tool 可以同時改善「辨識文字」、「時間碼」與「字幕斷句」，但這三件事不應再當成同一個模型輸出：

1. **OpenAI** 應提供兩種明確模式：`gpt-transcribe` 做「文字優先」，`whisper-1` 加 `word` 時間碼做「字幕時間碼優先」。OpenAI 官方把 `gpt-transcribe` 列為錄音轉寫的建議起點，但也明確說明需要逐字／逐段時間碼時要用 `whisper-1`。[OpenAI 檔案轉寫指南](https://developers.openai.com/api/docs/guides/speech-to-text)
2. **Groq** 是現有雲端選項中最容易立即改善字幕時間碼的一個：現用 `whisper-large-v3` 已是 Groq 官方建議給錯誤敏感、多語需求的模型，API 又原生支援同時回傳 `word` 與 `segment` 時間碼。[Groq Speech-to-Text](https://console.groq.com/docs/speech-to-text)
3. **Google Gemini** 可用來轉寫、標點與語意整理，也能按提示詞產生「帶時間的片段」；但 Google 自己將專用 Speech-to-Text 指向 Google Cloud Speech-to-Text，Gemini 文件也沒有定義可直接依賴的逐字 offset 回應。因此 Gemini 時間碼應標示為「模型估計的段落時間」，不應當成專業字幕的逐字時間來源。[Gemini Audio understanding](https://ai.google.dev/gemini-api/docs/audio)
4. **本機 Transformers.js / Whisper** 可改用帶 alignment heads 的 `_timestamped` ONNX 模型並設 `return_timestamps: "word"`；但 Hugging Face 官方原始碼明確將 Whisper 逐字時間說明為由 cross-attention 經 DTW 推定的「近似值」，必須再做單調性、重疊與異常間隔驗證。[Hugging Face ASR pipeline 原始碼](https://github.com/huggingface/transformers/blob/main/src/transformers/pipelines/automatic_speech_recognition.py#L244-L266)
5. **斷句應收斂為 SUB Tool 的共用後處理**：供應商回傳的 segment 不等於好讀的字幕句。應先保留逐字時間證據，再依標點、字詞間隔、最長顯示時間與字數生成 cue。現有文本匹配已能優先使用 `segment.words`，沒有 words 時才按段落時間比例分配，這是可直接延伸的接點。[現有文本匹配實作](../../src/transcript-alignment.js#L34-L69)

| 引擎 | 原生文字引導 | 原生時間證據 | 建議定位 |
|---|---|---|---|
| OpenAI | `gpt-transcribe` 有 prompt / keywords / `zh-tw`、`en` 語言提示 | `whisper-1` 才有 word / segment timestamps | 分為「文字優先」與「時間碼優先」，高品質需求可選雙階段對齊。[OpenAI 指南](https://developers.openai.com/api/docs/guides/speech-to-text) |
| Groq | prompt + ISO-639-1 `language` | word + segment，segment 另有品質 metadata | 保留 `whisper-large-v3`，開啟 words 並接共用斷句器。[Groq 指南](https://console.groq.com/docs/speech-to-text) |
| Gemini | 通用多模態提示與 structured output | 官方公開介面為提示導向的 segment analysis，無 STT `words[]` 契約 | 作文字／語意引擎；時間標為估計，成品與另一路 word timing 對齊。[Gemini 音訊指南](https://ai.google.dev/gemini-api/docs/audio) |
| 本機 Transformers.js / Whisper | 可指定 language；可依語言選多語或 `.en` 模型 | `true` 為 segment，`"word"` 為 DTW 近似 word timing | 新增 timestamped 模型檔位，保留 WASM fallback，words 必須驗證後再斷句。[Transformers.js 3.3.3 原始碼](https://github.com/huggingface/transformers.js/blob/3.3.3/src/pipelines.js#L1629-L1716) |

## 2. 目標與判斷原則

這份評估將品質拆成三個可獨立驗證的目標：

- **文字正確度**：繁體中文主要看字錯率（CER）、專有名詞、語氣詞與繁簡字形；英文主要看詞錯率（WER）、拼字與標點。
- **時間碼正確度**：逐字起訖／結束時間的誤差，以及有無負時長、倒退、重疊或跨越長靜音。
- **字幕斷句**：一個 cue 是否在自然語意邊界結束，同時符合顯示時間、字數與閱讀速度。

「逐段時間碼」只能說明一整段大致落在哪裡，無法支撐把段內任意一句拆開後仍保有準確邊界。因此，供應商回傳 `word` 時間碼時，SUB Tool 應保留它；只回傳 segment 或由模型生成時間時，UI 與資料結構也應讓這個品質差異可見。

## 3. SUB Tool 現況

- 引擎會將音訊轉為 16 kHz 單聲道，也已有把多個音訊 buffer 等量平均混音的函式；所以此層並非只能處理某一聲道。不過「所有來源都有混入」不等於「人聲最清楚」：5.1、M&E、FM 或相位不同的來源可能稀釋甚至抵消對白，辨識前仍需要可驗證的音訊來源選擇。[音訊預處理](../../src/speech-recognition-engine.js#L95-L181)
- OpenAI 與 Groq 共用的請求現已送出 `verbose_json` 及 word + segment `timestamp_granularities[]`，並將 words 掛回唯一所屬 segment。長音訊採 600 秒／10 秒 overlap，先依 core 中點分配，再用兩邊完整逐字序列中「文字相同、時間接近且雙向候選唯一」的 word 移除 timestamp 抖動造成的跨 core 重複；候選不唯一時保留證據，不冒險刪除真實重複台詞。桌面版只在辨識當下將已混音 WAV 暫壓為 64 kbps MP3，網頁／壓縮失敗則保留 `<20 MB` WAV 分段。[現有 OpenAI/Groq 實作](../../src/speech-recognition-engine.js)
- Gemini 目前以提示詞要求模型自行生成 `start` / `end` / `text`，只設 `application/json`、沒有 schema，並會嘗試從自由文字中擷取 JSON。[現有 Gemini 實作](../../src/speech-recognition-engine.js#L362-L505)
- Gemini 模型解析器仍優先尋找 `gemini-1.5-*` 與 `gemini-2.0-*`，且最後回退到 `gemini-1.5-flash`。[現有 Gemini 模型選擇](../../src/speech-recognition-engine.js#L325-L356)
- 本機 worker 已改用 `_timestamped` 模型、29 秒 chunk／5 秒 stride 與 `return_timestamps: "word"`；正規化器會修補零長度／倒退時間並將 words 依標點、停頓、時長與字數組成字幕段，同時保留 `words[]` 給文本匹配。[現有本機生成參數](../../src/speech-recognition-worker-runtime.js)
- 繁中結果目前會用 OpenCC 轉成台灣繁體字形；這能統一字形，但不會修復「語音本身辨識錯」的字。[現有繁體轉換](../../src/speech-recognition-engine.js#L63-L72)

## 4. 供應商逐項評估

### 4.1 OpenAI

#### API 原生能力

- OpenAI 目前建議錄音轉寫從 `gpt-transcribe` 開始；需要逐字時間、字幕格式等專項功能時，再選專用模型。[OpenAI 檔案轉寫指南](https://developers.openai.com/api/docs/guides/speech-to-text)
- `gpt-transcribe` 原生接受 `prompt`、`keywords` 與 `languages`；語言提示支援 `zh-tw`。官方將這些參數定位為改善領域專有名詞與多語音訊的上下文。[OpenAI 轉寫上下文與語言](https://developers.openai.com/api/docs/guides/speech-to-text#add-transcription-context)
- `whisper-1` 支援 `verbose_json` 加 `timestamp_granularities[]=word` 或 `segment`；官方文件明確說明這個時間粒度參數只支援 `whisper-1`。[OpenAI 時間碼指南](https://developers.openai.com/api/docs/guides/speech-to-text#timestamps)
- `prompt` 可引導專名、縮寫、標點、大小寫、語氣詞與書寫系統；`whisper-1` 的 prompt 上限為 224 tokens，而官方也說明其可控程度低於建議的新轉寫模型。[OpenAI prompting 指南](https://developers.openai.com/api/docs/guides/speech-to-text#prompting)
- 現行 API 另有 `chunking_strategy` 可做音量正規化與 VAD 邊界選擇；`gpt-4o-transcribe` 系列可額外回傳 token log probabilities，但這不是 `gpt-transcribe` 或 `whisper-1` 的逐字時間。[OpenAI 轉寫 API 規格](https://developers.openai.com/api/reference/resources/audio/subresources/transcriptions/methods/create)

#### SUB Tool 可做的後處理／產品改善

1. 保留現有 `whisper-1` 作為「字幕時間碼優先」，請求同時加入 `word` 與 `segment`，並將 `words` 保存到統一辨識結果，不再只保留 segment。
2. 新增 `gpt-transcribe` 「文字正確度優先」選項，把使用者的提示詞拆為簡短上下文、專有名詞 `keywords`、語言 `zh-tw` / `en`。
3. 如果使用者同時要求更好文字與逐字時間，提供可選的「雙階段」：`gpt-transcribe` 產生文字，`whisper-1` 產生 word timing，再用文本對齊將文字映射到時間證據。這是 SUB Tool 的組合策略，會增加一次 API 成本與等待時間，不應默認啟用。
4. 不論哪個 OpenAI 模型，供應商的 segment 都只當辨識邊界證據；最終 cue 仍交由共用斷句器處理。

### 4.2 Groq

#### API 原生能力

- Groq 同時提供 `whisper-large-v3` 與 `whisper-large-v3-turbo`；官方建議錯誤敏感、多語使用情境選 `whisper-large-v3`，追求價格／效能時選 turbo。因此 SUB Tool 現行 `whisper-large-v3` 已符合「準確度優先」目標，不應為了準確度改成 turbo。[Groq 模型選擇](https://console.groq.com/docs/speech-to-text#which-whisper-model-should-you-use)
- API 支援 `verbose_json`，並能在 `timestamp_granularities[]` 同時要求 `word` 與 `segment`。segment 保留完整 metadata，word 提供字詞、起點與終點。[Groq 請求參數](https://console.groq.com/docs/speech-to-text#using-the-api)
- `language` 提示可改善準確度與延遲；`prompt` 可引導風格或陌生字的拼法，上限 224 tokens；轉寫溫度官方建議保持 0。[Groq 請求參數](https://console.groq.com/docs/speech-to-text#using-the-api)
- `verbose_json` segment 含 `avg_logprob`、`compression_ratio` 與 `no_speech_prob`，Groq 官方將它們定位為理解轉寫品質與除錯的 metadata。[Groq metadata 說明](https://console.groq.com/docs/speech-to-text#understanding-metadata-fields)
- Groq 對多音軌檔案只轉寫第一軌，並會將音訊降採樣為 16 kHz mono；超過限制或需精細控制時，官方建議使用有重疊的 chunk 再處理重疊區。[Groq 音訊與分段規格](https://console.groq.com/docs/speech-to-text#working-with-audio-files)

#### SUB Tool 可做的後處理／產品改善

1. **基礎版已完成**：保留 `whisper-large-v3`，multipart 同時要求 `timestamp_granularities[]=word` 與 `[]=segment`，並解析 `data.words`。
2. 保留 segment metadata，把可疑區間標為「建議人工複核」；閾值不可直接抄一個常數，應用 SUB Tool 的繁中／英文驗證集決定。
3. **基礎版已完成**：長音訊以 600 秒／10 秒 overlap 分段，依全域 word／segment midpoint 的不重疊 core 分配，再以正規化文字相同、時間接近且雙向候選唯一的逐字證據去重；後續仍可用固定繁中／英文樣本評估是否需要更進階的模糊文字相似度。
4. Groq 的「只辨識第一音軌」限制不應由 API 側解決；SUB Tool 已有多 buffer 混音後輸出單聲道 WAV 的路徑，應對實際送出檔做可測的聲道／音軌驗收。[現有混音實作](../../src/speech-recognition-engine.js#L153-L181)

### 4.3 Google Gemini

#### API 原生能力

- Gemini 官方將音訊能力列為音訊理解，可做轉寫、翻譯、說話者辨識與特定時間片段分析；同頁建議「專用、即時轉寫」使用 Google Cloud Speech-to-Text。[Gemini Audio understanding](https://ai.google.dev/gemini-api/docs/audio)
- 當前官方音訊範例使用 `gemini-3.7-flash` 與 Interactions API；官方模型清單也將 `gemini-3.7-flash` 列為穩定版 Flash。[Gemini 音訊範例](https://ai.google.dev/gemini-api/docs/audio) [Gemini 模型清單](https://ai.google.dev/gemini-api/docs/models)
- Gemini 2.0 Flash 的官方最早關停日為 2026-06-01，建議替代為 `gemini-3.6-flash`；因此 2026-08-25 仍將 1.5 / 2.0 當優先或最後 fallback 已不符合官方生命週期資料。[Gemini 模型停用時程](https://ai.google.dev/gemini-api/docs/deprecations)
- Gemini 支援用 JSON Schema 限制 structured output，可宣告必要欄位與類型，比單純要求 `application/json` 更能避免欄位缺失或格式漂移。[Gemini Structured outputs](https://ai.google.dev/gemini-api/docs/structured-output)
- Gemini 音訊文件展示的時間碼是提示導向的片段分析；官方文件沒有定義像 OpenAI/Groq `words[]` 那樣的 STT 逐字 offset 回應結構。這裡的結論是從官方公開介面做的保守推論，不是說 Gemini 永遠不能生成字級時間字串。[Gemini Audio understanding](https://ai.google.dev/gemini-api/docs/audio)

#### SUB Tool 可做的後處理／產品改善

1. 移除 1.5 / 2.0 的默認 fallback，改成明確的穩定、可處理音訊的模型清單；不要在列模型失敗時任意挑「第一個模型」。
2. 使用 structured output schema，要求每項必有 `start`、`end`、`text`；收到後再做數值有限性、`start < end`、單調性、不重疊、不超出音訊長度與空文字驗證。Schema 保證格式，不保證時間內容就是真實邊界。
3. 將 Gemini 結果標記為 `timingEvidence: "estimated-segment"`；它可作為語意文字、標點或二次校稿來源，但要求準確字幕邊界時，應與 Groq / OpenAI Whisper / 本機 timestamped Whisper 的 word timing 進行文本對齊。
4. 只有 segment 時不要用字數線性平均偽裝為精準逐字時間；可用比例分配當 fallback，但資料層與 UI 必須保留「估計」狀態。

### 4.4 本機 Transformers.js / Whisper

#### 套件／模型原生能力

- SUB Tool worker 目前釘住 `@huggingface/transformers@3.3.3`。[現有 worker import](../../src/speech-recognition-worker.js#L1-L18)
- Transformers.js 3.3.3 的 ASR pipeline 支援 `return_timestamps: true` 的段落時間，也支援 `return_timestamps: "word"` 的逐字時間；同一份官方原始碼也提示已知語言時指定 `language` 可改善效果。[Transformers.js 3.3.3 ASR pipeline](https://github.com/huggingface/transformers.js/blob/3.3.3/src/pipelines.js#L1629-L1716)
- Hugging Face 官方 Transformers ASR pipeline 將 Whisper word timing 定義為根據 cross-attention weights 以 DTW 推定的 approximation；`true` 則是一組字詞的 segment timing。[Hugging Face ASR pipeline 時間碼說明](https://github.com/huggingface/transformers/blob/main/src/transformers/pipelines/automatic_speech_recognition.py#L244-L266)
- ONNX Community 已有直接標示可與 Transformers.js 使用的 timestamped 模型，包含多語 `whisper-small_timestamped`、英文 `whisper-small.en_timestamped` 與 `whisper-large-v3-turbo_timestamped`。[多語 Small timestamped](https://huggingface.co/onnx-community/whisper-small_timestamped) [英文 Small timestamped](https://huggingface.co/onnx-community/whisper-small.en_timestamped) [Large v3 Turbo timestamped](https://huggingface.co/onnx-community/whisper-large-v3-turbo_timestamped)
- OpenAI 官方 Whisper 說明 `.en` 模型在純英文中通常更好，尤其 tiny / base 差異較明顯；`turbo` 是以小幅準確度損失換取更快速度的 `large-v3` 優化版。它也列出不同模型的記憶體／速度取捨。[OpenAI Whisper README](https://github.com/openai/whisper/blob/main/README.md#available-models-and-languages)
- Whisper 官方模型卡明確提醒可能生成音訊中沒說的文字，也可能產生重複文字，而且不同語言、口音與方言表現不均。[OpenAI Whisper model card](https://github.com/openai/whisper/blob/main/model-card.md#performance-and-limitations)
- Transformers.js v3 可透過 `device: "webgpu"` 啟用 WebGPU，官方文件也直接給出 Whisper ASR 範例；但不是所有瀏覽器／硬體都支援 WebGPU，因此 WASM fallback 仍必須保留。[Transformers.js WebGPU 指南](https://huggingface.co/docs/transformers.js/guides/webgpu)

#### SUB Tool 可做的後處理／產品改善

1. **基礎版已完成**：既有設定 key 保持相容，但實際載入 Tiny／Base／Small／Large v3 Turbo 對應的 `_timestamped` 模型，並一律要求 `"word"`；首次使用需重新下載 timestamped 模型，仍保留 WebGPU / WASM fallback。
2. 繁中選多語 timestamped 模型並明確傳 `language: "zh"`；純英文可增加 `.en_timestamped` tiny / base / small 檔位，而不是所有語言共用同一個多語模型。
3. **基礎版已完成**：對回傳 words 驗證有限時間與正時長，修補可由下一個開始時間界定的零長度 word，強制單調且限制在音訊長度內；後續仍應用固定影片樣本量測 DTW word timing 的實際誤差。
4. 已將 window 改為 29 秒、左右各 5 秒 stride，避開 timestamped Whisper 在恰好 30 秒 chunk 的已知邊界異常；下一階段可再加入靜音感知切點與重疊區文字相似度去重。[Transformers.js issue #1358](https://github.com/huggingface/transformers.js/issues/1358)
5. OpenCC 保留為「輸出字形轉換」，不要把它計入 ASR 正確度改善；評測時應同時報告轉換前的辨識 CER 與轉換後的顯示字形正確性。

## 5. 共用斷句與文本匹配架構

### 5.1 統一辨識證據，不直接統一供應商輸出

建議每個 provider adapter 都轉成下列領域結構：

```js
{
  text,
  words: [{ text, start, end, confidence? }],
  segments: [{ text, start, end, confidence? }],
  timingEvidence: 'word' | 'segment' | 'estimated-segment',
  providerMetadata
}
```

- OpenAI `whisper-1`、Groq 與 timestamped 本機 Whisper 可以提供 `word`。
- OpenAI `gpt-transcribe` 在單次純文字模式沒有可當逐字 offset 的原生回應，應保持無 word timing；若開雙階段才結合另一路時間證據。[OpenAI 時間碼指南](https://developers.openai.com/api/docs/guides/speech-to-text#timestamps)
- Gemini 為 `estimated-segment`，除非再與有 words 的第二來源對齊。[Gemini Audio understanding](https://ai.google.dev/gemini-api/docs/audio)

### 5.2 供應商不決定字幕 cue

共用 splitter 的輸入是上述證據，輸出才是 SUB Tool cue。建議順序為：

1. 優先在句號、問號、驚嘆號等句末標點切開。
2. 無句末標點時，用 word gap 當候選邊界。
3. 到達最長顯示時間、中文字數或英文詞數上限時，在最近的合理邊界切開。
4. 修正太短 cue，但不可把 cue 邊界移過已知的下一個字或前一個字。
5. 最後才在寫入時間軸時按專案 FPS 對齊 frame，且必須再檢查不重疊。

這套規則不應各 provider 複製一份。現有 Azure word refiner 已包含標點、word gap、最長時間與連接邏輯，建議先抽成 provider-neutral splitter，再讓 Azure、OpenAI、Groq 與本機共用。[現有 Azure word refiner](../../src/speech-recognition-engine.js#L566-L741)

### 5.3 「已分好每行」的純文字稿

文本匹配模式應將使用者每一行視為不可再分的目標 cue：

- 只移除每行首尾空白；不合併、不重新斷句、不改行內文字。
- 有 word timing 時，用文本對齊找出每行對應的第一與最後字時間。
- 只有 segment timing 時，允許比例分配當 fallback，但標記為估計時間。
- 任一引擎無法可靠匹配或整次分析失敗時，仍保留每一行及原編號；該行以 `timed:false` 的 `--:--:--:--` 佔位，交由使用者後續補 In／Out，不得刪句或填入假時間。
- 現行流程分三態：完整可靠時直接建立；高覆蓋稿件只有少量、短連續漏句時，保留所有可靠時間並只為漏句建立受時長限制的 `review/interpolated` 初稿，明列需校對行號且不宣稱精準；覆蓋不足、漏句過多、缺少雙側錨點或逐格後會重疊時，可靠行保留時間，其餘行改為未定時字幕。三種狀態都建立完整原稿，不可靜默丟掉任何一行。

現有 `parseTranscriptLines()` 已會對每行 `trim()` 並略過空行，而對齊也已優先使用 `segment.words`。[現有文稿正規化與 word 證據](../../src/transcript-alignment.js#L9-L69)

### 5.4 辨識音訊來源

所有 provider 共用同一份前處理音訊。基礎版已提供「全部來源聲道等權混音」（預設）、明確的單一來源聲道，以及三軌以上依來源座標排序後的最後兩軌組；8 軌素材的預設值就是 8 軌平均，因為人聲不一定只存在某一軌。最後兩軌只顯示確切軌號，不推論為 Stereo；恰好兩軌時與全部 PCM 相同，因此不重複顯示。選擇已由 PCM／WAV 契約測試確認實際送入辨識引擎，且只影響本次辨識輸入，不改動專案 bus、預覽監聽、波形或交付輸出的聲道規則。後續若新增中心聲道名稱或監聽混音，必須先有可靠 metadata，不可只看聲道數猜語意。

## 6. 建議實作順序

| 順位 | 改善 | 預期影響 | 主要風險 |
|---|---|---|---|
| P0（基礎版已完成） | OpenAI `whisper-1` 與 Groq 同時請求 word + segment，保留 words | 不換辨識模型就能大幅增加可用時間證據 | 回應變大，仍需持續驗證異常 word 與品質 metadata |
| P0 | 抽出 provider-neutral word splitter | Azure、OpenAI、Groq、本機使用同一斷句品質 | 必須有繁中／英文與長靜音測試 |
| P0 | Gemini 改當前穩定音訊模型 + schema + 時間驗證 | 減少無效模型、JSON 漂移與壞時間段 | 模型生命週期仍需定期更新 |
| P0 | 每個結果保留 `timingEvidence` | UI 可區分原生 word timing 與模型估計 | 需資料升級與舊專案 fallback |
| P0（基礎版已完成） | 新增辨識音訊來源選擇與實際送出音訊驗收 | 預設保留全部聲道，同時可隔離特定乾淨對白軌，所有引擎同時受益 | 不可與專案 bus 或交付聲道設定混用；不可猜聲道語意 |
| P1 | OpenAI 新增 `gpt-transcribe` 文字優先，支援 keywords / `zh-tw` | 改善專名與多語文字準確度 | 無原生 word timing，選雙階段會加費加時 |
| P1 | 本機新增 timestamped 模型檔位與 `"word"` 模式 | 離線文本匹配與斷句能用更細時間證據 | 近似 timing、記憶體、下載與推論時間 |
| P1 | Groq metadata / Whisper 異常檢測轉成待複核標記 | 把容易錯、幻覺或重複區間集中給人工處理 | 閾值必須由本專案資料校準 |
| P2 | OpenAI 雙階段文字 + timing 對齊 | 在高品質成品上同時追求文字與邊界 | 雙倍請求成本、需處理兩輪文字差異 |

## 7. 驗證規格

不應只用「有產出字幕」驗收。建議建立一組固定的繁體中文與英文樣本，包含對話、背景音樂，多人、專有名詞、快速語速、長靜音與長片，每次記錄：

- 中文 CER／英文 WER。
- 字幕起點與終點的絕對誤差。
- 負時長、時間倒退、重疊、超出音訊範圍的數量。
- 系統斷句與人工參考邊界的相符率，以及最後需人工調整的 cue 比例。
- 辨識時間、峰值記憶體、下載量與雲端成本。
- 同一份已分行稿的對齊成功率；驗證輸出行數與文稿非空行數完全一致，且每行只有首尾空白被移除。

只有在同一批樣本上同時比完上述指標，才能決定某個模型或後處理是否真正讓「字比較準、時間也比較準」，而不是只讓句子看起來更漂亮。
